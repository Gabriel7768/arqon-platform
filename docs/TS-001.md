# ARQON Platform — Technical Standard Meta-Specification
## TS-001 — Version 1.0.0
**Status:** Frozen
**Owner:** Chief Architect
**Audience:** All architects, engineers, and technical leads who author, review, approve, or inherit from any Technical Standard on the ARQON Platform.
**Depends on:** EDS-001 v1.0, EES-001 v1.0, EDS-002/ESS-001 v1.0.0
**Supersedes:** None

---

## 1. Purpose of a Technical Standard

### 1.1 Definition

A **Technical Standard** is an engineering governance document that defines how a specific class of engineering artifact — a public API, a runtime specification, a state machine, a security contract, a performance contract, a test specification, an observability specification, a deployment specification, or an adapter specification — must be structured, authored, validated, versioned, frozen, and evolved across every package on the ARQON Platform.

A Technical Standard is not itself a specification for any package. It is the specification for specifications of a given class. Every package-level document of the governed class derives its structure, terminology, validation model, and governance obligations from its parent Technical Standard.

### 1.2 Problems a Technical Standard solves

Without a Technical Standard, two independent architects asked to write a public API specification for two different packages will produce documents with different section orderings, different levels of detail, different terminology, different error contract formats, and different validation criteria. The result is a documentation corpus that is internally inconsistent, difficult to audit, and insufficient to guarantee that two independent implementation teams produce compatible software.

A Technical Standard solves this by establishing, for one class of artifact:

- A single canonical document structure that every instance must follow
- A shared terminology model that eliminates semantic ambiguity between documents
- A validation framework that produces a deterministic pass/fail verdict for any document of that class
- A versioning and freeze policy that governs how standards and documents under them evolve
- A cross-reference model that prevents content duplication and circular dependency

### 1.3 Relationship to platform governance documents

The ARQON Platform governance stack has four layers. TS-001 occupies the third layer.

```
Layer 1 — Documentation Governance
  EDS-001    Engineering Documentation Standard
             Defines what documents exist and what each owns.

Layer 2 — Execution Governance
  EES-001    Engineering Execution Standard
             Defines how engineering work is performed.

Layer 3 — Specification Writing Governance
  EDS-002    Engineering Specification Standard (ESS-001)
             Defines general writing rules for all specification documents.
  TS-001     Technical Standard Meta-Specification (this document)
             Defines the mandatory structure of every Technical Standard.

Layer 4 — Technical Standards (governed by TS-001)
  API-001    Public API Specification Standard
  RT-001     Runtime Specification Standard
  SM-001     State Machine Specification Standard
  SEC-001    Security Specification Standard
  PERF-001   Performance & Concurrency Specification Standard
  TEST-001   Testing Specification Standard
  OBS-001    Observability Specification Standard
  DEPLOY-001 Deployment Specification Standard
  ADAPT-001  Adapter Specification Standard
```

**Relationship with EDS-001:** EDS-001 defines the document type taxonomy, what each type owns, and who is responsible for it. TS-001 does not change those definitions. TS-001 specifies how the standards that govern each type are internally organized.

**Relationship with EES-001:** EES-001 defines the engineering lifecycle, quality gates, and release governance that apply to all engineering work. Technical Standards are engineering artifacts; they are authored, reviewed, frozen, and versioned under EES-001. TS-001 adds Technical-Standard-specific authorship rules on top of EES-001's general lifecycle.

**Relationship with EDS-002/ESS-001:** ESS-001 defines general writing rules: modal vocabulary, forbidden language, table requirements, section numbering, change history, freeze mechanics. TS-001 inherits all of ESS-001 without modification and adds the rules specific to Technical Standards as a document class.

**Relationship with ADR documents:** ADRs record architectural decisions that create obligations. When an ADR creates an obligation affecting a class of engineering artifact (e.g., "all public APIs must expose a health-check method"), the corresponding Technical Standard is updated to encode that obligation as a normative rule. The ADR is the decision record; the Technical Standard is the enduring governance expression of that decision.

**Relationship with package specifications:** A Technical Standard is the parent of every package specification in its class. A package specification is compliant with its parent Technical Standard if and only if it satisfies every normative requirement of that standard. A package specification does not restate rules from its parent Technical Standard; it instantiates them for the specific package.

**Relationship with implementation:** A Technical Standard is implementation-agnostic. It does not specify algorithms, data structures, programming languages, frameworks, or runtime behavior. An implementation team uses the package specification (not the Technical Standard directly) as its implementation contract. The Technical Standard ensures that the package specification is complete and deterministic enough to serve that purpose.

### 1.4 Technical Standard identity

Every Technical Standard has:

- A stable identifier of the form `{DOMAIN}-{NNN}` (e.g., `API-001`, `RT-001`)
- Exactly one owner, the Chief Architect or a designated Principal Architect
- A parent document: TS-001 (this document)
- A governed document type: the EDS-001 document type whose instances it governs
- A scope statement: the exact set of package-level documents it governs

Every Technical Standard MUST contain the following sections in the order listed. No section may be omitted. The section numbering is canonical and shared across all Technical Standards. This uniformity means that §7 of any Technical Standard always contains its validation checklist, §8 always contains its completeness scoring model, and so on — making cross-standard navigation predictable for any reader.

### 2.2 Document header

Every Technical Standard's document header follows the ESS-001 §4.1 format with these additional mandatory fields:

```
# ARQON Platform — {Standard Title}
## {STANDARD-ID} — Version {MAJOR}.{MINOR}.{PATCH}
**Status:** {Draft | Under Review | Frozen | Superseded | Archived}
**Owner:** {Full name and role}
**Audience:** {One sentence naming the reader role(s)}
**Depends on:** EDS-001 v{VERSION}, EES-001 v{VERSION}, EDS-002/ESS-001 v{VERSION}[, TS-001 v{VERSION}]
**Governs document type:** {EDS-001 document type identifier, e.g., "API", "RT", "SM"}
**Governed document naming convention:** {e.g., "{PACKAGE}-API-{MAJOR}.{MINOR}.{PATCH}"}
**Supersedes:** {Document ID of prior version; "None" if version 1.0.0}
**Superseded by:** {Document ID of successor; omit if not yet superseded}
```

The `Depends on` field for a Technical Standard MUST include TS-001 at version 1.0.0 or later.

The `Governs document type` field is the EDS-001 §3 document type identifier. It is singular — each Technical Standard governs exactly one document type.

### 2.3 Purpose section content

The Purpose section of a Technical Standard MUST contain:

1. **Definition paragraph.** What the governed document type is and what problem it solves.
2. **Scope differentiation.** What this standard governs that TS-001 does not already govern.
3. **Relationship statement.** A prose table or list explaining the relationship between this standard and each governance layer document it depends on.
4. **Non-goals.** What this standard explicitly does not govern.

A Purpose section that does not contain all four of these elements is incomplete.

### 2.4 Scope section content

The Scope section MUST state:

1. **Governed documents.** The complete set of document types this standard applies to, with their EDS-001 identifiers.
2. **Non-governed documents.** Related document types that this standard does not govern (e.g., API-001 does not govern RT documents).
3. **Package applicability.** Whether this standard applies to all packages or only packages meeting a stated criterion.

### 2.5 Audience section content

The Audience section MUST identify at minimum two audiences: the primary audience (who authors documents governed by this standard) and the secondary audience (who consumes documents governed by this standard). It MUST state what each audience uses the standard for and what knowledge is assumed.

## 3. Shared Terminology

This section defines terms used normatively across all Technical Standards. A Technical Standard MUST import these definitions by reference to TS-001 §3 and MUST NOT redefine any term defined here. Additional domain-specific terms are defined in the Technical Standard's own §3 (Definitions) and MUST NOT conflict with any term defined here.

### 3.1 Normative Requirement

A **Normative Requirement** is a statement in a specification or Technical Standard that creates a binding obligation or prohibition on a conforming implementation, document, or process. Normative Requirements use the RFC 2119 modal vocabulary as defined in ESS-001 §5.1. A statement that uses normative vocabulary but cannot be tested for conformance is an invalid Normative Requirement; see **Validation Rule** (§3.9).

### 3.2 Recommendation

A **Recommendation** is a normative statement that creates a strong preference without creating an absolute obligation. It is expressed with SHOULD or SHOULD NOT per RFC 2119. Non-conformance to a Recommendation is permitted but MUST be justified in the package's IMPL document. A Recommendation that is systematically ignored by all implementations is a signal that it should be converted to a Normative Requirement or removed.

### 3.3 Constraint

A **Constraint** is a restriction on the values or states that a variable, parameter, field, or system may take. A Constraint is normative. A Constraint that is not expressible in the type system MUST be stated in an invariants table or numbered list in the governed document. A Constraint that is expressible in the type system MUST be encoded in the type definition rather than stated only in prose.

### 3.4 Invariant

An **Invariant** is a property that MUST hold at all times for a given object, type, or system across all observable states. An Invariant that is violated by any observable operation on the object or type is a defect in the specification. Invariants are normative. They are stated in invariants sections and are subject to testing obligations defined in the TEST document.

### 3.5 Compliance

**Compliance** is the state of a document, implementation, or process that satisfies every Normative Requirement applicable to it. Compliance is binary: a subject is compliant or non-compliant. Partial compliance does not exist. A subject that satisfies 99 of 100 Normative Requirements is non-compliant.

An **Exemption** is a documented, time-bounded deviation from one specific Normative Requirement, approved in writing by the Package Owner and Principal Architect, and filed as a known risk in the release record per EES-001 §9.2. An Exemption acknowledges non-compliance; it does not create a state of partial compliance.

### 3.6 Validation Rule

A **Validation Rule** is a Normative Requirement that is expressed in testable form. Every Normative Requirement in a Tier 2 document MUST be traceable to at least one Validation Rule. A Normative Requirement that cannot be expressed as a Validation Rule is a specification defect; it must be restructured to be falsifiable per ESS-001 SP5.

### 3.7 Quality Gate

A **Quality Gate** is a mandatory checkpoint in the EES-001 engineering lifecycle (EES-001 §6) at which a specific set of Validation Rules is evaluated. A Quality Gate produces a binary pass/fail verdict. Failure blocks advancement to the next lifecycle stage. Quality Gates are defined in each Technical Standard's §21 (Quality Gates section).

### 3.8 Implementation Note

An **Implementation Note** is informative content that explains the rationale behind a Normative Requirement, provides context for an Invariant, or describes a common implementation approach. Implementation Notes appear in governed documents in sections labeled `[INFORMATIVE]` per ESS-001 §4.3. An Implementation Note MUST NOT introduce a Normative Requirement, Constraint, or Invariant that is not also stated normatively elsewhere in the document.

### 3.9 Example

An **Example** is informative content that illustrates a Normative Requirement or Constraint. An Example MUST be preceded by the normative content it illustrates per ESS-001 §4.8. An Example is not a specification. In any conflict between an Example and a Normative Requirement, the Normative Requirement governs. An Example that contradicts a Normative Requirement is a documentation defect. Examples use the labeling format defined in ESS-001 §4.8.

### 3.10 Anti-pattern

An **Anti-pattern** is a documented approach that MUST NOT be used, presented as a negative Example for clarity. Anti-patterns appear in governed documents in sections labeled `[Anti-pattern — {description}]`. An Anti-pattern MUST be accompanied by the Normative Requirement it violates and the compliant alternative. An Anti-pattern is informative; it does not itself create a prohibition (the prohibition is in the normative section the anti-pattern references).

### 3.11 Extension Point

An **Extension Point** is a defined location in a specification where domain-specific or adapter-specific content may be added without modifying the base specification. Extension Points are how child Technical Standards extend TS-001, and how governed package documents extend their parent Technical Standard. An Extension Point MUST be explicitly designated in the parent document; extensions outside designated Extension Points are non-compliant.

### 3.12 Compatibility Rule

A **Compatibility Rule** is a Normative Requirement that governs the relationship between two versions of the same document. Compatibility Rules define what changes are backward-compatible (non-breaking) and what changes break compatibility (breaking). Every Technical Standard MUST define its Compatibility Rules exhaustively in §13. A change that falls outside the defined categories is treated as breaking by default.

### 3.13 Deprecation Rule

A **Deprecation Rule** is a Normative Requirement that governs the process of retiring a symbol, section, or document. Every Technical Standard MUST define its Deprecation Rules in §14. The general Deprecation Rules are defined in §4.5 of this document; Technical Standards may impose stricter rules but never looser ones.

### 3.14 Review Rule

A **Review Rule** is a Normative Requirement that defines who must review a document or change, and what criteria they apply. Review Rules for governed documents are defined in each Technical Standard's Quality Gates section (§21) and are consistent with EES-001 §6.

### 3.15 Approval Rule

An **Approval Rule** is a Normative Requirement that defines who has authority to approve a document, change, or state transition. Approval Rules for governed documents are defined in each Technical Standard's §22 (Freeze Criteria). Approval Rules are consistent with the role definitions in EES-001 §3.

## 4. Versioning Model

### 4.1 Scope of this section

This section defines the versioning model for Technical Standards themselves. The versioning model for the documents governed by a Technical Standard is defined in that standard's §13. The two models follow the same semantic versioning principles but are applied to different artifact types.

### 4.2 Semantic versioning for Technical Standards

Technical Standards follow semantic versioning: `MAJOR.MINOR.PATCH`.

**PATCH increment** — A change that corrects an ambiguity, typographical error, or broken cross-reference without changing any Normative Requirement, Validation Rule, Quality Gate, or section structure. A PATCH change does not invalidate any previously compliant governed document. No RFC required. No notification to governed document owners required. Example: correcting "interrface" to "interface" in a table caption.

**MINOR increment** — A change that adds a new Normative Requirement, Validation Rule, Quality Gate, mandatory section, or required table column to the standard without removing or changing any existing requirement. A MINOR change does not invalidate any previously frozen governed document (grandfathering, §4.6). Governed document owners are notified. New governed documents must comply with the new MINOR version. No RFC required for standards owned by the Chief Architect; RFC recommended for standards owned by a Principal Architect. Example: adding a new required table column to the method signature format.

**MAJOR increment** — A change that removes, renames, or changes any existing Normative Requirement, Validation Rule, Quality Gate, mandatory section, or required table column. A MAJOR change triggers the supersession process (§4.4). RFC mandatory with minimum 10 business day comment period for changes to TS-001 itself; 5 business days for individual Technical Standards. Example: removing a mandatory section, changing the definition of a Compatibility Rule.

### 4.3 Version progression constraints

- A Technical Standard MUST NOT skip a MINOR version (1.0.0 → 1.2.0 is non-compliant; 1.0.0 → 1.1.0 is correct).
- A Technical Standard MUST NOT skip a MAJOR version (1.0.0 → 3.0.0 is non-compliant).
- PATCH versions may be non-contiguous within a MINOR series when multiple patches are batched (1.0.1 → 1.0.5 is compliant if 1.0.2–1.0.4 were intermediate working drafts never published).

### 4.4 Supersession

**Supersession** is the process by which a new MAJOR version of a Technical Standard replaces its predecessor.

1. The new MAJOR version is authored, reviewed, and frozen under the full process.
2. Upon freezing, the predecessor's Status header is updated to `Superseded`.
3. The predecessor's `Superseded by` field is populated with the new version's ID.
4. The new version's `Supersedes` field is populated with the predecessor's ID.
5. All governed document owners are notified of the supersession.
6. A minimum 6-month transition period begins. During this period, governed documents compliant with either the old or new major version of the standard are accepted.
7. After the transition period, new governed documents MUST comply with the new MAJOR version.
8. Superseded versions are never deleted. They remain accessible as historical record.

### 4.5 General deprecation rules for governed documents

These rules apply to all governed documents. Technical Standards MAY impose stricter rules per §3.13 but MUST NOT loosen them.

- A symbol, section, or requirement may be deprecated in a MINOR version of the governed document.
- Deprecation MUST include: the item deprecated, the version it was deprecated, the removal version, and the migration path.
- The minimum period between deprecation and removal is defined by the consuming scope (EES-001 §7.6, Table).
- The removal version stated at deprecation time MUST NOT be moved to an earlier version after announcement.
- Removal of a deprecated item is a MAJOR version increment of the governed document.

### 4.6 Grandfathering policy

A governed document that was frozen while compliant with version N of its parent Technical Standard remains compliant with version N, even after a newer version of the standard is published. Grandfathering does not exempt a document from compliance obligations when it is next revised; any new version of a governed document MUST comply with the current version of its parent Technical Standard at the time of revision.

### 4.7 Backward compatibility expectations for Technical Standards

A MINOR version of a Technical Standard is backward-compatible with all governed documents frozen under any prior MINOR version in the same MAJOR series. This means governed documents do not need to be updated to remain compliant when a MINOR standard update is published — only new documents and revised documents are held to the new MINOR version.

A MAJOR version of a Technical Standard is not backward-compatible. The supersession process (§4.4) and the grandfathering policy (§4.6) together define the migration path.

## 5. Extension Mechanism

### 5.1 Purpose of extension

Technical Standards extend TS-001. Governed package documents extend their parent Technical Standard. Extension is the mechanism by which domain-specific rules are added without duplicating the rules already defined in the parent. Extension is additive only: a child document adds rules; it does not remove or weaken rules inherited from its parent.

### 5.2 Extension hierarchy

```
TS-001
  └── {DOMAIN}-001  (e.g., API-001, RT-001, SM-001)
        └── {PACKAGE}-{DOCTYPE}-{VERSION}  (e.g., I18N-API-1.0.0)
```

Rules flow downward: TS-001's rules apply to all Technical Standards; a Technical Standard's rules apply to all governed documents of that type. Rules do not flow upward: a package document's conventions do not constrain its parent Technical Standard.

### 5.3 How a Technical Standard extends TS-001

A Technical Standard extends TS-001 by:

1. **Inheriting:** Adopting all TS-001 Normative Requirements, Validation Rules, and Quality Gates without modification. The Technical Standard does not restate inherited rules; it cites TS-001 by section.
2. **Specializing:** Adding domain-specific Normative Requirements, Validation Rules, and Quality Gates that apply only to the governed document type. These are stated in the Technical Standard's domain-specific sections.
3. **Instantiating Extension Points:** Populating the Extension Points defined by TS-001 (§5.4) with domain-specific content.

A Technical Standard MUST NOT modify any rule inherited from TS-001. If a conflict exists between a Technical Standard and TS-001, TS-001 governs. The conflict MUST be reported to the Chief Architect and resolved through an RFC against TS-001.

### 5.4 Extension Points in TS-001

TS-001 defines the following Extension Points. Each Technical Standard instantiates each of these points with domain-specific content:

| Extension Point ID | Location in Technical Standard | What is filled in |
|---|---|---|
| EP-01 | §8 — Mandatory Sections | The canonical list of sections for governed package documents |
| EP-02 | §9 — Mandatory Section Ordering | The required section order for governed package documents |
| EP-03 | §10 — Required Tables | The mandatory tables in governed package documents |
| EP-04 | §11 — Notation Rules | Domain-specific notation (signatures, identifiers, units) |
| EP-05 | §12 — Domain-Specific Rules | Rules unique to this document class |
| EP-06 | §17 — Prohibited Content | Content forbidden specifically in governed documents of this class |
| EP-07 | §19 — Validation Checklist | Domain-specific checklist items appended to the universal checklist |
| EP-08 | §21 — Quality Gates | Domain-specific gates appended to the universal gates |

A Technical Standard that does not instantiate every Extension Point is structurally incomplete.

### 5.5 How governed package documents extend their parent Technical Standard

A governed package document extends its parent Technical Standard by:

1. Following the canonical section structure from the standard's EP-01 and EP-02.
2. Instantiating the required tables from EP-03 with package-specific data.
3. Following the notation rules from EP-04.
4. Complying with all rules in EP-05 and EP-06.
5. Satisfying all Validation Rules in EP-07 and Quality Gates in EP-08.

A governed package document MUST NOT add sections, change section ordering, or omit sections from the canonical structure. If a section does not apply, it MUST be present and marked "None — {reason}" per §9.1.

### 5.6 Future Technical Standards

A future Technical Standard (e.g., `DATA-001`, `PROTO-001`) is created by:

1. Filing an RFC proposing the new standard.
2. Architecture Review confirming the new document type is not already governed.
3. The new standard being authored per TS-001, instantiating all Extension Points.
4. The new standard being reviewed and frozen per §4.4 (Freeze Criteria for Technical Standards, §9.3).

A future Technical Standard MUST declare `Depends on: TS-001 v{VERSION}` in its header. It is bound by TS-001's rules at the version declared.

## 6. Cross-Reference Rules

### 6.1 Governing principle

All cross-reference rules in ESS-001 §22 apply to Technical Standards and governed documents without modification. This section adds obligations specific to Technical Standards and their governed documents.

### 6.2 Citation format

Per ESS-001 §22.1, all references use the pinned format:

> See {DOCUMENT-ID} §{N.N} — {section title}.

The document ID MUST include the full version number. A floating reference (no version) is non-compliant in any frozen Technical Standard or governed document.

### 6.3 Reference directionality — Technical Standards

The allowed reference directions for Technical Standards follow the governance layer hierarchy:

| Document | May reference | May NOT reference |
|---|---|---|
| TS-001 | EDS-001, EES-001, EDS-002/ESS-001 | Any Technical Standard, any package document |
| Any Technical Standard | TS-001, EDS-001, EES-001, EDS-002/ESS-001 | Other Technical Standards, any package document |
| Governed package document | Its parent Technical Standard, TS-001, EDS-001, EES-001, EDS-002/ESS-001, other package documents of related types | Technical Standards for different document types unless the relationship is explicitly permitted by the parent Technical Standard |

A Technical Standard MUST NOT reference another Technical Standard. If RT-001 needs to align with API-001's error contract rules, the alignment is expressed by both standards independently referencing the same EDS-001 or TS-001 sections. Cross-Technical-Standard dependencies create governance coupling that reduces the standards' independent evolvability.

### 6.4 Mandatory references per document type

Each Technical Standard MUST specify in its §18 (Cross-Reference Rules) which references are mandatory for governed documents. The following are mandatory for all governed documents regardless of type:

| Reference | When mandatory |
|---|---|
| Parent Technical Standard | Always — every governed document cites its parent standard |
| Package ARCH document | Always — every governed document is grounded in the package's module structure |
| EDS-001 | When the governed document's Change History section cites document type definitions |

### 6.5 Forbidden references

The following references are forbidden in all governed documents:

| Forbidden reference | Reason |
|---|---|
| Tier 4 documents (MIG, RUN, DEV, IMPL) as authoritative | Tier 4 documents are not contractual |
| Unfrozen documents | Unfrozen documents are not stable contracts |
| Documents without version numbers | Version-free references are floating and non-deterministic |
| Circular references | A document that creates a reference cycle with any document it depends on is non-compliant |

### 6.6 Circular reference prevention

A circular reference exists when Document A references Document B and Document B references Document A (direct cycle), or when a chain of references from A eventually returns to A (transitive cycle).

Prevention rules:
- Before filing a cross-reference, the author traces the full reference chain from the cited document and verifies it does not return to the citing document.
- The Specification Review panel checks for circular references as part of the universal validation checklist (§7.1, item U-14 per ESS-001).
- A circular reference is a blocking defect; neither document in the cycle may be frozen until the cycle is broken.

Permitted reference patterns between related package documents:

| From | To | Permitted? | Condition |
|---|---|---|---|
| RT document | API document | Yes | RT may cite API for type definitions |
| API document | RT document | Yes | API must cite RT for behavioral specification |
| RT document | SM document | Yes | RT may cite SM for state transitions |
| SM document | API document | Yes | SM may cite API for error types |
| API document | SM document | Yes | API may cite SM for lifecycle state names |
| RT document | API document, SM document | Yes | Both in same direction |
| API → RT → API | — | NO | Creates a cycle |
| SM → API → SM | — | NO | Creates a cycle |

When API cites RT and RT cites API, this is NOT a cycle because the direction is RT-cites-API-for-types and API-cites-RT-for-behavior — these are references to different sections for different purposes. A cycle requires the same information to be authoritative in two places simultaneously.

## 7. Validation Framework

Every Technical Standard MUST define a Validation Framework for governed documents. The Validation Framework is instantiated in §§19–22 of the Technical Standard. This section defines the structure that all Technical Standards share.

### 7.1 Universal validation checklist

Every Technical Standard's §19 (Validation Checklist) inherits all 20 universal checklist items U-01 through U-20 from ESS-001 §19.1 without modification. The Technical Standard appends domain-specific checklist items using identifiers of the form `{DOMAIN}-{category}-{NNN}` (e.g., `API-C-01`, `RT-S-02`, `SM-X-01`).

The checklist is organized into three tiers:

**Tier A — Universal (from ESS-001):** Items U-01 through U-20. Apply to all specification documents. Not restated in Technical Standards; cited by reference to ESS-001 §19.1.

**Tier B — Standard structural checks:** Domain-specific structural completeness items defined by the Technical Standard. Identifier format: `{DOMAIN}-S-{NNN}`. Example: `API-S-01` through `API-S-08` as defined in API-001 §23.2.

**Tier C — Standard content checks:** Domain-specific content correctness items defined by the Technical Standard. Identifier format: `{DOMAIN}-C-{NNN}`.

**Tier D — Standard consistency checks:** Cross-document consistency items defined by the Technical Standard. Identifier format: `{DOMAIN}-X-{NNN}`.

Every checklist item MUST:
- Have a unique identifier within its Technical Standard
- Be a binary pass/fail test (no partial credit)
- Reference the governing Normative Requirement by section number
- Name the responsible party (author, Package Owner, or Specification Review panel)

### 7.2 Completeness scoring model

Every Technical Standard's §20 (Completeness Scoring) inherits the five-dimension model from ESS-001 §20 and instantiates it with domain-specific scoring criteria. The five dimensions are fixed across all Technical Standards:

| Dimension | Maximum points | What it measures |
|---|---|---|
| D1 — Structural completeness | 20 | All required sections present with substantive content |
| D2 — Normative precision | 20 | Modal vocabulary used correctly; no forbidden language |
| D3 — Error path coverage | 20 | All error conditions specified per SP7 |
| D4 — Cross-reference integrity | 20 | All citations correct, pinned, non-duplicative |
| D5 — Audience appropriateness | 20 | Content scoped correctly; no off-type content |

**Total: 100 points.**

Each Technical Standard defines its domain-specific scoring rubric per dimension with five levels: 20, 15, 10, 5, 0. The rubric describes what evidence of each dimension is evaluated and what distinguishes each level.

**Thresholds are fixed and MUST NOT be changed by individual Technical Standards:**

| Score | Decision |
|---|---|
| 95–100 | Eligible for freezing |
| 85–94 | Accepted with tracked deficiencies; must be resolved before next minor version |
| 70–84 | Returned for revision |
| 0–69 | Rejected; full rewrite required |

### 7.3 Quality gates

Every Technical Standard's §21 (Quality Gates) MUST define at minimum the following gates. Additional domain-specific gates are added by the Technical Standard. Gate identifiers follow the format `{DOMAIN}G-{NNN}` (e.g., `AG-01` for API gates, `RG-01` for RT gates).

| Gate | Description | Responsible party |
|---|---|---|
| {DOMAIN}G-01 | All universal ESS-001 checklist items pass | Author + Package Owner |
| {DOMAIN}G-02 | All Tier B structural checks pass | Author + Package Owner |
| {DOMAIN}G-03 | All Tier C content checks pass | Author + Package Owner |
| {DOMAIN}G-04 | All Tier D consistency checks pass | Specification Review panel |
| {DOMAIN}G-05 | Completeness score ≥ 85 | Specification Review panel |
| {DOMAIN}G-06 | All cross-references resolve to frozen documents at stated versions | Specification Review panel |
| {DOMAIN}G-07 | No prohibited content present | Author + Package Owner |
| {DOMAIN}G-08 | Version increment is correct for changes introduced | Package Owner |

All gates must pass before a governed document advances to Frozen status. A single gate failure is a blocking defect.

### 7.4 Approval criteria

A governed document is approved for freezing when:

1. All Quality Gates pass (zero failures).
2. The Completeness Score is ≥ 85.
3. The Specification Review panel has approved in writing.
4. For MAJOR versions: the RFC is closed as Accepted and any required ADR is filed.
5. For MINOR versions: consuming teams have been notified.
6. The Package Owner has signed the validation checklist.

### 7.5 Audit expectations

The Architecture Review Board (EES-001 §9.4) conducts annual compliance audits. For Technical Standards:

- Each Technical Standard is audited to confirm its continued conformance with TS-001.
- If a MINOR or PATCH update to TS-001 has been published since the last audit, the Technical Standard's owner is notified and has 60 days to assess whether an update is needed.
- If a MAJOR update to TS-001 has been published, the supersession process (§4.4) applies.

For governed package documents:

- Compliance is audited at each major version boundary per EES-001 §9.4.
- The audit checks compliance with the version of the parent Technical Standard current at the time the document was frozen (grandfathering, §4.6).
- If the document is being revised, it is audited against the current Technical Standard version.

## 8. Ownership

### 8.1 TS-001 ownership

**Owner:** Chief Architect.

**Responsibilities:** Maintain TS-001 as the root governance document for all Technical Standards. Approve all RFCs against TS-001. Ensure consistency between TS-001 and the four governance layer documents above it.

**Version authority:** Only the Chief Architect may approve MAJOR and MINOR version increments of TS-001. The Chief Architect may delegate PATCH version approval to a designated Principal Architect.

### 8.2 Technical Standard ownership

Each Technical Standard has exactly one designated owner. The owner is named in the document header and recorded in the platform's standards registry.

**Owner responsibilities:**
- Maintain the Technical Standard in conformance with TS-001.
- Approve all changes to the standard.
- Initiate RFC processes for MAJOR changes.
- Notify governed document owners of MINOR changes.
- Conduct or delegate the Specification Review panel for governed documents.
- Respond to Architecture Review Board audit findings within 60 days.

**Ownership transfer:** Ownership transfers in writing, with a PATCH version increment to record the new owner in the document header and Change History.

### 8.3 Reviewers

Every Technical Standard has at minimum two designated reviewers named in the platform's standards registry. Reviewers are nominated by the owner and confirmed by the Chief Architect.

**Reviewer responsibilities:**
- Review all MINOR and MAJOR version changes before publication.
- Participate in Specification Review panels for governed documents.
- Provide written feedback within the review SLA defined in EES-001 §6.4.

### 8.4 Approval authority

| Change type | Approver |
|---|---|
| PATCH to any Technical Standard | Standard owner |
| MINOR to any Technical Standard | Standard owner + one designated reviewer |
| MAJOR to any Technical Standard | Standard owner + Principal Architect + Chief Architect |
| PATCH, MINOR, MAJOR to TS-001 | Chief Architect + two Principal Architects |
| New Technical Standard | Chief Architect |

### 8.5 Version authority

The standard owner controls version numbering. Version numbers are not negotiated with the Architecture Review Board — they are determined by the standard owner per the rules in §4.2 and are subject to post-publication audit rather than pre-publication approval.

## 9. Compliance Rules

### 9.1 Compliance definition for Technical Standards

A Technical Standard is **compliant** with TS-001 if and only if:

1. All 24 mandatory sections (§2.1) are present in the correct order.
2. The document header contains all mandatory fields (§2.2).
3. All 8 Extension Points (§5.4) are instantiated with domain-specific content.
4. All Normative Requirements inherited from TS-001 are honored without modification.
5. No Normative Requirements in the standard conflict with TS-001, ESS-001, EDS-001, or EES-001.
6. All cross-reference rules in §6 are followed.
7. The Validation Framework in §§19–22 follows the structure in §7.
8. The standard has passed all Quality Gates and been frozen.

### 9.2 Non-compliance definition for Technical Standards

A Technical Standard is **non-compliant** with TS-001 if any one of the conditions in §9.1 is not met. Non-compliance is binary. Partial compliance does not exist (§3.5).

### 9.3 Compliance definition for governed documents

A governed document is **compliant** with its parent Technical Standard if and only if:

1. All mandatory sections defined by the standard (EP-01, EP-02) are present in the correct order.
2. All required tables (EP-03) are present and complete.
3. All notation rules (EP-04) are followed.
4. All domain-specific rules (EP-05) are satisfied.
5. No prohibited content (EP-06) is present.
6. All validation checklist items (EP-07) pass.
7. All quality gates (EP-08) pass.
8. The document has been frozen at the current version.

### 9.4 Remediation process

When a non-compliance finding is raised against a Technical Standard or governed document:

**Stage 1 — Classification (within 5 business days of finding):**
The standard or document owner classifies the finding as:
- **Critical:** The non-compliance creates an ambiguity that can result in incompatible implementations. Blocks publication or deployment.
- **Significant:** The non-compliance reduces document quality but does not create implementation ambiguity. Blocks next version publication until resolved.
- **Minor:** The non-compliance is structural or presentational. Resolved in the next PATCH version.

**Stage 2 — Resolution planning (within 10 business days of classification):**
The owner creates a remediation plan specifying: the exact change to be made, the target version, and the timeline.

**Stage 3 — Resolution (per the remediation plan):**
The change is made, reviewed, and the document is versioned and re-frozen per standard process.

**Stage 4 — Verification (within 5 business days of the new version being frozen):**
The Architecture Review Board or delegated reviewer confirms the finding is resolved in the new version.

**Escalation:** If a Critical finding is not resolved within 30 calendar days, the Chief Architect is notified. If it is not resolved within 60 calendar days, the standard or document is placed in a non-compliant registry and may not be referenced as authoritative by other documents until resolved.

## 10. Freeze Policy

### 10.1 Freeze criteria for Technical Standards

A Technical Standard MAY be frozen only when all of the following hold:

1. All 24 mandatory sections (§2.1) are present with substantive content.
2. All 8 Extension Points (§5.4) are instantiated.
3. All inherited universal checklist items (ESS-001 §19.1, U-01–U-20) pass.
4. The Completeness Score is ≥ 85 per §7.2.
5. All minimum Quality Gates defined in §7.3 pass.
6. For MAJOR versions: RFC closed as Accepted; Architecture Review complete.
7. The document contains no "TBD", "TODO", "to be specified", or placeholder strings.
8. The Change History table is current.
9. The standard owner and at minimum one designated reviewer have approved.
10. All cross-references resolve to frozen documents at the stated versions.

### 10.2 What may change after freeze

After a Technical Standard is frozen, the following changes are permitted through the versioning process (§4.2); none is made by editing the frozen document in place:

- PATCH: Typographical corrections, broken cross-reference corrections, clarification of ambiguous normative language without behavioral change.
- MINOR: Addition of new Normative Requirements, Validation Rules, or Quality Gates.
- MAJOR: Any removal or change to existing Normative Requirements, Validation Rules, or Quality Gates.

No change, regardless of magnitude, may be made to a frozen document by direct edit. The frozen version is immutable. All changes produce a new version.

### 10.3 How supersession works

See §4.4 (Supersession) for the complete supersession process. Key properties:

- Superseded versions are never deleted.
- The transition period is a minimum of 6 months.
- During the transition period, governed documents compliant with either version are accepted.
- Governed documents revised after the transition period MUST comply with the new MAJOR version.
- A governed document that has not been revised is grandfathered per §4.6 indefinitely.

### 10.4 Relationship between Technical Standard freeze and governed document freeze

A governed document may not be frozen under a Technical Standard that is itself not frozen. A Draft or Under Review Technical Standard does not carry enough governance authority to authorize a document freeze.

Exception: When a new package is being developed in parallel with the first version of its parent Technical Standard, the package document may proceed to implementation under a Release Candidate version of the Technical Standard (designated `1.0.0-rc.N`). The document is not frozen until the Technical Standard is frozen.

## 11. Amendment Policy for TS-001

### 11.1 What requires an amendment to TS-001

An amendment to TS-001 is required when:

- The mandatory section structure in §2.1 changes.
- A term in the Shared Terminology (§3) is added, removed, or redefined.
- The versioning rules in §4 change.
- The Extension Mechanism in §5 changes.
- The Cross-Reference Rules in §6 change.
- The Validation Framework structure in §7 changes.
- The Ownership rules in §8 change.
- The Compliance Rules in §9 change.
- The Freeze Policy in §10 changes.

### 11.2 Amendment process

1. File an RFC against TS-001. Comment period: minimum 10 business days.
2. The Chief Architect and two Principal Architects review.
3. If approved, TS-001 is updated to a new version per §4.2.
4. All Technical Standard owners are notified.
5. Technical Standards that are affected assess whether a MINOR or MAJOR update is needed per §4.2.

### 11.3 Effect on existing Technical Standards

A PATCH or MINOR amendment to TS-001 does not require Technical Standards to update immediately. Technical Standards are grandfathered at the TS-001 version current when they were frozen. They must comply with the new TS-001 version at their next MINOR or MAJOR revision.

A MAJOR amendment to TS-001 triggers the supersession process. The 6-month transition period applies to Technical Standards updating to comply with the new TS-001 MAJOR version.
