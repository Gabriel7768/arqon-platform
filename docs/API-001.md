# ARQON Platform — Public API Specification Standard
## API-001 — Version 1.0.0
**Status:** Frozen
**Owner:** Chief Architect
**Audience:** All engineers, architects, and technical leads who author, review, approve, or consume Public API Specification documents on the ARQON Platform.
**Depends on:** EDS-001 v1.0, EES-001 v1.0, EDS-002/ESS-001 v1.0.0
**Supersedes:** None

---

## 1. Purpose

API-001 defines the mandatory standard that every Public API Specification (document type `API` per EDS-001 §4.4) on the ARQON Platform must conform to. It is not an API for any specific package. It is the governing authority on how API specifications are structured, written, validated, versioned, frozen, and evolved.

EDS-001 defines what an API document owns. EDS-002/ESS-001 defines the general writing rules for all specification documents. API-001 defines the API-specific rules that are too detailed for a general standard: signature notation, parameter ownership, error contract structure, backward compatibility rules, deprecation mechanics, extension policy, and the complete validation model for API documents.

A Public API Specification that does not conform to API-001 is non-compliant regardless of its technical accuracy. Conformance to API-001 is a precondition for freezing any `API` document on the ARQON Platform.

---

## 2. Scope

API-001 governs every document of type `API` as defined by EDS-001 §4.4, across every current and future package on the ARQON Platform.

API-001 does not govern:

- The Runtime Specification (`RT`) — behavioral algorithms and execution flows are owned by `RT` documents; API-001 governs only the interface surface.
- The Data Model Specification (`DATA`) — schema definitions for persistent or transmitted data are owned by `DATA` documents; API-001 governs type definitions only as they appear in the public interface.
- Adapter Specifications (`ADAPT`), CLI Specifications (`CLI`), or SDK Specifications (`SDK`) — these may impose additional rules beyond API-001 but must not contradict it.
- Implementation code — API-001 does not constrain how a conforming implementation is written, only how its public interface is specified.

---

## 3. Definitions

**API document:** A Public API Specification document of type `API` as defined by EDS-001 §4.4.

**Authoritative definition:** The single canonical statement of a symbol's identity, type, and contract. Every exported symbol has exactly one authoritative definition in exactly one API document. See §7.

**Breaking change:** A change to an API document that can cause a previously conforming consumer to fail to compile, fail at runtime, or observe different behavior without modifying its own code. Defined exhaustively in §17.

**Calling convention:** The rules governing how a caller invokes a function or method: argument order, passing style, optionality, and any side-channel requirements (headers, context objects, ambient state).

**Consumer:** Any package, application, or team that depends on the public API of another package by importing its exported symbols.

**Exported symbol:** Any type, interface, class, function, constant, or enumeration made available to consumers outside the package boundary.

**Non-breaking change:** A change to an API document that cannot cause a previously conforming consumer to fail. Defined exhaustively in §17.

**Normative statement:** A statement using RFC 2119 modal vocabulary that creates an obligation or prohibition. See EDS-002 §5.1.

**Observable behavior:** Any effect of calling a public function or method that is detectable by a consumer: return value, thrown exception, mutation of a passed argument, emitted event, or state change visible through another public method.

**Precondition:** A condition that MUST hold when a method is called. Violation of a precondition by the caller is a programming error; the implementation's behavior is explicitly undefined unless this document states otherwise.

**Postcondition:** A condition that MUST hold when a method returns normally.

**Symbol owner:** The team or individual designated in the package's ARCH document as responsible for the API surface of a given module.

## 4. Ownership

### 4.1 Document ownership

Every API document has exactly one owner, designated in the package's ARCH document per EDS-001 §4.3. The owner is responsible for:

- Authoring and maintaining the API document.
- Approving all changes to the document.
- Signing the Specification Review sign-off (EES-001 §6.2).
- Initiating the RFC process for breaking changes (EDS-001 §7.3).
- Notifying consuming teams of changes.

Ownership transfers in writing, recorded in the ARCH document.

### 4.2 Symbol ownership

Every exported symbol in an API document has exactly one owner: the owner of the document in which it is defined. A symbol defined in two documents is a governance defect; the duplicate must be removed through the RFC process.

### 4.3 Cross-package symbol use

When Package B reexports a symbol defined in Package A's API document, Package B MUST cite Package A's API document as the authoritative definition. Package B MUST NOT restate the symbol's definition. See §21 for cross-reference rules.

---

## 5. Audience

An API document is written for two distinct audiences simultaneously. Both must be able to use the document without additional verbal communication.

**Primary audience — Implementing engineers:** Engineers building the package. They use the API document to understand what must be implemented, what signatures must be satisfied, and what error types must be raised.

**Secondary audience — Consuming engineers:** Engineers importing and using the package. They use the API document to understand what they can call, what arguments to pass, what to expect in return, and what errors to handle.

A section that serves only one audience must be labeled `[For implementors]` or `[For consumers]` to prevent confusion. The majority of an API document serves both audiences and requires no such label.

---

## 6. Lifecycle

An API document passes through the following states. Transitions are governed by EES-001 §4.6 and §6.

```
Draft → Under Review → Frozen → Superseded | Archived
```

**Draft:** Under active authorship. May be shared for early feedback but carries no implementation obligation.

**Under Review:** Complete draft submitted to the Specification Review panel (EES-001 §6.2). No implementation work begins on symbols first defined in this version until the document is Frozen.

**Frozen:** All quality gates passed; document approved by the Specification Review panel. Implementation work is authorized. The document may not be edited in place; any change requires a new version through the amendment process (§24).

**Superseded:** A new major version has been frozen. The superseded version remains accessible but is no longer the implementation target for new work.

**Archived:** The package has been archived (EES-001 §5.8). The document is retained indefinitely as historical record.

## 7. One Symbol, One Definition

This is the foundational rule of API-001. It governs every other decision in this standard.

**Rule:** Every exported symbol has exactly one authoritative definition, in exactly one API document, owned by exactly one team.

**Corollary 1:** If Symbol S appears in Package A's API document and Package B needs to reference it, Package B cites Package A's API document. Package B does not copy, restate, or paraphrase the definition. See §21.

**Corollary 2:** If a symbol must be shared across packages, it belongs in a shared library package whose sole purpose is to own that symbol. Both consuming packages cite that library's API document.

**Corollary 3:** If two API documents define a symbol with the same name, at least one of them is wrong. Resolution is through the RFC process (EDS-001 §7.3); it is never resolved by convention or by precedence.

**Violation detection:** The Specification Review panel checks for duplicate symbol definitions across all API documents in the platform as part of SG-04 (§22.4). A symbol found in two documents is a blocking defect.

## 8. Normative Language

API-001 adopts the RFC 2119 modal vocabulary as defined in EDS-002 §5.1 without modification. The following applications of that vocabulary are specific to API documents:

**For implementors:**
- MUST → The implementation must satisfy this property.
- MUST NOT → The implementation must not exhibit this behavior.
- SHOULD → The implementation is strongly recommended to satisfy this; non-conformance is permitted with documented justification in the package's IMPL document.
- MAY → The implementation may or may not exhibit this behavior.

**For consumers:**
- MUST → The consumer must satisfy this precondition.
- MUST NOT → The consumer must not perform this action.
- MAY → The consumer may perform this action; the implementation MUST handle it correctly.

When a normative statement could be read as applying to either the implementation or the consumer, it MUST explicitly name the subject: "The implementation MUST…" or "The caller MUST…".

## 10. Definitions Section (§2 of every API document)

Every API document's §2 MUST contain an alphabetically ordered definitions table for all terms used normatively in the document that are not defined by EDS-001, EES-001, or EDS-002.

**Format:**

```
## 2. Definitions

| Term | Definition |
|---|---|
| **{Term}** | {Precise definition. One or two sentences maximum. No forward references.} |
```

**Rules:**
- A term defined here is written in **bold** on its first use in each subsequent section.
- A term defined in a dependency document (EDS-001, EES-001, EDS-002, the package's RT or ARCH document) is cited rather than redefined here.
- A term must be defined before it is used normatively. If the definitions section requires a term to define another term, terms are ordered to satisfy this dependency.

## 11. Scope Section (§3 of every API document)

Every API document's §3 MUST contain:

1. **The complete list of exported symbols.** Every type, interface, class, function, and constant that this document defines is listed. This list is normative: symbols on the list are public; symbols not on the list are internal, regardless of their visibility in the source code.

2. **Explicit exclusions.** If any symbol is accessible in the source code but is not part of the public API (e.g., a type exported for technical reasons but not intended for direct consumer use), it is listed here as explicitly excluded with the reason.

3. **Dependency statement.** The ARCH module that owns these symbols is named, with a citation to the package's ARCH document.

**Format:**

```
## 3. Scope

### 3.1 Exported symbols

| Symbol | Kind | Module | Status |
|---|---|---|---|
| `{SymbolName}` | type | alias | interface | class | function | constant | enum | {module} | Active | Deprecated |

### 3.2 Explicitly excluded symbols

| Symbol | Reason for exclusion |
|---|---|

### 3.3 Module ownership
The symbols in §3.1 are owned by the `{module}/` module as defined in
{PACKAGE}-ARCH-{VERSION} §3.{N}.
```

## 12. Type Definitions

### 12.1 Required coverage

Every type listed in §3.1 MUST have a definition in §4 of the API document. A type that appears in a method signature but is not defined in §4 is a defect; it must either be added to §4 or cited from another API document.

### 12.2 Type definition format

Each type has its own subsection. The subsection title is the type name in `monospace`. The content follows this exact structure:

```
### 4.{N} `{TypeName}`

**Kind:** type alias | enum | interface | class
**Stability:** Stable | Experimental | Deprecated
**Since:** {document version in which this type was introduced}

\`\`\`typescript
{complete TypeScript-notation definition}
\`\`\`

**Field table** (required for interfaces and classes with fields):

| Field | Type | Required | Default | Mutability | Description |
|---|---|---|---|---|---|
| `{field}` | `{type}` | Yes / No | `{value or "—"}` | Readonly / Mutable | {one sentence} |

**Invariants:**
{Numbered list of constraints on the type's values not expressible in the
type system. If none: "None."}

**Relationship to other types:**
{Named relationships (extends, implements, composes). If none: "None."}
```

### 12.3 Enum definitions

Enums require an additional values table:

```
**Values:**

| Value | Numeric equivalent | Description | Since |
|---|---|---|---|
| `{VALUE}` | {N or "N/A"} | {Exact meaning.} | {version} |
```

No enum value may be added, removed, or renumbered in a MINOR or PATCH version. All enum changes are MAJOR. See §17.

### 12.4 Generic types

Generic type parameters MUST be named and constrained. An unconstrained `T` is non-compliant.

```typescript
// Compliant
interface Repository<TEntity extends Entity, TId extends string | number> { }

// Non-compliant
interface Repository<T, U> { }
```

Each type parameter MUST have a row in an additional table:

| Type parameter | Constraint | Description |
|---|---|---|
| `TEntity` | `extends Entity` | The domain entity this repository manages. |

### 12.5 Union and intersection types

Union types MUST enumerate all members explicitly. An open union (`string | {other}`) that does not enumerate all valid string values is treated as an unconstrained string type and requires a separate invariant statement listing all valid values.

## 13. Error Types

### 13.1 Error contract requirement

Every exported error type is a first-class API citizen. Error types are specified with the same rigor as any other type. An API document that lists "throws an error" without specifying the error type is non-compliant.

### 13.2 Error hierarchy section

Section §5 of every API document MUST contain the complete error type hierarchy for the package. The hierarchy is presented as a nested list and a detailed table.

```
## 5. Error Types

### 5.1 Error hierarchy

{PackageName}Error (base)
├── {Category}Error
│   ├── {SpecificError}
│   └── {SpecificError}
└── {Category}Error
    └── {SpecificError}

### 5.2 Base error type

\`\`\`typescript
interface {PackageName}Error {
  readonly code: {PackageName}ErrorCode;
  readonly message: string;
  readonly cause?: unknown;
}
\`\`\`

### 5.{N} `{SpecificErrorType}`

\`\`\`typescript
{complete definition}
\`\`\`

| Property | Type | Always present | Description |
|---|---|---|---|
| `code` | `{ErrorCode}` | Yes | Machine-readable error code. |
| `message` | `string` | Yes | Human-readable description. Suitable for logging only, not for display to end users. |
| `cause` | `unknown` | No | Underlying cause if this error wraps another error. |
| `{property}` | `{type}` | Yes/No | {description} |
```

### 13.3 Error code enumeration

Every error type that carries a `code` property MUST have a complete error code table. No error code registry may use open strings; all valid codes are enumerated:

```
**Error codes for `{ErrorType}`:**

| Code | When thrown | State after throw | Recoverable? |
|---|---|---|---|
| `{ERROR_CODE}` | {Exact condition that causes this code to be used. No vague language.} | {State of the object after this error is thrown.} | Yes / No / {condition} |
```

**Recoverable** means the object is in a defined, usable state after the error is caught. A non-recoverable error means the object MUST be discarded.

### 13.4 Error ownership

Every error type is owned by exactly one API document. If Package B catches an error from Package A and rethrows a different error, the new error type is defined in Package B's API document. The original Package A error type is cited, not redefined.

### 13.5 Prohibited error patterns

The following error patterns are prohibited in API documents:

| Prohibited pattern | Reason | Compliant replacement |
|---|---|---|
| Throwing `Error` directly | No machine-readable code | Define a typed error with a `code` property |
| Error message as the only error identifier | Messages are not contractual | Define an error code enum |
| "throws if something goes wrong" | Non-deterministic | Enumerate each condition that throws |
| Multiple conditions mapped to one code | Ambiguous for consumers | One code per distinct error condition |
| Swallowing errors silently | Unobservable failure | Specify what is logged; errors MUST be surfaced |

## 14. Constructor Signatures

### 14.1 Constructor section format

Section §6 of every API document MUST contain one subsection per exported class. The subsection title is the class name in `monospace`.

```
## 6. Constructor Signatures

### 6.{N} `{ClassName}`

\`\`\`typescript
constructor({params}): void
\`\`\`

**Parameter table:**

| # | Name | Type | Required | Default | Description |
|---|---|---|---|---|---|
| 1 | `{name}` | `{Type}` | Yes / No | `{value or "—"}` | {one sentence} |

**Construction invariants:**

| # | Invariant | Violation throws |
|---|---|---|
| 1 | {Condition that MUST hold on all arguments collectively.} | `{ErrorType}(code: {CODE})` |

**Post-construction state:**
{The exact state of the newly constructed instance, referenced by state name
from the SM document if one exists, or described in normative prose.}

**Construction failure:**
{What state is the object in if construction throws? Can it be retried?}

**Thread safety of construction:**
{Is it safe to construct multiple instances concurrently? Is it safe to call
methods on an instance before the constructor returns?}
```

### 14.2 Parameter numbering

Parameters are numbered by position starting at 1. Position numbers are normative — they are stable across MINOR and PATCH versions. Adding a parameter at a position that shifts existing parameters is a MAJOR (breaking) change.

### 14.3 Optional parameters

A parameter marked Required: No MUST have an explicit default value in the Default column. The default value is normative: the implementation MUST behave identically whether the caller passes the default explicitly or omits the parameter. "Undefined behavior when omitted" is non-compliant.

### 14.4 Variadic parameters

Variadic parameters (`...args: T[]`) are specified with the element type and the minimum and maximum number of elements:

| # | Name | Type | Min count | Max count | Description |
|---|---|---|---|---|---|
| N | `...{name}` | `{ElementType}[]` | {N} | {N or "unbounded"} | {description} |

### 14.5 Overloaded constructors

When a class has multiple constructor signatures, each overload is defined as a separate subsection numbered `6.{N}.{M}`. The overload resolution rules MUST be stated explicitly in a subsequent prose section: "When the caller passes {condition}, overload 6.{N}.1 applies. When…".

## 15. Method Signatures

### 15.1 Method section structure

Section §7 of every API document MUST contain one subsection per public method per exported class. Methods are grouped by class. Within a class, methods appear in this order:

1. Lifecycle methods: constructor (cross-referenced from §6), open/init/start, close/stop/dispose
2. Query methods (return a value without mutating state)
3. Command methods (mutate state)
4. Event registration methods (subscribe/unsubscribe/on/off)

Alphabetical ordering within each group is required. A method not in this ordering is non-compliant.

### 15.2 Method signature format

```
### 7.{N} `{ClassName}.{methodName}`

\`\`\`typescript
{methodName}({params}): {ReturnType}
\`\`\`

**Synchrony:** Synchronous | Asynchronous (Promise) | Asynchronous (callback) | Asynchronous (observable)

**Parameter table:**

| # | Name | Type | Required | Default | Mutated by callee? | Description |
|---|---|---|---|---|---|---|
| 1 | `{name}` | `{Type}` | Yes/No | `{value or "—"}` | Yes/No | {one sentence} |

**Return value:**
{Normative description of what is returned. If the return type is defined
in §4, cite the section. State what is returned in every non-error case,
including void and null/undefined returns.}

**Preconditions:**

| # | Condition | Violation throws |
|---|---|---|
| 1 | {What MUST be true when this method is called.} | `{ErrorType}(code: {CODE})` |

**Postconditions:**

| # | Condition |
|---|---|
| 1 | {What MUST be true when this method returns normally.} |

**Error contract:**

| Error type | Code | Condition | State after throw | Recoverable? |
|---|---|---|---|---|
| `{ErrorType}` | `{CODE}` | {Exact condition.} | {Object state after this error.} | Yes/No |

**Behavioral specification:**
See {PACKAGE}-RT-{VERSION} §{N.N} — `{ClassName}.{methodName}`.
[This line is required. The behavioral algorithm is owned by the RT document.]

**Idempotency:** Idempotent | Non-idempotent | Idempotent under {condition}
**Side effects:** {List observable side effects beyond the return value, or "None."}
**Thread safety:** Per class-level guarantee in {PACKAGE}-PERF-{VERSION} §7.1 | {specific exception}
```

### 15.3 The behavioral specification citation requirement

Every method in an API document MUST include a "Behavioral specification" line that cites the RT document section describing that method's execution. This line is normative: it establishes that the RT document is the authority for behavioral questions and prevents behavioral creep into the API document.

If the method is so simple that no RT entry exists (e.g., a pure getter with no side effects), the line reads: "Behavioral specification: This method is a pure accessor with no side effects. See §7.{N} return value description above for the complete specification."

### 15.4 Asynchronous methods

For methods returning `Promise<T>`:

**Resolution contract:**
```
**Resolution contract:**
| Condition | Resolves with | Rejects with |
|---|---|---|
| {Condition} | `{value or type}` | — |
| {Condition} | — | `{ErrorType}(code: {CODE})` |
```

Rejection with an untyped error (e.g., rejecting with a plain `Error` or a string) is non-compliant. Every rejection MUST use a typed error from the package's error hierarchy.

### 15.5 Callback methods (event registration)

For methods that register callbacks:

**Callback signature:**
```typescript
callback({params}): {ReturnType}
```

| # | Callback parameter | Type | Description | When provided |
|---|---|---|---|---|

**Invocation contract:**
{How many times will the callback be called? In which thread/context? Before or after the registering method returns?}

**Deregistration:**
{How is the callback deregistered? What happens to pending invocations after deregistration?}

## 16. Function Signatures, Constants, and Calling Conventions

### 16.1 Function signatures

Section §8 covers exported functions that are not methods on a class. The format is identical to §15.2 except the class name prefix is omitted from the signature and the section title.

### 16.2 Module-level functions

Functions exported at the module level MUST specify their module of origin (from the package's ARCH document):

```
**Module:** `{module-name}/` — as defined in {PACKAGE}-ARCH-{VERSION} §3.{N}.
```

### 16.3 Pure functions

A function declared pure MUST satisfy:
- Given the same arguments, it always returns the same value.
- It produces no observable side effects.
- It does not throw except under conditions that constitute programming errors (invalid arguments).

A pure function that violates any of these properties is a behavioral defect. The declaration of purity is normative: tests MUST verify these properties.

### 16.4 Constants section

Section §9 covers all exported constants.

```
## 9. Constants

| Constant | Type | Value | Description | Since |
|---|---|---|---|---|
| `{CONSTANT_NAME}` | `{type}` | `{value}` | {One sentence.} | {version} |
```

A constant whose value may change between major versions is a versioned constant and MUST carry an additional note: "This value changed from `{old}` to `{new}` in version {X.0.0}." Constants that must not change between any versions carry the note: "This value is invariant across all versions of this package."

### 16.5 Calling conventions section

Section §10 of every API document covers any cross-cutting calling conventions that apply to multiple methods or functions.

**Required subsections:**

**10.1 — Context requirements.** If any methods require an ambient context object (request context, execution context, security context), the type, source, and lifetime of that context are specified here once, not repeated on every method.

**10.2 — Null and undefined handling.** The package's policy on null and undefined as arguments and return values. One of: "This package follows strict null policy: null and undefined are never accepted as arguments unless explicitly typed as `T | null` or `T | undefined`. Passing null or undefined to a parameter not typed to accept it is a precondition violation." Or a stated alternative.

**10.3 — Argument mutation policy.** Whether the implementation may mutate arguments passed by the caller. One of: "This package follows the no-mutation policy: the implementation MUST NOT mutate any argument passed by the caller unless the parameter is explicitly marked `Mutated by callee: Yes` in the method's parameter table." Or a stated alternative.

**10.4 — Return value ownership.** Who owns returned objects. One of: "Return values are owned by the caller upon return. The implementation MUST NOT retain a reference to a returned value after the method returns." Or a stated alternative.

**10.5 — Exception vs. error return policy.** Whether errors are thrown as exceptions or returned as values. The package MUST specify exactly one policy per method category, documented here.

## 17. Versioning and Backward Compatibility

### 17.1 Semantic versioning

API documents follow semantic versioning per EDS-001 §6.6 and EES-001 §8.1. Section §11 of every API document states the current version and documents the compatibility policy.

### 17.2 Breaking changes — exhaustive definition

The following changes are MAJOR (breaking). This list is exhaustive. Any change not on this list is either non-breaking or explicitly addressed:

**Type definition changes (§4):**
- Removing an exported type
- Renaming an exported type
- Removing a field from an interface or class
- Adding a required field to an interface or class
- Changing the type of any field to an incompatible type
- Narrowing the type of any field (e.g., `string` → `"a" | "b"`)
- Changing a field from optional to required
- Changing a field from mutable to readonly
- Removing an enum value
- Adding an enum value (breaking for consumers using exhaustive switch statements; see §17.4)
- Renaming an enum value
- Changing an enum value's numeric equivalent

**Error type changes (§5):**
- Removing an exported error type
- Removing an error code
- Renaming an error code
- Changing the condition under which an error code is used
- Adding a required property to an error type

**Constructor changes (§6):**
- Adding a required parameter
- Removing a parameter
- Changing a parameter's type to an incompatible type
- Changing a parameter's position
- Removing an overload
- Changing construction invariants in a way that rejects previously valid inputs

**Method changes (§7):**
- Removing a method
- Renaming a method
- Adding a required parameter
- Removing a parameter
- Changing a parameter's type to an incompatible type
- Changing a parameter's position
- Changing the return type to an incompatible type
- Narrowing the return type
- Adding a new error to a method's error contract
- Changing idempotency from idempotent to non-idempotent
- Changing synchrony (synchronous to asynchronous or vice versa)
- Changing a method's thread safety guarantee in a way that requires callers to add synchronization

**Behavioral changes (owned by RT, surfaced here for completeness):**
- Any change to a postcondition that causes previously correct consumer code to produce incorrect results

### 17.3 Non-breaking changes — exhaustive definition

The following changes are MINOR (non-breaking). This list is exhaustive:

- Adding a new optional parameter with a stated default to a method or constructor
- Adding a new exported type
- Adding a new method to a class
- Adding a new function
- Adding a new constant
- Adding an optional field to an interface or class
- Adding a new error type (without adding it to an existing method's error contract)
- Widening a parameter type (e.g., `"a" | "b"` → `string`)
- Widening a return type (e.g., `string` → `string | null`)
- Adding a deprecation notice to any symbol
- Adding an overload to an existing constructor or method

### 17.4 Enum value addition policy

Adding an enum value is a breaking change for consumers who use exhaustive switch statements without a default case. Every API document MUST specify one of the following policies for each enum type:

- **Sealed:** No new values will be added in MINOR versions. New values constitute a MAJOR change.
- **Open:** New values MAY be added in MINOR versions. Consumers MUST handle unknown values.

The policy is stated in the enum's type definition section (§12.3).

### 17.5 Experimental symbols

A symbol may be designated Experimental in its type definition (§12.2). Experimental symbols carry these additional properties:

- Breaking changes to Experimental symbols do not increment the document MAJOR version.
- Experimental symbols MUST carry a `@experimental` annotation in their signature block.
- Experimental symbols MUST have a stabilization plan (target version for Stable promotion) or an explicit note that no stabilization is planned.
- A symbol may not remain Experimental across more than two MAJOR versions without a written decision filed in the package's ADR log.

### 17.6 Support windows

When a new MAJOR version is released:

- The previous MAJOR version enters a support window.
- The minimum support window for any package with production consumers is 6 months from the date the new MAJOR version reaches Frozen status.
- During the support window, the previous MAJOR version receives security patches and critical bug fixes only; no new features.
- The support window end date is stated in the new MAJOR version's §11 and in the release notes.

## 18. Deprecation

### 18.1 Deprecation is a contract

Deprecation is a binding commitment. When a symbol is deprecated, the deprecation notice, migration path, and removal version are stated at the time of deprecation and MUST NOT be changed to an earlier removal version after announcement.

### 18.2 Deprecation register

Section §12 of every API document is the Deprecation Register. It is a complete, ordered table of all symbols that are currently deprecated or were deprecated in a prior version of this document.

```
## 12. Deprecation Register

| Symbol | Kind | Deprecated since | Removal version | Migration path |
|---|---|---|---|---|
| `{Symbol}` | {type/method/function/constant/enum value} | {version} | {version or "unscheduled"} | {What the consumer MUST do instead. Cite the replacement symbol.} |
```

### 18.3 Deprecation process

1. The symbol's definition in §4, §5, §6, §7, §8, or §9 is annotated with `@deprecated since {version} — see {DOCUMENT-ID} §12 for migration path.`
2. The Deprecation Register (§12) is updated with a complete row.
3. The change is a MINOR version increment (adding a deprecation notice is non-breaking).
4. Consuming teams are notified as per EES-001 §7.6.

### 18.4 Removal process

Removal of a deprecated symbol is a MAJOR version increment. The removal requires:

1. The symbol's row in the Deprecation Register is updated: the symbol's definition sections (§4–§9) have the entry removed.
2. The deprecation register row is moved to an appendix titled "Removed Symbols — Historical Record."
3. The MIG document for this MAJOR version documents the removal.

The removal version MUST NOT be earlier than the announced removal version. If the implementation team discovers that removal must be deferred, the removal version in the Deprecation Register is updated to a later version — never to an earlier one.

### 18.5 Minimum deprecation periods

| Consumer scope | Minimum period |
|---|---|
| Platform-wide use (consumed by 3 or more packages) | 12 months |
| Domain-wide use (consumed by 2 packages in same domain) | 6 months |
| Single consumer | 3 months |
| Experimental symbols | 1 month or one MAJOR version, whichever is shorter |

## 19. Extension Points

### 19.1 Extension point definition

An extension point is an interface or abstract class that the package defines but that consumers are expected to implement. Extension points are first-class API citizens and are specified with full rigor.

### 19.2 Extension point format

Extension points appear in §4 (Type Definitions) and are additionally listed in Section §13 of the API document with augmented information:

```
## 13. Extension Points

### 13.{N} `{InterfaceName}` — Extension Point

**Purpose:** {One sentence. What capability does implementing this interface provide?}
**Stability:** Stable | Experimental
**Implementation contract:** {What invariants MUST every implementation satisfy?
This is the specification for implementors of the extension point.}
**Lifecycle managed by:** The host package | The implementor
**Threading contract:** {Under which threading conditions will the implementation be called?
Is the implementation guaranteed to be called from a specific thread? Is it called concurrently?}
**Resource contract:** {Who allocates resources? Who releases them?}

**Required method implementations:**

| Method | Purpose | Invariants for implementors |
|---|---|---|
| `{methodName}` | {one sentence} | {What a correct implementation MUST guarantee.} |

**Implementation validation:**
{Does the host package validate implementations at construction time?
What validation is performed? What error is thrown for a non-conforming implementation?}
```

### 19.3 Extension point stability

Adding a method to an extension point interface is always a MAJOR (breaking) change, because every existing implementation immediately fails to compile. Extension point interfaces are therefore held to a higher stability bar:

- A new method MUST NOT be added to a Stable extension point interface without a MAJOR version increment and an RFC.
- Extension point interfaces that are expected to grow MUST use an abstract base class with default implementations, or provide a separate versioned interface per cohort of methods.

## 20. Examples Policy

### 20.1 Examples are informative

Every example in an API document is informative. A compliant consumer implementation is determined by the normative sections, not by examples. In the event of conflict between an example and the normative specification, the normative specification governs, and the example is treated as a documentation defect to be corrected in the next patch version.

### 20.2 Example placement

Examples MUST follow the normative content they illustrate. An example placed before its normative statement is non-compliant. Examples MUST use the labeling format from EDS-002 §4.8:

```
[Example — {description}]
{content}
[End Example]
```

### 20.3 Example correctness

Every example in a Frozen document MUST be correct at the time of freezing. An example that demonstrates a call that would throw at runtime is non-compliant unless the example is explicitly labeled as a negative example: `[Example — incorrect usage; produces {ErrorType}]`.

### 20.4 Example scope

Examples in an API document are limited to demonstrating the public interface. They MUST NOT demonstrate internal implementation details, use non-exported symbols, or show output that depends on behavioral algorithms (the RT document owns behavioral examples).

### 20.5 Code-only examples

Examples that consist entirely of code are permitted without prose explanation. However, a code-only example for a complex operation is strongly discouraged — a brief prose sentence preceding the example block that explains what the example demonstrates increases document quality.

## 21. Prohibited Content

The following content is explicitly prohibited in API documents. Its presence is a blocking defect at Specification Review.

| Prohibited content | Reason | Correct location |
|---|---|---|
| Algorithm descriptions (how a method works internally) | RT document owns algorithms | {PACKAGE}-RT |
| Sequence diagrams | RT document owns execution flows | {PACKAGE}-RT |
| Concurrency guarantees beyond method-level thread safety | PERF document owns concurrency | {PACKAGE}-PERF |
| Cache TTL, invalidation rules, or caching behavior | RT document owns caching | {PACKAGE}-RT |
| Lifecycle rules beyond construction and disposal preconditions | RT document owns lifecycle | {PACKAGE}-RT |
| Deployment configuration (environment variables, infrastructure) | DEPLOY document owns deployment | {PACKAGE}-DEPLOY |
| Metric names, log event names, or trace span names | OBS document owns observability | {PACKAGE}-OBS |
| Performance benchmarks or SLOs | PERF document owns SLOs | {PACKAGE}-PERF |
| Test cases or mock contracts | TEST document owns tests | {PACKAGE}-TEST |
| Security threat models or mitigations | SEC document owns security | {PACKAGE}-SEC |
| Migration instructions | MIG document owns migration | {PACKAGE}-MIG |
| Rationale for architectural decisions | ADR owns decisions | ADR-{NNN} |
| Implementation notes or optimization hints | IMPL owns implementation notes | IMPL |
| Future plans, planned extensions, or roadmap items | RFCs own proposals | RFC-{PACKAGE}-{NNN} |
| "TBD", "TODO", "to be determined", "to be specified" | Documents containing these strings may not be frozen | N/A |
| Restatement of content defined in a dependency document | Cross-document duplication | Cite via §21 cross-reference rules |
| Prose descriptions of type shapes in lieu of typed signatures | Ambiguous and non-deterministic | TypeScript-notation signature per §12 |

## 22. Cross-Reference Rules

### 22.1 Citation format

Every reference to content in another document uses the pinned citation format defined in EDS-002 §22.1:

> See {DOCUMENT-ID} §{N.N} — {section title}.

The document ID MUST include the full version number. Example:

> See I18N-RT-2.1.0 §4.3 — `Registry.load` behaviors.

### 22.2 Intra-document references

References within the same API document use the section symbol without a document ID:

> See §7.{N} for the method signature.

Intra-document references do not carry version numbers.

### 22.3 Behavioral specification citations

Every method signature section (§15) MUST contain a behavioral specification citation to the RT document. This citation is the bridge between the API document and the RT document. It is non-optional and its absence is detected by validation checklist item API-02 (§23.3).

### 22.4 Error type citations

When an API document lists errors that are defined in the RT document (because the RT document specifies when they occur), the error type definition is in the API document, and the error-triggering condition is cited in the RT document. The two documents are consistent: the API document owns the type; the RT document owns the trigger condition for each method.

### 22.5 Prohibited reference patterns

| Prohibited pattern | Reason |
|---|---|
| Citing an unfrozen document as a dependency | Unfrozen documents are not stable contracts |
| Citing a document without a version number | Version-free references are floating and non-deterministic |
| Citing a section that does not exist in the referenced version | Broken reference |
| Summarizing or paraphrasing cited content | Duplication violates EDS-001 §6.3 |
| Citing a Tier 4 document (MIG, RUN, DEV, IMPL) as authoritative | Tier 4 documents are not contractual |

## 24. Completeness Scoring

API documents are scored using the EDS-002 §20 five-dimension model. The API-specific scoring criteria are:

**Dimension 1 — Structural completeness (0–20):**
- 20: All 15 mandatory sections present; all sections have substantive content; §3.1 symbol table is complete.
- 15: One non-critical section is thin (e.g., §13 Extension Points is "None" when there are extension points).
- 10: One critical section is missing or empty (§5 Error Types, §7 Method Signatures).
- 5: Two or more sections are missing.
- 0: Template was not followed.

**Dimension 2 — Normative precision (0–20):**
- 20: All signatures are fully typed; all tables are complete; no forbidden language in normative sections.
- 15: 1–2 parameters missing types or defaults.
- 10: A method's error contract is missing or has "N/A" rows.
- 5: Multiple methods have incomplete contracts; generic types have unconstrained parameters.
- 0: Signatures are prose descriptions with no TypeScript notation.

**Dimension 3 — Error path coverage (0–20):**
- 20: Every method has an error contract; every error code has a triggering condition and recoverability.
- 15: One method has an incomplete error contract.
- 10: Multiple methods have incomplete error contracts, or error codes map multiple conditions.
- 5: Error types are named but conditions are vague ("throws if something goes wrong").
- 0: No error contracts.

**Dimension 4 — Cross-reference integrity (0–20):**
- 20: All RT citations present; all citations pinned to frozen versions; no content duplication.
- 15: 1–2 missing RT citations.
- 10: Multiple missing RT citations, or one instance of restated RT content.
- 5: RT citations systematically absent; behavioral descriptions embedded in API document.
- 0: No RT citations; behavioral algorithms described in API document throughout.

**Dimension 5 — Audience appropriateness (0–20):**
- 20: Implementor-facing and consumer-facing content is clearly scoped; no prohibited content.
- 15: Minor off-type content (one paragraph from RT scope).
- 10: A section describes algorithm behavior that belongs in RT.
- 5: The document functions as a combined API+RT document.
- 0: The document is a code walkthrough or tutorial rather than a specification.

**Scoring thresholds per EDS-002 §20.2:**
- 95–100: Eligible for freezing.
- 85–94: Accepted with tracked deficiencies.
- 70–84: Returned for revision.
- 0–69: Rejected; full rewrite required.

## 26. Freeze Criteria

An API document MAY be frozen only when all of the following hold:

1. All 10 Quality Gates (§25, AG-01 through AG-10) pass.
2. The completeness score is ≥ 85.
3. The document contains no "TBD", "TODO", "to be specified", or placeholder strings in any section.
4. Every cross-reference in the document resolves to a frozen document at the stated version.
5. The corresponding ARCH document is frozen and contains the module cited in §3.3.
6. The Status header reads "Under Review" and the Specification Review panel has approved.
7. For a MAJOR version: the RFC has been closed as Accepted, and the ADR (if required) has been filed as Accepted.
8. The Change History table contains an entry for the version being frozen.
9. The Package Owner has signed the validation checklist.
10. All symbols introduced in this version have a corresponding entry in the RT document (which need not be frozen simultaneously, but must be in a committed draft).

**Post-freeze immutability:** A frozen API document MUST NOT be modified in place. Any change — from a typographical correction to a method addition — requires a new version, a new review, and a new freeze.

## 27. Amendment Policy for API-001

### 27.1 What requires an amendment to API-001

An amendment to this document (API-001) is required when:

- A new mandatory section is added or removed from §9.
- A new item is added to the validation checklist (§23).
- A new quality gate is added to or removed from §25.
- A change is made to the breaking/non-breaking change classification in §17.
- A new required table column is added to the signature format in §14 or §15.
- The error contract specification rules in §13 change.

### 27.2 Amendment process

1. File an RFC against API-001 with a minimum 5 business day comment period.
2. Chief Architect reviews and approves.
3. API-001 is updated to a new version per §17.1.
4. The grandfathering rule applies: existing frozen API documents are compliant with the version of API-001 current when they were frozen. Revision of an existing API document requires compliance with the current API-001 version.
