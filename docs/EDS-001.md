# ARQON Platform — Engineering Documentation Standard
## EDS-001 — Version 1.0
**Status:** Active — Effective immediately upon ratification.
**Owner:** Chief Architect
**Audience:** All engineering teams, technical leads, architects, and maintainers across all ARQON platform packages.

---

## 1. Purpose and Scope

This standard defines the authoritative documentation model for every package published under the ARQON Platform. It applies without exception to all packages — current and future — including but not limited to: `i18n`, `auth`, `billing`, `rbac`, `workflow`, `notifications`, `storage`, `search`, `ai`, `event-bus`, `audit`, `integrations`, and all SDKs.

EDS-001 governs:

- What document types exist
- What each document type owns exclusively
- How documents reference each other
- How documents version and evolve
- What triggers each document tier's change process
- What governance is required for each class of change

EDS-001 does not govern implementation choices, code style, testing frameworks, or tooling selection beyond their documentation obligations.

---

## 2. Foundational Principles

**P1 — Single Source of Truth.** Every engineering fact has exactly one authoritative home. If a fact appears in two documents, one of them is wrong by definition.

**P2 — No Duplication Allowed.** Documents reference each other by citation; they never copy content. A summary of another document's content in a downstream document is a violation of P2, not a convenience.

**P3 — Deterministic Implementation.** The combination of an Architecture Specification, Public API Specification, and Runtime Specification for a given package must be sufficient to produce two independently identical implementations without any verbal communication between the two teams.

**P4 — Strict Ownership.** Every engineering topic in §5 belongs to exactly one document type. No exception process exists for P4. Disputes about topic ownership are resolved by the Chief Architect with a written ruling that amends §5.

**P5 — Independent Versioning.** Each document versions independently. A breaking change to the Public API Specification does not require a new version of the Architecture Specification unless the architecture itself changed.

**P6 — Freeze Is Binding.** A frozen document may not be edited. It may be superseded by a new major version. "Clarifying" a frozen document by annotation or errata is forbidden; the correct process is a patch version or a supersession.

**P7 — Breaking Changes Require Prior Art.** No breaking change may be introduced to any Tier 1 or Tier 2 document without an RFC at or above the required threshold (§8).

---

## 3. Documentation Taxonomy

Documents are organized into four tiers. Tier 1 is the most stable; Tier 4 is the most volatile.

```
Tier 1 — Governance
  EDS    Engineering Documentation Standard
  ADR    Architecture Decision Record

Tier 2 — Package Specifications (one set per package)
  ARCH   Architecture Specification
  API    Public API Specification
  RT     Runtime Specification
  SEC    Security Specification
  PERF   Performance & Concurrency Specification
  DATA   Data Model Specification
  SM     State Machine Specification

Tier 3 — Integration & Operational Specifications (per package, as needed)
  ADAPT  Adapter Specification
  PROTO  Protocol Specification
  CLI    CLI Specification
  SDK    SDK Specification
  OBS    Observability Specification
  DEPLOY Deployment Specification
  TEST   Testing Specification

Tier 4 — Living Documents (per package, continuously updated)
  MIG    Migration Guide
  RUN    Operational Runbook
  DEV    Developer Guide
  IMPL   Implementation Notes
  RFC    Request for Comments
```

## 4. Document Type Definitions

Each entry below specifies: purpose, audience, owner, lifecycle, versioning strategy, freeze policy, update frequency, dependencies, allowed contents, and forbidden contents.

---

### 4.1 EDS — Engineering Documentation Standard

**Purpose:** Defines the documentation model itself — this document. All other document types derive their authority from EDS-001.

**Audience:** All engineers, architects, technical leads, documentation reviewers.

**Owner:** Chief Architect.

**Lifecycle:** Created once. Superseded by a new major version when the documentation model itself changes structurally.

**Versioning:** Semantic. Major version increments on structural change to the taxonomy, ownership table, or governance rules. Minor version increments on new document type definitions. Patch version increments on ambiguity resolutions within existing rules.

**Freeze policy:** Each published version is frozen. Corrections produce a patch version, not an annotation.

**Update frequency:** Rare. Structural changes to the documentation model are architectural events.

**Dependencies:** None. EDS is the root of the dependency graph.

**Allowed contents:** Document type definitions, ownership table, cross-document rules, governance rules, taxonomy.

**Forbidden contents:** Package-specific content of any kind, implementation notes, code examples, operational procedures.

---

### 4.2 ADR — Architecture Decision Record

**Purpose:** Records a single architectural decision: the context, the options considered, the decision made, and the consequences. ADRs are the changelog of the architecture.

**Audience:** Architects, senior engineers, future maintainers reading history.

**Owner:** The architect who made the decision. Transferred to successor on role change.

**Lifecycle:** Proposed → Accepted → Superseded or Deprecated. An ADR is never deleted.

**Versioning:** ADRs are numbered sequentially within a package (`ADR-001`, `ADR-002`, …). A superseding ADR references its predecessor by number.

**Freeze policy:** An Accepted ADR is frozen. Its content may never be edited. If the decision changes, the existing ADR is marked Superseded and a new ADR is created.

**Update frequency:** Created when a qualifying architectural decision is made (§8.1). Not updated after acceptance.

**Dependencies:** May reference prior ADRs by number. May not reference Tier 2–4 documents.

**Allowed contents:** Decision context, options considered, decision made, consequences, supersession chain.

**Forbidden contents:** Implementation instructions, API signatures, algorithm descriptions, code, operational procedures. An ADR states *what* was decided and *why* — never *how*.

---

### 4.3 ARCH — Architecture Specification

**Purpose:** Defines the module boundaries, internal structure, dependency graph, and ownership philosophy of a single package. It is the structural contract that all downstream Tier 2 specifications must respect.

**Audience:** Architects, senior engineers, implementation leads for the package.

**Owner:** The package's lead architect.

**Lifecycle:** Created when a package's architecture is settled. Versioned on structural change. Supersedes prior version when module boundaries or dependency rules change.

**Versioning:** `{PACKAGE}-ARCH-{MAJOR}.{MINOR}.{PATCH}`. Major on boundary restructure. Minor on new module addition. Patch on ambiguity resolution.

**Freeze policy:** Each version is frozen. A frozen ARCH may be superseded. It may not be annotated.

**Update frequency:** Low. Structural changes to a package are architectural events governed by §8.

**Dependencies:** References the governing ADR(s) by number. No other dependencies.

**Allowed contents:** Module/folder structure (names and boundaries only), dependency rules between modules (allowed/forbidden), ownership assignments, module purpose statements (one sentence per module), references to governing ADRs.

**Forbidden contents:** Constructor signatures, method signatures, type definitions, algorithm descriptions, sequence diagrams, runtime behavior, operational procedures, code examples. If it describes *how* something works rather than *what exists and what owns what*, it does not belong here.

---

### 4.4 API — Public API Specification

**Purpose:** Defines every public symbol that a consuming package or application may depend on: constructors, method signatures, type definitions, constants, error types, and the calling conventions for each. This document is the implementation contract for the public surface of the package.

**Audience:** Implementing engineers, consuming team engineers, SDK authors.

**Owner:** The package's API owner (designated in the package's ARCH).

**Lifecycle:** Created after ARCH is frozen. Each version represents a stable public API contract. Breaking changes increment the major version and require an RFC.

**Versioning:** `{PACKAGE}-API-{MAJOR}.{MINOR}.{PATCH}`. Major on any breaking change (removed symbol, changed signature, changed semantics). Minor on additive change (new optional parameter, new exported symbol). Patch on non-behavioral clarification.

**Freeze policy:** Each version is frozen when it enters production use. A version may not be edited after first consumer release.

**Update frequency:** Low to medium. Driven by product feature requirements.

**Dependencies:** Must be consistent with the package's current ARCH. May reference RT by section citation for behavioral semantics it does not define itself. May not duplicate RT content.

**Allowed contents:** Constructor signatures with all parameter types and optionality, method signatures with all parameter types and return types, type and interface definitions, enum definitions and values, error type hierarchy and codes, constants, calling conventions (parameter order, nullability, overload resolution), deprecation notices with replacement.

**Forbidden contents:** Algorithms, sequence diagrams, runtime execution flows, performance guarantees, concurrency guarantees, caching rules, adapter-specific behavior, framework integration instructions, code examples longer than a single invocation demonstrating a signature. A signature with a one-line call example is permitted; a tutorial is not.

---

### 4.5 RT — Runtime Specification

**Purpose:** Defines every observable runtime behavior that is not captured by a type signature: execution flows, algorithm descriptions, state transitions (by reference to SM), concurrency guarantees, caching rules, lifecycle rules, error propagation rules, and memory ownership.

**Audience:** Implementing engineers. This is the document an engineer reads to know exactly how to implement a method whose signature is specified in API.

**Owner:** The package's runtime behavior owner (may be the same person as API owner; designated in ARCH).

**Lifecycle:** Created in parallel with or immediately after API. Versioned independently. Breaking changes increment the major version.

**Versioning:** `{PACKAGE}-RT-{MAJOR}.{MINOR}.{PATCH}`. Major on change to any observable behavior. Minor on description of previously-unspecified edge case. Patch on ambiguity resolution without behavioral change.

**Freeze policy:** Each version is frozen when the corresponding API version enters production use.

**Update frequency:** Low to medium. Changes in lock-step with behavioral changes.

**Dependencies:** Must be consistent with API. May reference SM by section citation. May not duplicate API content. May not duplicate SM content.

**Allowed contents:** Execution flows (prose and sequence diagrams), algorithm descriptions, concurrency model (thread safety, lock acquisition order, atomicity guarantees), caching rules (what is cached, for how long, invalidation triggers), lifecycle rules (initialization order, teardown order), error propagation (which errors are swallowed, rethrown, or transformed), memory ownership (who allocates, who frees, sharing rules), in-flight deduplication behavior.

**Forbidden contents:** Type definitions, constructor signatures, module structure, deployment procedures, configuration values, code examples. If it is a type definition, it belongs in API. If it is a procedure, it belongs in a Tier 3 or Tier 4 document.

---

### 4.6 SEC — Security Specification

**Purpose:** Defines the security contracts of the package: authentication requirements, authorization model, secrets handling, trust boundaries, and known threat mitigations.

**Audience:** Security engineers, implementing engineers, auditors.

**Owner:** The package's security owner (may differ from API and RT owners; designated in ARCH).

**Lifecycle:** Created when the package handles any sensitive data, authentication, authorization, secrets, or untrusted input. Must be created before production deployment.

**Versioning:** `{PACKAGE}-SEC-{MAJOR}.{MINOR}.{PATCH}`. Major on change to trust boundary or authentication model. Minor on addition of new threat mitigation.

**Freeze policy:** Frozen per version. Superseded on major version increment.

**Update frequency:** Low. Driven by security review findings or threat model changes.

**Dependencies:** May reference API and RT by section citation. May reference external standards (e.g., OWASP) by URL.

**Allowed contents:** Trust boundaries, authentication requirements, authorization model, secrets handling rules, threat mitigations, known limitations, audit requirements.

**Forbidden contents:** Type definitions, algorithm implementations, operational runbook content.

---

### 4.7 PERF — Performance & Concurrency Specification

**Purpose:** Defines performance guarantees, latency budgets, throughput targets, concurrency models, and thread safety contracts.

**Audience:** Implementing engineers, SREs, performance engineers.

**Owner:** The package's performance owner (designated in ARCH).

**Lifecycle:** Created when the package has measurable performance obligations or a non-trivial concurrency model.

**Versioning:** `{PACKAGE}-PERF-{MAJOR}.{MINOR}.{PATCH}`. Major on change to a stated guarantee. Minor on addition of a new guarantee.

**Freeze policy:** Frozen per version.

**Update frequency:** Low. Driven by SLA changes or architecture restructuring.

**Dependencies:** May reference RT by section citation for behavioral context. May not duplicate RT content.

**Allowed contents:** Latency SLOs, throughput SLOs, memory budgets, CPU budgets, thread safety guarantees, lock-free guarantees, benchmark conditions, measurement methodology.

**Forbidden contents:** Algorithm implementations, type definitions, deployment procedures.

---

### 4.8 DATA — Data Model Specification

**Purpose:** Defines the authoritative data schema for the package: entities, fields, types, constraints, relationships, and evolution rules.

**Audience:** Implementing engineers, data engineers, migration authors.

**Owner:** The package's data owner (designated in ARCH).

**Lifecycle:** Created when the package owns persistent or transmitted data structures. Versioned on schema change.

**Versioning:** `{PACKAGE}-DATA-{MAJOR}.{MINOR}.{PATCH}`. Major on breaking schema change (field removal, type change, constraint tightening). Minor on additive change. Patch on constraint clarification.

**Freeze policy:** Frozen per version. Superseded on major version increment.

**Update frequency:** Medium. Driven by product data requirements.

**Dependencies:** May reference API for type names. May not duplicate API type definitions.

**Allowed contents:** Entity definitions, field names and types, nullability, constraints (uniqueness, foreign keys, enumerations), relationship cardinalities, index definitions, schema evolution rules, deprecation timeline for fields.

**Forbidden contents:** Business logic, API signatures, runtime behavior, query implementations.

---

### 4.9 SM — State Machine Specification

**Purpose:** Defines the complete state machine for any entity or component with a non-trivial lifecycle: states, transitions, guards, entry and exit actions, and terminal states.

**Audience:** Implementing engineers.

**Owner:** The package's runtime behavior owner (same as RT owner; designated in ARCH).

**Lifecycle:** Created when a package contains a state machine with more than two states and at least one conditional transition.

**Versioning:** `{PACKAGE}-SM-{MAJOR}.{MINOR}.{PATCH}`. Major on removal of state or transition. Minor on addition of state or transition. Patch on guard clarification.

**Freeze policy:** Frozen per version.

**Update frequency:** Low to medium.

**Dependencies:** Referenced by RT. Must be consistent with API error types.

**Allowed contents:** State enumeration, transition table (from-state, event, guard, to-state, action), entry and exit actions per state, terminal states, error states.

**Forbidden contents:** Algorithm implementations, type definitions, performance guarantees.

---

### 4.10 ADAPT — Adapter Specification

**Purpose:** Defines the behavioral contract for a specific adapter or integration point (e.g., `HttpLoader`, `MemoryCache`, a specific storage backend). One document per adapter family.

**Audience:** Adapter implementing engineers and consuming teams.

**Owner:** The adapter's owner (designated in ARCH).

**Lifecycle:** Created when an adapter contract needs to be independently versioned from the core package API.

**Versioning:** `{PACKAGE}-ADAPT-{ADAPTERNAME}-{MAJOR}.{MINOR}.{PATCH}`.

**Freeze policy:** Frozen per version.

**Dependencies:** References API and RT by section citation. Must be consistent with both.

**Allowed contents:** Adapter-specific constructor parameters, configuration schema, behavior under failure conditions specific to the adapter, adapter-specific error codes, compatibility matrix.

**Forbidden contents:** Core API signatures already in API, core runtime behavior already in RT.

---

### 4.11 PROTO — Protocol Specification

**Purpose:** Defines the wire format, message schema, encoding, framing, versioning, and compatibility rules for any protocol the package implements or exposes.

**Audience:** Integration engineers, SDK authors, external implementors.

**Owner:** Designated in ARCH.

**Lifecycle:** Created when the package owns a wire protocol or message format consumed externally.

**Versioning:** `{PACKAGE}-PROTO-{MAJOR}.{MINOR}.{PATCH}`.

**Allowed contents:** Message schemas, encoding specifications, framing rules, version negotiation, backwards-compatibility guarantees, error response formats.

**Forbidden contents:** Internal data model (belongs in DATA), API signatures (belongs in API).

---

### 4.12 CLI — CLI Specification

**Purpose:** Defines every CLI command, flag, argument, output format, exit code, and environment variable consumed by the package's command-line interface.

**Audience:** Engineers using the CLI, documentation authors.

**Owner:** Designated in ARCH.

**Lifecycle:** Created when the package exposes a CLI surface.

**Versioning:** `{PACKAGE}-CLI-{MAJOR}.{MINOR}.{PATCH}`. Major on breaking change (removed command, changed flag semantics, changed exit code). Minor on additive change. Patch on description clarification.

**Freeze policy:** Frozen per version.

**Allowed contents:** Command names, flag names and types, argument ordering, output format (schema of stdout/stderr), exit codes and their meanings, environment variables read, stdin/stdout/stderr contracts.

**Forbidden contents:** Internal implementation, algorithm descriptions, deployment procedures.

---

### 4.13 SDK — SDK Specification

**Purpose:** Defines the public surface of any SDK layer built over the package's core API, including language-specific conventions, initialization patterns, and ergonomic wrappers.

**Audience:** SDK consuming engineers.

**Owner:** Designated in ARCH.

**Lifecycle:** Created when the package ships an SDK layer distinct from the core API.

**Versioning:** `{PACKAGE}-SDK-{LANG}-{MAJOR}.{MINOR}.{PATCH}`.

**Dependencies:** References API. Must not duplicate API content.

**Allowed contents:** SDK-specific initialization patterns, language-specific type mappings, ergonomic wrapper signatures, framework integration conventions.

**Forbidden contents:** Core API signatures already in API, runtime behavior already in RT.

---

### 4.14 OBS — Observability Specification

**Purpose:** Defines all metrics, log events, trace spans, and alerts that the package emits or must emit. This is the contract consumed by SRE and monitoring infrastructure.

**Audience:** Implementing engineers, SREs, observability platform engineers.

**Owner:** Designated in ARCH.

**Lifecycle:** Created before production deployment.

**Versioning:** `{PACKAGE}-OBS-{MAJOR}.{MINOR}.{PATCH}`. Major on removal or rename of a metric. Minor on addition.

**Freeze policy:** Frozen per version.

**Dependencies:** May reference RT for behavioral context. Must not duplicate RT.

**Allowed contents:** Metric names, types, labels, and cardinality constraints; log event names, structured fields, and severity levels; trace span names and attribute keys; alert thresholds and routing; correlation between observability events and state transitions.

**Forbidden contents:** Algorithm descriptions, deployment procedures, business logic.

---

### 4.15 DEPLOY — Deployment Specification

**Purpose:** Defines how the package is deployed: artifacts, configuration, required environment variables, feature flags, dependencies on infrastructure, and health check contracts.

**Audience:** SREs, DevOps engineers, release engineers.

**Owner:** Designated in ARCH.

**Lifecycle:** Created before production deployment.

**Versioning:** `{PACKAGE}-DEPLOY-{MAJOR}.{MINOR}.{PATCH}`.

**Freeze policy:** Frozen per version.

**Allowed contents:** Deployment artifact names, required environment variables (names only — values belong in secrets management), feature flag keys and their default values, infrastructure dependencies, health check endpoint contracts, readiness and liveness criteria, zero-downtime deployment constraints.

**Forbidden contents:** Secret values, algorithm descriptions, API signatures.

---

### 4.16 TEST — Testing Specification

**Purpose:** Defines the testing contract: what must be tested, which behaviors constitute acceptance criteria, mock contracts, and test isolation rules. Not a test implementation guide — a contract that tests must satisfy.

**Audience:** Implementing engineers, QA engineers.

**Owner:** Designated in ARCH.

**Lifecycle:** Created alongside or immediately after API and RT.

**Versioning:** `{PACKAGE}-TEST-{MAJOR}.{MINOR}.{PATCH}`. Major on removal or change of a required test case. Minor on addition.

**Freeze policy:** Frozen per version.

**Dependencies:** References API and RT by section citation for the behaviors being tested.

**Allowed contents:** Required test cases (input conditions, expected outputs, error conditions), mock contracts (what a mock must simulate and what it must not), test isolation rules (what state must be reset between tests), integration test boundary definitions.

**Forbidden contents:** Test implementation code, framework-specific instructions, tooling setup. A TEST document specifies *what* must hold; a DEV guide explains *how* to run the tests.

---

### 4.17 MIG — Migration Guide

**Purpose:** Describes how to migrate from one version of the package to another. One document per major version boundary.

**Audience:** Engineers consuming the package and upgrading.

**Owner:** The team releasing the major version.

**Lifecycle:** Created when a major version is released. Never retroactively updated for old version pairs.

**Versioning:** `{PACKAGE}-MIG-{FROM_MAJOR}-to-{TO_MAJOR}`.

**Freeze policy:** Not frozen. May be updated as issues are discovered during migration.

**Allowed contents:** Breaking changes (with reference to the API document section that changed), step-by-step migration procedure, code transformation examples (before/after), compatibility shims, deprecation timelines, known migration pitfalls.

**Forbidden contents:** Architecture rationale (belongs in ADR), API definitions (belongs in API), runtime behavior (belongs in RT).

---

### 4.18 RUN — Operational Runbook

**Purpose:** Step-by-step procedures for operating the package in production: incident response, configuration changes, scaling events, backup and restore, failover.

**Audience:** SREs, on-call engineers.

**Owner:** SRE team for the package.

**Lifecycle:** Created before production deployment. Continuously maintained.

**Versioning:** Not semantically versioned. Maintained as a living document with a changelog section.

**Freeze policy:** Not frozen.

**Allowed contents:** Named procedures with numbered steps, decision trees for incident scenarios, rollback procedures, escalation paths, safe configuration change procedures.

**Forbidden contents:** Architecture rationale, API definitions, algorithm descriptions. If a procedure requires understanding an algorithm, it cites the RT document — it does not reproduce the algorithm.

---

### 4.19 DEV — Developer Guide

**Purpose:** Explains how to set up a development environment, run tests, contribute changes, and use the package's development CLI or tooling.

**Audience:** Engineers contributing to or integrating the package.

**Owner:** The package's developer experience owner.

**Lifecycle:** Created when the package is opened for contribution. Continuously maintained.

**Versioning:** Not semantically versioned. Maintained as a living document with a changelog section.

**Freeze policy:** Not frozen.

**Allowed contents:** Environment setup, dependency installation, test execution, build commands, local development workflow, contribution process, code review standards.

**Forbidden contents:** API definitions, runtime behavior, deployment procedures. If a developer needs to understand an API to contribute, they read the API document — the DEV guide links to it and does not reproduce it.

---

### 4.20 IMPL — Implementation Notes

**Purpose:** Captures implementation decisions, optimizations, and gotchas that are specific to a concrete implementation and would be lost if the code alone were read. These are the "why we did it this way" notes that do not rise to the level of an ADR.

**Audience:** Implementing engineers maintaining the package.

**Owner:** The implementing engineer who writes it.

**Lifecycle:** Created alongside implementation. Updated when the implementation changes. Deleted when superseded or obsolete.

**Versioning:** Not semantically versioned. Free-form. Dated entries preferred.

**Freeze policy:** Not frozen.

**Allowed contents:** Implementation-specific context, chosen algorithm rationale (when the specification permitted multiple options), optimization rationale, known technical debt with root cause, links to relevant commits or issues.

**Forbidden contents:** API definitions, runtime behavior specifications. IMPL must not be the authoritative source for any observable behavior. If an IMPL entry describes something that should be specified, it must be moved to the appropriate Tier 2 document and the IMPL entry updated to cite it.

---

### 4.21 RFC — Request for Comments

**Purpose:** Proposes a change to a Tier 1 or Tier 2 document — or introduces a new architecture concept — and solicits structured engineering feedback before adoption.

**Audience:** All engineers affected by the proposed change.

**Owner:** The RFC author.

**Lifecycle:** Draft → Comment Period → Accepted or Rejected → (if accepted) triggers document update. Closed RFCs are archived, never deleted.

**Versioning:** `RFC-{PACKAGE}-{SEQUENCE}`. Sequence is per-package, starting at 001.

**Freeze policy:** Not frozen during comment period. Frozen on close (accept or reject).

**Allowed contents:** Current state, proposed change, motivation, impact analysis (which documents change and how), open questions, dissenting views.

**Forbidden contents:** Finalized API definitions, finalized type signatures. An RFC proposes; it does not specify. Accepted RFC content is migrated to the target document and the RFC is updated to reference the new document version.

## 6. Cross-Document Rules

### 6.1 Reference Model

Documents reference each other by citation. A citation takes the form:

```
See {PACKAGE}-{DOCTYPE}-{VERSION} §{SECTION}
```

Example: `See AUTH-RT-1.2 §4.3 for error propagation rules.`

A citation is not a copy. The citing document may not restate the cited content. If the citation is insufficient to understand the citing document in isolation, the solution is to restructure the boundary — not to duplicate content.

### 6.2 Reference Graph (Allowed Directions)

The reference graph is a directed acyclic graph. Lower-tier documents may reference higher-tier documents but not vice versa.

```
EDS  ← (nothing)
ADR  ← EDS
ARCH ← ADR
API  ← ARCH
RT   ← API, SM
SM   ← API
SEC  ← API, RT
PERF ← RT
DATA ← API
ADAPT ← API, RT
PROTO ← DATA
CLI  ← DEPLOY (env vars only)
SDK  ← API
OBS  ← RT, SM
DEPLOY ← (no specification documents)
TEST ← API, RT
MIG  ← API (previous version)
RUN  ← DEPLOY, OBS
DEV  ← TEST, DEV workflow only
IMPL ← RT (by citation, never duplication)
RFC  ← any (as proposal context)
```

No document may introduce a reference cycle.

### 6.3 Duplication Prohibition

If document A cites document B §3.2, document A may not restate, paraphrase, or summarize the content of B §3.2. A statement such as "As defined in B §3.2, the cache TTL is 60 seconds" is a violation. The correct form is "See B §3.2 for cache TTL rules" and nothing further.

### 6.4 Change Propagation

When a document at version N introduces a change that could affect a dependent document:

1. The author of the changed document opens an RFC against each dependent document if the change is breaking (§7.1 defines "breaking").
2. The dependent document's owner reviews the RFC and publishes a new version if needed.
3. The changed document's new version is not considered released until all dependent documents have published compatible versions or filed a formal compatibility statement.

For non-breaking changes, step 1 is replaced by a notification to dependent document owners, who determine whether a version update is needed on their own timeline.

### 6.5 Breaking Changes Defined

A change is breaking if it:

- Removes or renames any symbol, field, state, transition, metric, command, or flag already present in a released version
- Narrows a guarantee (e.g., reduces a performance SLO, adds a required parameter, removes an optional parameter's default)
- Changes the observable behavior of any method, state transition, or lifecycle event

A change is non-breaking if it:

- Adds a new optional symbol, field, state, transition, metric, command, or flag
- Widens a guarantee (e.g., improves a performance SLO, makes a required parameter optional)
- Clarifies ambiguous behavior without changing any observable outcome for a compliant implementation

### 6.6 Package Versioning Relationship

Package semantic version and document version are independent. However:

- A breaking change to API or RT must accompany a major version increment of the package.
- A minor API or RT change must accompany at least a minor version increment of the package.
- Patch document changes may accompany a patch package version.
- Document version numbers must appear in the package's changelog alongside the corresponding package version they were released with.

## 7. Governance

### 7.1 When an ADR Must Be Created

An ADR is required when a decision:

- Changes the module boundaries or dependency graph of any package
- Introduces a new package to the platform
- Selects a new external dependency that crosses a trust or security boundary
- Changes the data persistence model (storage backend, schema format)
- Changes the communication model (sync vs async, protocol selection)
- Changes the error handling philosophy (panic vs error return, checked vs unchecked exceptions)
- Deprecates or retires a package
- Establishes a platform-wide standard (including this document)

An ADR is not required for: algorithm selection within an already-specified component, implementation framework selection within an already-specified architecture, tooling changes with no API or runtime impact.

### 7.2 When an ADR Must Be Superseded

An ADR is superseded when the decision it recorded is reversed or materially replaced. A new ADR references the superseded ADR by number and states the new decision. The superseded ADR is updated only to add a `Superseded by: ADR-NNN` header. Its body is not modified.

### 7.3 When an RFC Is Required

An RFC is required before any of the following actions:

| Action | RFC threshold |
|---|---|
| Breaking change to API (major version) | Mandatory — open RFC, minimum 5 business day comment period |
| Breaking change to RT (major version) | Mandatory — open RFC, minimum 5 business day comment period |
| New package added to platform | Mandatory — open RFC, minimum 5 business day comment period |
| Breaking change to CLI (major version) | Mandatory — open RFC, minimum 3 business day comment period |
| Breaking change to PROTO | Mandatory — open RFC, minimum 5 business day comment period |
| Breaking change to DATA | Mandatory — open RFC, minimum 5 business day comment period |
| Minor change to API | Optional — owner discretion; notification to consuming teams required |
| Patch change to any document | Not required |
| New Tier 3 document created | Not required |
| Amendment to EDS | Mandatory — open RFC, minimum 10 business day comment period |

### 7.4 What Requires Architecture Review

Architecture review (by the Chief Architect or designated Architecture Review Board) is required for:

- Any new ADR
- Any RFC proposing a breaking change to API or RT
- Any RFC proposing a new package
- Any change to ARCH
- Any change to EDS
- Any change to SEC involving a trust boundary

Architecture review is not required for: Tier 3 or Tier 4 document changes, non-breaking minor changes to API or RT, changes to DEV, RUN, MIG, or IMPL.

### 7.5 What Requires Only Implementation Review

Implementation review (by the package's lead engineer or designated reviewer) is sufficient for:

- New minor version of API (additive only)
- New minor version of RT (edge case description, no behavior change)
- New version of ADAPT, CLI, SDK, OBS, DEPLOY, TEST
- All Tier 4 documents (MIG, RUN, DEV, IMPL)
- Patch versions of any Tier 2 document

### 7.6 When a Runtime Specification Changes

The RT document is updated when:

- A behavior that was previously unspecified is given a specification
- An algorithm is changed in a way observable through the public API
- A concurrency or caching rule changes
- A lifecycle order changes
- An error propagation rule changes

The RT version increment follows the breaking-change rules in §6.5.

### 7.7 When an API Specification Changes

The API document is updated when:

- A new public symbol is added
- A signature changes
- A type definition changes
- An error code is added, removed, or renamed
- A deprecation notice is added or a deprecated symbol is removed

The API version increment follows the breaking-change rules in §6.5.

Every package in the ARQON platform must maintain at minimum:

**Required (all packages):**
- ARCH
- API
- RT

**Required before production deployment:**
- SEC
- OBS
- DEPLOY

- SM — if the package contains a state machine with more than two states

**Living documents (continuously maintained):**
- MIG — on each major version boundary
- RUN — before production deployment
- DEV — before opening to contribution

## 9. Document Naming Convention

All documents follow the pattern:

```
{PACKAGE}-{DOCTYPE}[-{QUALIFIER}]-{MAJOR}.{MINOR}.{PATCH}
```

Where `{QUALIFIER}` is used only for documents that are scoped to a specific adapter, language, or version pair (e.g., `-NODE`, `-HTTP`, `-1-to-2`).

Examples:

```
I18N-ARCH-1.0.0
I18N-API-2.1.0
I18N-RT-2.1.0
I18N-ADAPT-HTTP-1.0.0
I18N-SDK-NODE-1.0.0
I18N-MIG-1-to-2
AUTH-SEC-1.0.0
AUTH-SM-1.0.0
RFC-I18N-001
ADR-007
```

EDS and ADR documents are platform-scoped and do not carry a package prefix. All others carry a package prefix.

## 10. Compliance and Enforcement

A package is non-compliant with EDS-001 if:

- It is missing any required document from §8
- Any of its documents contain content prohibited by §4
- Any of its documents duplicate content owned by another document (§6.3)
- A breaking change has been released without a completed RFC (§7.3)
- A Tier 2 document has been edited after being frozen (§2, P6)

Non-compliant packages may not be promoted to production. Non-compliance discovered in a production package triggers a remediation ADR within 30 calendar days.

Architecture Review Board conducts compliance audits at each major version boundary. Spot audits may be requested by any team or conducted by the Chief Architect at any time.
