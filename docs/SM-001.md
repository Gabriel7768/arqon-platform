## 1. Purpose

### 1.1 Definition

A **State Machine Specification** is a Tier 2 engineering document, as defined by EDS-001 §4.9, that specifies the complete lifecycle of every stateful entity in a package: the set of valid states, the events that drive transitions between them, the guards that condition those transitions, the actions performed on entry and exit, the initial state, and all terminal states. A State Machine Specification is prescriptive — it defines what must be true of any conforming implementation, not what a current implementation happens to do.

A stateful entity is any object or component whose externally observable behavior differs depending on the history of operations performed on it. If two instances constructed identically and given identical inputs produce different outputs, they are stateful. All stateful entities with more than two states and at least one conditional transition MUST have a State Machine Specification per EDS-001 §4.9.

The state machine model governed by SM-001 is a Mealy-Moore hybrid: actions may be associated with states (Moore behavior: entry/exit actions), and error types may be associated with transitions (Mealy behavior: transition outputs). Both are fully specified in every SM document.

### 1.2 Problems this standard solves

Without SM-001, two State Machine Specifications for different packages will differ in their table layouts, state naming conventions, guard expression formats, entry/exit action granularity, and treatment of error states. One engineer will name a state `LOADING`, another `IN_PROGRESS`. One will list guards as predicate expressions, another as prose. One will declare terminal states explicitly, another will leave them implicit. The result is a platform where state machines are nominally specified but structurally incomparable — impossible to audit, easy to misimplement, and fragile under change.

SM-001 eliminates this by establishing a canonical vocabulary (state naming convention, event naming convention, guard notation), a fixed table structure (state inventory table, transition table), and a validation framework that produces a deterministic conformance verdict for any SM document.

### 1.3 Relationship to other document types

**With ARCH (Architecture Specification):** The ARCH document declares which modules contain stateful entities. The SM document specifies the state machine for those entities. An SM document MUST NOT define a state machine for an entity not declared in ARCH. If the SM author identifies a stateful entity not declared in ARCH, ARCH must be updated before the SM section for that entity is written.

**With API (Public API Specification):** The API document defines the error types that transition failure actions reference (e.g., when a transition fires an error to the caller, the error type is defined in API). The SM document references those error types by name. This creates a co-authorship coordination dependency: the SM is authored before the API is frozen (because the API must reference state names in preconditions), yet the SM references API error types (because transition failures produce typed errors). The resolution of this dependency is governed by §12.8 of this document.

**With RT (Runtime Specification):** The RT document specifies what observable events trigger state transitions. When a runtime operation causes a state transition, the RT document cites the SM transition row. The SM document does not describe runtime behavior — it describes the state machine's topology. The ownership split is: SM owns "what transition fires," RT owns "when the transition fires." Every transition in the SM that is triggered by a runtime event MUST have a corresponding citation in the RT method section per RT-001 §12.4.

**With SEC (Security Specification):** Some state transitions may be restricted to callers with specific permissions (e.g., only an administrator-level caller may trigger the `CLOSE` event). When this is the case, the guard expression for the transition references a SEC trust boundary. The SM document states the guard; the SEC document defines the trust boundary it references.

**With implementation:** An implementing engineer uses the SM document to build the entity's state tracking logic. The SM is the authoritative source for all valid states, all valid transitions, and all invalid transitions (any (state, event) pair not in the transition table is explicitly forbidden). An implementation that allows a transition not in the SM, or that handles a state not in the state inventory, is non-conforming.

**With TEST (Testing Specification):** The TEST document derives required test cases from the SM document. Every transition in the SM generates at least one required test case. Every guard expression generates at least one required test case per branch. Every terminal state generates at least one required test case confirming that no further transitions are accepted.

### 1.4 Non-goals

SM-001 does not govern:

- The runtime conditions that trigger state transitions (owned by RT)
- Error type definitions and error codes (owned by API)
- The concurrency model for state transitions (owned by PERF)
- Input validation rules that appear in guards (the guard cites SEC; SEC owns the rule)
- Performance guarantees for transition execution (owned by PERF)
- Observable metric emission keyed to state transitions (owned by OBS, which cites SM)
- Package module structure (owned by ARCH)
- Adapter-specific state machine variations (owned by ADAPT documents, which cite SM)

## 2. Scope

### 2.1 Governed documents

SM-001 governs every document of type `SM` as defined in EDS-001 §4.9, across every current and future package on the ARQON Platform. This includes but is not limited to the State Machine Specifications for `packages/i18n`, `packages/auth`, `packages/workflow`, and any package containing a stateful entity with more than two states and at least one conditional transition.

### 2.2 Applicability threshold

A package MUST produce an SM document when it contains at least one entity that satisfies all of the following:
- The entity has more than two observable states.
- At least one transition between states is conditional (guarded).
- The state is observable through the package's public API surface.

A package that does not contain such an entity MUST note this in its ARCH document. It does not produce an SM document.

### 2.3 Non-governed documents

SM-001 does not govern:

- ADAPT documents that describe adapter-specific deviations from a base state machine. Those documents cite the SM they deviate from.
- Protocol state machines defined in PROTO documents for wire-protocol message sequencing. PROTO documents may reference SM-001's notation (with citation) but are not formally governed by it.

### 2.4 Content that belongs in an SM document

| Content class | Description |
|---|---|
| State inventory | Every valid state the entity can occupy, with its name, description, entry actions, exit actions, and flags |
| Transition table | Every valid (from-state, event, guard, to-state) combination with associated actions and errors |
| Guard expressions | Boolean predicates that determine which transition fires when multiple transitions share the same (from-state, event) pair |
| Initial state declaration | The state in which a newly constructed entity begins |
| Terminal state declaration | Every state from which no outbound transitions exist |
| Error state declaration | States that represent failure conditions, distinguishing recoverable from unrecoverable error states |
| State invariants | Properties that MUST hold whenever the entity is in a given state |
| Transition error types | The error types thrown to the caller when a transition is rejected, referenced from the API document |
| Event vocabulary | The complete enumeration of events the entity accepts, with their names and payload descriptions |

### 2.5 Content that does NOT belong in an SM document

| Content class | Owner |
|---|---|
| Runtime conditions that cause an event to fire | RT |
| Error type definitions and error code enumerations | API |
| Algorithm descriptions for actions | RT |
| Concurrency model for concurrent events | PERF |
| Trust boundary definitions referenced in guards | SEC |
| Named metric emissions keyed to transitions | OBS |
| Module structure | ARCH |
| Type definitions for event payloads | API |

## 3. Definitions

The following terms are used normatively in SM-001 and in all SM documents governed by it. Terms defined in TS-001 §3 are not restated here; they apply without modification. Additional terms defined here are specific to the state machine domain.

| Term | Definition |
|---|---|
| **Action** | A side effect that the entity performs as part of entering a state, exiting a state, or firing a transition. Actions are named (e.g., `ReleaseResources`, `EmitLoadedEvent`) and their semantics are specified in the RT document. An SM document names actions; it does not define their implementation. |
| **Determinism** | A state machine is deterministic if and only if for every (state, event) pair, at most one transition fires — either because at most one transition exists for that pair, or because exactly one guard evaluates to true. A non-deterministic (state, event) pair is a specification defect. |
| **Entry action** | An action that the entity performs every time it enters a given state, regardless of which transition caused the entry. Entry actions are listed in the state inventory table. |
| **Error state** | A state that represents a failure condition. An error state may be terminal (unrecoverable failure) or non-terminal (recoverable failure with a defined recovery path). |
| **Event** | An occurrence that drives a state transition. Events are named and may carry a typed payload. Events are the inputs to the state machine; they are not the same as the runtime conditions that cause them to fire (which belong in RT). |
| **Event payload** | The typed data associated with an event. Payload types are defined in the API document and referenced in the SM event vocabulary. |
| **Exit action** | An action that the entity performs every time it exits a given state, regardless of which transition caused the exit. Exit actions are listed in the state inventory table. |
| **Guard** | A boolean predicate that is evaluated when an event is received in a given state. If a guard evaluates to false, the transition does not fire. Guards do not have side effects. |
| **Initial state** | The state in which a newly constructed entity begins. Every SM document MUST declare exactly one initial state. |
| **Reachability** | A state is reachable if there exists a sequence of valid transitions from the initial state to that state. A state that is not reachable is a specification defect. |
| **Rejection** | What happens when an entity receives an event in a state for which no transition exists (or whose transitions' guards all evaluate to false). Rejection behavior is stated in the SM document's §5 (Rejection Policy). |
| **State** | A distinct condition of the entity that persists until an event triggers a transition. A state's name is a stable identifier; it is used by citation in RT and API documents. |
| **State invariant** | A predicate that MUST hold at all times while the entity is in a given state. A state invariant is checked conceptually before every event is processed and after every transition completes. A state invariant that can be violated by a transition is a specification defect. |
| **Terminal state** | A state from which no outbound transitions exist. An entity in a terminal state MUST NOT accept any event; it MUST reject all events uniformly. |
| **Transition** | A directed edge from one state to another (or to the same state, as a self-transition), triggered by an event and conditioned by a guard. |
| **Transition table** | The complete, exhaustive enumeration of all valid transitions in the state machine. Any (from-state, event) combination not in the transition table is implicitly forbidden. |
| **Unguarded transition** | A transition with no guard condition. An unguarded transition fires whenever its event is received in its from-state. If multiple transitions share the same (from-state, event) pair, at most one may be unguarded, and it represents the default branch when all guards of the other transitions evaluate to false. |

## 5. Audience

### 5.1 Primary audience — implementing engineers

Engineers who build stateful entities use the SM document to implement state tracking logic. They read SM to know every valid state, every valid transition, every guard, and every action. The SM document tells them exactly what the entity must accept, what it must reject, and what it must do on each transition. Combined with the RT document (which specifies what runtime operations trigger which events), the SM document is fully sufficient to implement the entity's state machine without any verbal communication.

### 5.2 Secondary audience — test authors

Engineers writing the TEST document and the test suite use the SM document as the source of state machine test case derivation. Every (state, event) pair in the transition table generates at least one required test case. Every guard condition generates at least one required test case per branch. Every terminal state generates at least one required test case confirming rejection.

### 5.3 Tertiary audience — RT and API document authors

The RT document author uses the SM to ensure that every runtime method that changes state cites the correct SM transition row. The API document author uses the SM to ensure that method preconditions correctly reference state names.

**Assumed knowledge:** Readers are assumed to have read the package's ARCH document before reading the SM document. The SM document does not explain module structure; it assumes the reader understands which modules contain the stateful entities it specifies.

## 6. Lifecycle

SM documents pass through the lifecycle states defined in EDS-001 §4.9 and governed by EES-001 §4.6:

```
Draft → Under Review → Frozen → Superseded | Archived
```

**Authorship dependency:** An SM document may be authored as soon as the package's ARCH document is frozen. It does not need to wait for the API document, because the SM is authored before the API (the API references state names from the SM). However, the SM document MUST NOT be formally frozen until the API document is frozen and the transition error type names in the SM have been confirmed against the API's error type hierarchy (see §12.8).

**Coordination window:** During the period between SM draft completion and API document freezing, the SM document is in a "stable draft" state: its state names, event names, and transition table structure are stable (so the API author can reference them), but its error type references remain placeholder values pending API confirmation. The SM enters formal Under Review status and is frozen in the same review cycle as the API document.

**Freeze dependency:** The SM document MUST be frozen before the RT document enters Under Review status. The RT document cites SM transition rows by reference; a non-frozen SM means those rows may change, requiring RT rework.

## 7. Normative Language

SM-001 and all governed SM documents use the RFC 2119 modal vocabulary as defined in ESS-001 §5.1 and TS-001 §3.1. The following applications are specific to state machine documentation:

**In the state inventory table:** MUST in an invariant column denotes a property that MUST hold at all times while the entity is in the stated state. Violation of a state invariant by any transition is a specification defect.

**In the transition table:** MUST in a guard column denotes a condition that must hold for the transition to fire. MUST NOT in a guard column denotes a condition that must not hold (the guard evaluates to false, blocking the transition).

**In the rejection policy:** MUST denotes the required behavior for any event received in a state where no transition exists.

**Subject specificity requirement:** Every normative statement in an SM document MUST name the entity explicitly. "The machine MUST NOT accept events" is non-compliant. "The `Registry` MUST NOT accept events in the `CLOSED` state" is compliant. Unnamed subjects are non-compliant per ESS-001 SP1.

## 8. Mandatory Sections

Every SM document MUST contain the following sections in the order defined in §9. No section may be omitted. A section that does not apply must be present and marked:

> None — this entity has no {section topic}. Rationale: {one sentence explanation}.

An omitted section without this marking is a structural defect detected at checklist item SM-S-01.

| Section # | Section title | Required content summary |
|---|---|---|
| 1 | Document Header | Per ESS-001 §4.1 and SM-001 §4 |
| 2 | Definitions | Alphabetical table of terms used normatively in this document |
| 3 | Scope | The stateful entities covered; explicit exclusions |
| 4 | Entity Overview | One subsection per stateful entity: name, module, purpose, and entity lifecycle summary |
| 5 | Event Vocabulary | Complete enumeration of all events the entity accepts, with payload type references |
| 6 | State Inventory | One row per state: name, description, entry actions, exit actions, invariants, terminal flag, initial flag |
| 7 | Transition Table | Complete transition table: from-state, event, guard, to-state, actions, error thrown |
| 8 | Guard Definitions | Formal definition of every guard predicate named in the transition table |
| 9 | Action Definitions | Name and normative summary of every action named in the state inventory and transition table |
| 10 | Initial State Declaration | Explicit declaration of the initial state and the conditions under which construction places the entity there |
| 11 | Terminal State Declaration | Explicit enumeration of all terminal states and the rejection policy |
| 12 | Error State Declaration | Explicit enumeration of all error states, their recovery classification, and their recovery paths |
| 13 | State Reachability Analysis | Proof that every non-initial state is reachable from the initial state |
| 14 | State Invariant Proofs | For each state invariant, a demonstration that no transition can violate it |
| 15 | Change History | Per ESS-001 §4.9 |

## 9. Mandatory Section Ordering

Section ordering is fixed and canonical. The rationale for the ordering is: the document progresses from definitions to the complete state machine topology, then validates the topology's correctness properties.

| Order | Section | Rationale for position |
|---|---|---|
| 1 | Document Header | Must precede all content |
| 2 | Definitions | Must precede use of defined terms |
| 3 | Scope | Must precede entity descriptions |
| 4 | Entity Overview | Establishes the entities before their machines are specified |
| 5 | Event Vocabulary | Events must be defined before they appear in the transition table |
| 6 | State Inventory | States must be defined before transitions reference them |
| 7 | Transition Table | Core topology; references states and events defined in prior sections |
| 8 | Guard Definitions | Guards are named in the transition table; definitions follow |
| 9 | Action Definitions | Actions are named in the state inventory and transition table; definitions follow |
| 10 | Initial State Declaration | References a state defined in §6 |
| 11 | Terminal State Declaration | References states defined in §6; establishes rejection policy |
| 12 | Error State Declaration | References states in §6; must follow terminal declaration to distinguish terminal errors from recoverable errors |
| 13 | State Reachability Analysis | Can only be performed after the full topology is defined (§6–§7) |
| 14 | State Invariant Proofs | Can only be performed after transitions are defined (§7) and actions defined (§9) |
| 15 | Change History | Must be final |

## 11. Notation Rules

### 11.1 State name notation

State names are written in `monospace` ALL_CAPS throughout all SM document sections and in all documents that cite them (RT, API). Examples: `READY`, `LOADING`, `CLOSED`, `FAILED`.

**Naming rules:**
- State names MUST be singular present-tense adjectives or passive-voice participles describing the entity's condition: `READY`, `LOADING`, `CLOSED`, `FAILED`, `INITIALIZING`. Not verbs (`LOADING` refers to "is loading", not the action "load").
- State names MUST be globally unique within the document. Two states MUST NOT share a name, even across different entities in the same SM document.
- State names MUST NOT use prefixes or suffixes that encode the entity type: `REGISTRY_READY` is non-compliant when the context makes the entity clear; `READY` is correct.

### 11.2 Event name notation

Event names are written in `monospace` PascalCase throughout all SM document sections. Examples: `Load`, `LoadCompleted`, `LoadFailed`, `Close`, `Reset`.

**Naming rules:**
- Events that initiate an operation are named with an imperative: `Load`, `Close`, `Reset`.
- Events that signal the completion of an asynchronous operation are named with a past participle: `LoadCompleted`, `LoadFailed`.
- Events that represent external signals use noun phrases: `ShutdownSignalReceived`.
- Event names MUST be globally unique within the document.

### 11.3 Guard notation

Guards are written as boolean predicate expressions in a uniform notation. Every guard in the transition table is:
1. Given a name (written in `monospace` `PascalCase` with a leading uppercase letter: `IsConfigured`, `HasCriticalNamespaces`)
2. Defined formally in the guard definition table (§8)
3. Named in the transition table (not inlined)

**Guard expression format in §8:**

```
Guard name:    IsConfigured
Expression:    configuration ≠ null AND configuration.baseUrl ≠ ""
References:    {PACKAGE}-SEC-{VERSION} §{N.N} (trust boundary for configuration)
Description:   True when the instance was constructed with a complete, non-empty configuration.
```

**Rules:**
- Guards MUST be side-effect-free. A guard that mutates state is a specification defect.
- Guards MUST be deterministic. A guard that can return different values for the same inputs is a specification defect.
- Guards MUST NOT reference mutable state that is not part of the entity's declared state. A guard that reads external state (e.g., current time, network availability) MUST declare that dependency explicitly with the notation `reads: {external state name}`.

### 11.4 Action notation

Actions are named in `monospace` PascalCase. Examples: `ReleaseResources`, `EmitReadyEvent`, `AbortInflightRequests`.

Actions named in the state inventory (entry/exit actions) and transition table are defined in the action definition table (§9). Each action definition names the RT section that specifies the action's implementation.

Actions in the transition table are listed as an ordered comma-separated sequence when multiple actions fire: `AbortInflightRequests, ReleaseResources, EmitFailedEvent`.

### 11.5 Transition table row format

Each row in the transition table MUST use this exact column structure:

| From state | Event | Guard | To state | Actions | Error thrown |
|---|---|---|---|---|---|
| `CURRENT_STATE` | `EventName` | `GuardName` or `—` (unconditional) | `NEXT_STATE` | `Action1, Action2` or `—` | Error type (API ref) or `—` |

**"Error thrown" column:** This column states the error type thrown to the caller when the transition fires but the operation subsequently fails (post-transition error), OR when the guard rejects the event and the implementation throws instead of silently ignoring. The error type is stated as its name and cited from the API document: `LoadError (see {PACKAGE}-API-{VERSION} §5.{N})`. During the SM authorship phase (before API is frozen), placeholder names are used with a `[PLACEHOLDER — to be confirmed against API error type hierarchy]` annotation.

### 11.6 State diagram policy

State diagrams are INFORMATIVE. They illustrate the normative transition table; they do not replace it. Every state diagram MUST be preceded by the normative transition table it illustrates. In the event of contradiction between a diagram and the transition table, the transition table governs.

Diagrams MUST be labeled:

> [Diagram — {entity name} state machine — INFORMATIVE. Normative source is §7, transition table.]

## 12. Domain-Specific Rules

### 12.1 State machine completeness rule

An SM document is complete only if the transition table covers every (state, event) pair that the implementation will encounter. A transition table that lists some events but omits others is non-compliant. The completeness obligation is:

For every state S and every event E in the event vocabulary: either
- There exists at least one row in the transition table with (from-state=S, event=E), or
- The SM document explicitly states in §11 (Terminal State Declaration) or §12.4 (Default Rejection) that event E received in state S is rejected per the default rejection policy.

### 12.2 Determinism requirement

For every (state, event) pair in the transition table, the set of guarded transitions MUST be mutually exclusive: no two guard expressions for the same (state, event) pair can both evaluate to true simultaneously. The author MUST verify this in the guard completeness justification in §8.

Additionally, if multiple transitions share a (state, event) pair, the union of all guard expressions MUST be a tautology (they cover all possible inputs). No (state, event) pair may have a gap — an input for which no guard is true and no default unguarded transition exists.

**Documentation requirement:** For every (state, event) pair with multiple guarded transitions, a guard completeness justification MUST appear in §8:

```
Guard completeness for (LOADING, LoadCompleted):
  Transitions:
    - Guard: HasSucceeded   → READY
    - Guard: HasPartialLoad → PARTIAL
    - Guard: HasFailed      → FAILED
  Mutual exclusivity: HasSucceeded, HasPartialLoad, and HasFailed are mutually exclusive
                      because they test disjoint outcome values of the load operation.
  Completeness: Every possible load outcome maps to exactly one of these three guards.
```

### 12.3 Reachability requirement

Every state declared in the state inventory MUST be reachable from the initial state via a finite sequence of valid transitions. A state with no path from the initial state is unreachable and MUST be removed from the document unless a rationale for its future use is stated. Rationale for an unreachable state is a documentation smell — the Specification Review panel MUST question it.

The reachability analysis in §13 MUST include the shortest event sequence to reach every non-initial state.

### 12.4 Terminal state exhaustiveness rule

Every state from which no outbound transitions exist MUST be declared as a terminal state in §11. The transition table implicitly defines terminal states (any state not appearing in the "from state" column). The SM author MUST verify that the set of implicitly terminal states matches the explicitly declared set in §11 exactly. Discrepancy is a specification defect.

The rejection policy for terminal states MUST be stated:
- Does the entity throw an error when it receives any event in a terminal state?
- Does it throw a specific error type (e.g., `StateError` with code `ENTITY_TERMINATED`)?
- Is the error type consistent with the error types in the API document?

### 12.5 Error state classification rule

Every error state MUST be classified as one of:
- **Terminal error state:** The entity cannot recover without disposal and reconstruction. No outbound transitions except (optionally) to a `CLOSED` or `DISPOSED` terminal state.
- **Recoverable error state:** A specific recovery path exists. The recovery path MUST be stated as one or more outbound transitions in the transition table.

An error state with no outbound transitions that is not declared as terminal is a specification defect.

### 12.6 Self-transition documentation rule

A self-transition (a transition where from-state equals to-state) MUST have explicit rationale in the transition table row's "Actions" column and an explanatory note in §9 (Action Definitions). Self-transitions are not inherently wrong — they may represent idempotent operations — but they require justification because they can obscure logic errors.

### 12.7 State invariant verification rule

For each state invariant declared in the state inventory (§6), the SM author MUST demonstrate in §14 (State Invariant Proofs) that no transition entering that state can violate the invariant. The proof has two parts:
1. **Entry proof:** Every transition whose to-state is S executes actions that establish the invariant before the transition completes.
2. **Persistence proof:** No event received while in state S can violate the invariant (because either no events are processed in S, or the guard conditions prevent invariant-violating inputs, or the invariant is only about external state not modified while in S).

An invariant without a proof in §14 is a specification defect.

### 12.8 SM/API co-authorship coordination rule

The SM document is authored before the API document is frozen, yet the SM transition table's "Error thrown" column references API error types. This creates a co-authorship coordination dependency that is resolved as follows:

**During SM authorship (Phase 3 per SPD conventions):**
The SM author records placeholder error type names in the "Error thrown" column. Every placeholder is annotated: `[PLACEHOLDER — to be confirmed against {PACKAGE}-API error type hierarchy]`.

The SM author produces an Error Type Coordination Note (a sub-section of §7) that lists every placeholder name with:
- The placeholder name used
- The semantic meaning (what kind of failure this error represents)
- A statement of the expected error hierarchy position (e.g., "this should be a subtype of `LoadError`")

**During API authorship (Phase 4 per SPD conventions):**
The API owner and the SM owner confirm the final error type names. The SM document is updated from placeholder names to final names. This update does not require a new SM review cycle — it is treated as a PATCH change to the SM draft (not yet frozen), applied atomically with the API freeze process.

**Freeze sequence:**
The SM document and the API document enter their joint Specification Review in the same cycle. Both are frozen in the same review event. Neither may be frozen independently during this coordination window.

### 12.9 Multi-entity SM documents

When a single SM document covers more than one stateful entity (e.g., both a `Registry` and a `RegistryEntry`), the following rules apply:
- The state inventories for different entities are in separate §6.{N} subsections.
- The transition tables for different entities are in separate §7.{N} subsections.
- Guard names MUST be globally unique across all entities in the document.
- Action names MUST be globally unique across all entities in the document.
- The reachability analysis (§13) covers each entity separately.
- The state invariant proofs (§14) cover each entity separately.

Cross-entity transitions (one entity's transition triggering another entity's event) MUST be documented in a Cross-Entity Interaction section appended to §7. These interactions are normative: they define the temporal coupling between entity state machines.

### 12.10 Forbidden states

The following states are explicitly forbidden by name in any ARQON Platform SM document, because they are reserved as universal platform terminology:

| Forbidden state name | Reason |
|---|---|
| `UNKNOWN` | Implies undefined behavior; states must be fully enumerated |
| `ANY` | A wildcard, not a state; use explicit enumeration |
| `DEFAULT` | Non-specific; every state must have a meaningful name |
| `PENDING` | Ambiguous; distinguish between pre-initialization pending and async-operation pending by naming the specific condition |

An SM document that uses any of these names MUST either rename the state or justify the use with a written ruling from the Chief Architect.

## 13. Versioning and Backward Compatibility

### 13.1 Semantic versioning for SM documents

SM documents follow semantic versioning per EDS-001 §6.6. The following criteria determine version type for SM-specific changes:

**MAJOR changes (breaking) in an SM document:**
- Removing a state from the state inventory
- Removing a transition from the transition table
- Renaming a state (all RT and API documents that cite the state name must be updated)
- Renaming an event
- Changing a guard expression in a way that permits previously-rejected transitions
- Adding a precondition to an existing guard (restricts previously-allowed inputs)
- Changing a terminal state to a non-terminal state or vice versa
- Changing an error state's classification from recoverable to terminal
- Removing a state invariant (weakens a guarantee)
- Making a previously synchronous event asynchronous in the transition model

**MINOR changes (non-breaking) in an SM document:**
- Adding a new state (additive — no existing behavior changes)
- Adding a new transition (additive — previously-rejected events are now accepted)
- Adding a new event to the vocabulary (additive)
- Adding a new state invariant (strengthens a guarantee)
- Adding an entry or exit action to a state
- Tightening a guard expression (further restricts an already-restricted transition — this is effectively additive from the caller's perspective if the additional restriction is from a guard evaluating false, resulting in rejection behavior the caller already had to handle)
- Adding a new error state with a recovery path

**PATCH changes in an SM document:**
- Typographical corrections
- Clarification of a guard expression without behavioral change
- Addition of an informative diagram
- Addition of an informative example
- Correction of a broken cross-reference
- Finalizing placeholder error type names (during Phase 4 coordination per §12.8)

### 13.2 RT/SM version alignment

When a new MAJOR or MINOR version of an SM document is published, the RT owner MUST assess whether an RT update is required. Specifically:
- Any state renaming triggers an RT PATCH update (to update all SM citation references).
- Any new transition triggers an RT MINOR update (to document the runtime conditions that trigger the new event).
- Any removed transition triggers an RT MAJOR update (existing RT sections that reference that transition must be revised).

The SM and RT version numbers need not be identical; they version independently per EDS-001 §P5.

## 14. Deprecation Rules

### 14.1 Applicability

The general deprecation rules from TS-001 §4.5 apply without modification. The following SM-specific rules are additive.

### 14.2 State deprecation

A state may be deprecated in a MINOR version of the SM document. Deprecation notice format:

```
[DEPRECATED since {version} — this state will be removed in version {N.0.0}.
 Migration: entities currently in this state will transition to `{REPLACEMENT_STATE}` on {event}.
 See {PACKAGE}-MIG-{N-1}-to-{N} for consumer migration guidance.]
```

A deprecated state MUST NOT be removed until both:
- All transitions that lead to that state have been removed from the transition table, and
- The minimum deprecation window defined in EES-001 §7.6 has elapsed.

### 14.3 Event deprecation

An event may be deprecated in a MINOR version. Deprecated events MUST continue to be accepted by the implementation until the removal version. The SM document MUST state what transition fires in response to the deprecated event during the deprecation window.

### 14.4 Transition deprecation

Individual transitions may be deprecated. The deprecation notice appears in the transition table row itself (in the "Actions" column as a trailing note) and in the change history. A deprecated transition MUST NOT be removed in the same version it is deprecated.

### 14.5 Guard weakening prohibition

Weakening a guard expression — allowing transitions that were previously blocked — is a MAJOR change regardless of how it is presented. It may not be introduced as a deprecation. Guard weakening requires a MAJOR version increment and a new version review.

An ADAPT document may define adapter-specific state machine variations. When it does, it MUST:
- Cite the SM section it extends.
- Define only the delta: added states, added transitions, or modified guard conditions specific to the adapter.

## 16. Examples Policy

### 16.1 All examples are informative

Examples in SM documents are informative. They illustrate normative content; they do not replace it. In any conflict between an example and a normative statement, the normative statement governs.

### 16.2 Transition scenario examples

A transition scenario example traces the state machine through a specific sequence of events. It MUST:
- State the initial state.
- List the events in sequence.
- Show which guard evaluates at each step.
- Show the resulting state after each transition.
- Show any actions fired at each transition.

Label: `[Example — {EntityName} scenario: {scenario description}]`

### 16.3 Guard evaluation examples

A guard evaluation example shows a specific input and demonstrates which guard evaluates to true. It MUST:
- State the (from-state, event) pair.
- State the input conditions.
- Trace each guard expression.
- Identify the winning transition.

Label: `[Example — guard evaluation for ({STATE}, {Event}) with {input description}]`

### 16.4 Anti-patterns

An anti-pattern in an SM document shows a state machine design that MUST NOT be used, paired with the normative rule it violates.

Label: `[Anti-pattern — {description}]`
Structure: show the forbidden design (as a prose description or table fragment), cite the normative rule it violates, show the compliant alternative.

### 16.5 Counterexamples

A counterexample shows a scenario that might appear to be a valid transition but is not. It is especially useful for clarifying the scope of guard expressions.

Label: `[Counterexample — {description}: this is NOT a valid transition]`

## 17. Prohibited Content

The following content is explicitly prohibited in SM documents. Its presence is a blocking defect at Specification Review.

| Prohibited content | Correct location |
|---|---|
| Algorithm descriptions for actions | RT document |
| Type definitions for event payloads | API document |
| Error type definitions or error code enumerations | API document |
| Quantified performance SLOs or timing guarantees | PERF document |
| Trust boundary definitions used in guards | SEC document (guards cite SEC, they do not define it) |
| Named metric or log event schemas | OBS document |
| Infrastructure dependencies or environment variables | DEPLOY document |
| Module structure or dependency rules | ARCH document |
| Adapter-specific behavioral variations | ADAPT document |
| Implementation code or pseudocode for guard evaluation | IMPL document |
| "TBD", "TODO", "to be specified", or placeholder strings (except the Phase 4 error type placeholders governed by §12.8) | N/A — blocking defect |
| Guards that reference mutable external state without declaring the dependency | Non-compliant per §12.3 of this document |
| States named with the forbidden names listed in §12.10 | Non-compliant per §12.10 of this document |
| Rationale for architectural decisions | ADR |
| Future plans or roadmap items | RFC |

|---|---|
| ARCH (this package) | For module ownership declarations |

### 18.4 Forbidden reference patterns in SM documents

| Forbidden pattern | Reason |
|---|---|

| Floating references without version numbers | Non-deterministic per EDS-002 §22.2 |

## 20. Completeness Scoring

SM documents are scored using the five-dimension model from TS-001 §7.2. The SM-specific rubric per dimension:

**Dimension 1 — Structural completeness (0–20):**
- 20: All 15 sections present in correct order; all required tables present; reachability analysis and invariant proofs complete.
- 15: One non-critical section is thin or has a placeholder note.
- 10: One critical section is missing (§6 State Inventory, §7 Transition Table, or §13 Reachability Analysis).
- 5: Two or more sections missing or empty.
- 0: Template not followed; fewer than half the required sections present.

**Dimension 2 — Normative precision (0–20):**
- 20: All state names ALL_CAPS; all event names PascalCase; all guards named in transition table and defined in §8; all actions defined in §9; no forbidden language.
- 15: 1–3 notation violations (inline guard expressions, missing action definitions).
- 10: A complete section violates notation rules systematically.
- 5: Notation is inconsistent throughout; some states unnamed.
- 0: No notation conventions followed.

**Dimension 3 — Transition completeness (0–20):**
- 20: Every (state, event) pair is either in the transition table or covered by the explicit rejection policy; guard completeness justifications present for all multi-guarded pairs.
- 15: 1–2 (state, event) pairs unaccounted for.
- 10: Multiple unaccounted pairs; or the rejection policy for terminal states is absent.
- 5: Transition table covers the happy path only; error events and rejections not specified.
- 0: Transition table present but incomplete to the point of non-usefulness.

**Dimension 4 — Cross-reference integrity (0–20):**
- 20: All error type references cite API; all guard SEC references cite SEC; all action definitions cite RT; no content duplication.
- 15: 1–3 missing citations (Phase 4 placeholders correctly annotated count as compliant).
- 10: Multiple missing citations or one instance of content duplication from API.
- 5: Systematic absence of API/SEC citations; error types defined inline.
- 0: No cross-references; SM functions as a standalone document defining its own types.

**Dimension 5 — Audience appropriateness (0–20):**
- 20: Content specifies topology only; no algorithm descriptions; no type definitions; no prohibited content.
- 15: Minor off-type content (one paragraph).
- 10: A section contains algorithm descriptions or type definitions that belong in RT or API.
- 5: The document conflates SM and RT throughout.
- 0: Document is a code walkthrough of the state machine implementation.

**Thresholds:** Per TS-001 §7.2: 95–100 eligible for freezing; 85–94 accepted with deficiencies; 70–84 returned for revision; 0–69 rejected.

## 22. Freeze Criteria

An SM document MAY be frozen only when all of the following hold:

1. All 11 Quality Gates (SMG-01 through SMG-11) pass.
2. Completeness score ≥ 85.
3. The document contains no "TBD", "TODO", "to be specified", or placeholder strings — except for Phase 4 error type coordination notes governed by §12.8, which are resolved atomically with API freeze.
4. All error type placeholder values have been confirmed with the API owner per §12.8, OR this document is being frozen in the same review event as the API document.
5. The ARCH document for this package is Frozen at the version cited.
6. All cross-references to non-placeholder documents resolve to frozen documents at the stated versions.
7. The Status header reads "Under Review" and the Specification Review panel has approved in writing.
8. For a MAJOR version: the RFC is closed as Accepted; any required ADR is filed as Accepted.
9. The Change History table contains an entry for the version being frozen.
10. The Package Owner has signed the validation checklist.
11. The API owner has co-signed per SMG-08.
12. The TEST owner has co-signed per SMG-09.

**Post-freeze immutability:** A frozen SM document MUST NOT be modified in place. Any change — including finalizing a Phase 4 error type placeholder that was not resolved before freeze — requires a new PATCH version, a new review, and a new freeze.

## 23. Amendment Policy for SM-001

### 23.1 What requires an amendment to SM-001

An amendment to this document is required when:
- The mandatory section list (§8) is changed.
- A new required table is added to §10.
- A notation rule in §11 is added, removed, or changed.
- A domain-specific rule in §12 is added, removed, or changed.
- A new item is added to the SM validation checklist (§19).
- A new quality gate is added to §21.
- The breaking/non-breaking change classification in §13 is changed.
- A new forbidden state name is added to §12.10.

### 23.2 Amendment process

1. File an RFC against SM-001 with a minimum 5 business day comment period.
2. Chief Architect and two Principal Architects review.
3. SM-001 is updated to a new version per §13.1.
4. All SM document owners are notified.
5. Grandfathering applies per TS-001 §4.6: existing frozen SM documents remain compliant with the SM-001 version under which they were frozen. Revised SM documents must comply with the current SM-001 version.
