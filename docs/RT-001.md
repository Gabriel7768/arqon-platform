## 1. Purpose

### 1.1 Definition

A **Runtime Specification** is a Tier 2 engineering document, as defined by EDS-001 §4.5, that specifies every observable runtime behavior of a package's public surface. "Observable" means detectable by a conforming consumer without access to source code: return values, thrown errors, argument mutations, emitted events, state transitions visible through other public methods, resource acquisition and release timing, and the behavior of the object under concurrent access.

A Runtime Specification is not a description of what the current implementation does. It is a prescriptive contract that any conforming implementation must satisfy. Two independent teams implementing the same package from the same frozen API and RT documents must produce implementations whose observable behavior is indistinguishable to a conforming consumer.

### 1.2 Problems this standard solves

Without RT-001, two Runtime Specifications written for different packages will differ in their section organization, their level of behavioral detail, the granularity at which concurrency is documented, the completeness of their error path coverage, and their treatment of lifecycle, caching, and retry behaviors. The result is a platform where some packages have deterministic behavioral contracts and others have partially-specified behaviors that differ across implementations.

RT-001 eliminates this variance by establishing: a canonical section structure shared by every RT document; required content for every behavioral claim; a standard vocabulary for concurrency, lifecycle, and error models; and a validation framework that produces a deterministic conformance verdict for any RT document.

### 1.3 Relationship to other document types

**With ARCH (Architecture Specification):** The ARCH document establishes the module structure that the RT document's sections are organized around. RT may not describe behavior for a module not declared in ARCH. If the RT author discovers that a behavior crosses module boundaries not declared in ARCH, the ARCH document must be updated before the RT section is written.

**With API (Public API Specification):** The API document defines every public symbol — types, signatures, error types, and calling conventions. The RT document defines the behavior behind those signatures. Every section in an RT document is keyed to one or more API symbols. The RT document must not restate type definitions or signatures from the API document; it cites them. The relationship is asymmetric: API cites RT for behavioral content; RT cites API for type content. This is a coordinated dependency, not a cycle (see EDS-002 §22.4).

**With SM (State Machine Specification):** The SM document defines the lifecycle states and transitions of stateful objects. The RT document references SM transitions when describing which state an object enters or exits as a result of a method call. RT does not restate state definitions; it cites them. For any method that causes a state transition, the RT section for that method MUST include a citation to the corresponding SM transition row.

**With SEC (Security Specification):** The SEC document defines trust boundaries, input validation rules, and threat mitigations. When an RT method behavior depends on a security validation (e.g., a method that validates a tenant identifier before loading a dictionary), the RT section cites the SEC trust boundary rather than restating the validation rule. SEC owns the validation rule; RT owns the method's execution flow.

**With PERF (Performance & Concurrency Specification):** The PERF document owns quantified SLOs and concurrency guarantees. The RT document references PERF for timeout values, retry budgets, and thread safety assertions. RT does not state "this method must complete within 50ms" — that is a PERF claim. RT states the sequence of operations; PERF states the constraint on their duration.

**With implementation:** An implementing engineer uses the RT document as the authoritative behavioral contract. Every step in every RT execution flow, every error path, and every lifecycle rule is an implementation obligation. An implementation that exhibits behavior not specified in the RT document — even if that behavior is correct, useful, or well-intentioned — is non-conforming if that behavior is observable.

**With testing:** The TEST document derives its required test cases from the RT document. Every normative postcondition in the RT document generates at least one required test case. Every error path in the RT document generates at least one required test case. The RT owner and the TEST owner collaborate to ensure that RT behavioral claims are expressed in terms that are testable.

### 1.4 Non-goals

RT-001 does not govern:

- Type definitions and signatures (owned by API)
- State enumeration and transition tables (owned by SM)
- Quantified performance SLOs (owned by PERF)
- Security threat models and mitigations (owned by SEC)
- Observable metric emission (owned by OBS)
- Adapter-specific behavior deviations (owned by ADAPT documents)
- Deployment configuration (owned by DEPLOY)
- Package module structure (owned by ARCH)

## 2. Scope

### 2.1 Governed documents

RT-001 governs every document of type `RT` as defined in EDS-001 §4.5, across every current and future package on the ARQON Platform. This includes but is not limited to the Runtime Specifications for `packages/i18n`, `packages/auth`, `packages/events`, `packages/config`, `packages/logger`, and `packages/cache`.

### 2.2 Non-governed documents

RT-001 does not govern:

- ADAPT documents, even when they contain adapter-specific behavioral deviations. ADAPT documents use RT as a foundation and cite RT sections; they are governed by ADAPT-001 (when published) or ESS-001's ADAPT template.
- The RT sections within EDS-002/ESS-001 that provide the generic RT template. ESS-001 §9 is a general template; RT-001 is the authoritative standard that supersedes the generic template for all RT documents authored after RT-001 is frozen.

### 2.3 Behaviors that belong in an RT document

The following behavior classes MUST be documented in RT documents. An RT document that omits any applicable class is incomplete.

| Behavior class | Description |
|---|---|
| Construction | The ordered sequence of operations the constructor performs, including validation of arguments and establishment of initial state |
| Initialization | Any asynchronous or deferred initialization that occurs after construction and before the object is ready to serve requests |
| Steady-state execution flows | The per-method execution sequences during normal operation |
| Request lifecycle | For request-scoped components: how each inbound request is received, processed, and completed |
| Resource acquisition | When and how the component acquires external resources (connections, file handles, memory allocations with ownership semantics) |
| Resource release | When and how acquired resources are released, including what triggers release and what happens to in-flight work |
| Caching | What is cached, the cache key computation, the TTL, invalidation triggers, eviction policy, and behavior on cache corruption or unavailability |
| Concurrency | How the component behaves under concurrent access: isolation guarantees, synchronization mechanisms, lock acquisition order, and atomicity claims |
| Retry | Whether failed operations are retried, what retry policy applies (count, backoff, jitter), which error classes are retryable, and what state is preserved across retry attempts |
| Timeout | How timeouts are measured, what event starts the timer, what happens when a timeout fires, and what state the component is in after a timeout |
| Cancellation | How in-progress operations are cancelled, what guarantees are provided to the caller after cancellation, and whether partial effects are rolled back |
| Fallback | When and how the component substitutes an alternative behavior for a primary behavior that has failed or is unavailable |
| Error propagation | Which errors are caught and swallowed (with logging obligations), which are caught and transformed into this package's error types, and which are rethrown unwrapped |
| Shutdown | The ordered sequence of operations on graceful shutdown: draining in-flight work, releasing resources, and reaching the terminal state |
| Recovery | How the component returns to a usable state after a recoverable error, and what preconditions must hold for recovery to succeed |
| Background execution | Any work that the component performs outside the caller's execution context: background refresh, periodic eviction, health probing |
| State transitions caused by runtime events | When a runtime event (timer expiry, external signal, background task completion) causes a state transition, the RT document owns the trigger description; the SM document owns the transition itself |

### 2.4 Behaviors that do NOT belong in an RT document

| Behavior class | Owner |
|---|---|
| Type definitions, interface shapes, method signatures | API |
| Error type hierarchy and error code enumeration | API |
| State enumeration and transition table | SM |
| Entry and exit actions on states | SM |
| Quantified SLOs (latency, throughput, memory budget) | PERF |
| Thread safety classifications expressed as guarantees | PERF |
| Trust boundaries and authentication/authorization rules | SEC |
| Input validation rules for security-relevant inputs | SEC |
| Named metric definitions, log event schemas, trace span names | OBS |
| Infrastructure dependencies and environment variables | DEPLOY |
| Migration instructions between package versions | MIG |
| Module structure and dependency rules | ARCH |
| Adapter-specific behavioral variations | ADAPT |

## 3. Definitions

The following terms are used normatively in RT-001 and in all RT documents governed by it. Terms defined in TS-001 §3 are not restated here; they apply without modification. Additional terms defined here are specific to the runtime behavior domain.

| Term | Definition |
|---|---|
| **Atomic operation** | An operation that either completes in full or has no observable effect. An atomic operation that is interrupted mid-execution MUST leave the system in the state it was in before the operation began. |
| **Background task** | Any work the component initiates that is not synchronously awaited by the caller's current execution context. Background tasks have defined lifecycles and MUST be terminated as part of shutdown. |
| **Caller** | The code that invokes a public method or function. The RT document specifies what the caller MUST guarantee (preconditions) and what the implementation MUST guarantee in return (postconditions). |
| **Completion** | The point at which a method returns normally — the return value or resolved promise is available to the caller and all postconditions hold. |
| **Deduplication** | The suppression of duplicate concurrent operations: when two callers request the same operation simultaneously, exactly one underlying execution occurs and both callers receive the same result. |
| **Disposal** | The act of releasing all resources held by a component and placing it in a terminal state from which no further operations are accepted. Disposal is irreversible. |
| **Durable side effect** | An observable effect that persists after the method returns: a mutation to shared state, a write to an external store, an emitted event. Distinguished from transient side effects (log entries) in that durability implies the effect survives a restart. |
| **Execution flow** | The complete ordered sequence of operations, decision points, and transitions that a component performs in response to a specific trigger. Each public method MUST have at least one documented execution flow (the success flow) and one or more error flows. |
| **Fatal failure** | A failure from which the component cannot recover without disposal and reconstruction. After a fatal failure, the component MUST NOT accept further method calls. |
| **In-flight operation** | An operation that has been initiated but has not yet completed or failed. A component undergoing shutdown MUST specify what it does with in-flight operations. |
| **Postcondition** | A condition that MUST hold when a method returns normally. Postconditions are what the caller may rely on after a successful invocation. |
| **Precondition** | A condition that MUST hold when a method is called. Violation of a precondition by the caller is a programming error. The implementation's behavior when a precondition is violated is explicitly defined in the precondition table or stated as "undefined behavior." |
| **Recoverable failure** | A failure from which the component can return to a usable state without disposal. The RT document specifies what recovery steps, if any, the caller must take. |
| **Side effect** | Any observable change to system state that occurs as a result of invoking a method, beyond the return value. |
| **Steady state** | The lifecycle phase during which the component is fully initialized and serving requests normally. A component in steady state accepts all non-lifecycle method calls. |
| **Terminal state** | A lifecycle state from which no transitions to non-terminal states exist. A component in a terminal state MUST reject all method calls with a `StateError` or equivalent. |
| **Visible state** | Component state that is directly observable by the caller through the public API — either as a property value or as a difference in the behavior of another method. Hidden state (private fields not reflected in the public API) is not subject to RT specification. |

## 4. Ownership

### 4.1 RT-001 ownership

**Owner:** Chief Architect.
**Version authority:** Chief Architect approves all MAJOR and MINOR increments. PATCH increments may be delegated to a designated Principal Architect.
**Designated reviewers:** Minimum two Principal Architects with runtime specification experience.

### 4.2 Governed document (RT) ownership

Every RT document has exactly one owner, designated in the package's ARCH document. The owner is the Staff Engineer responsible for the RT document type per EDS-001 §4.5.

**Owner responsibilities:** See TS-001 §8.2 for the general list. In addition, the RT owner MUST:
- Coordinate with the API owner to ensure every API method has a corresponding RT section before the API document is frozen.
- Coordinate with the SM owner to ensure all SM transitions that are triggered by runtime events are cited in the appropriate RT method sections.
- Coordinate with the SEC owner to identify which RT methods perform security-relevant operations.
- Own the deduplication model for concurrent operations, stated in §6 (Concurrency Model) of every governed RT document.

| Change type | Approver |
|---|---|

| MINOR to any RT document | RT document owner + Package Owner |
| MAJOR to any RT document | RT document owner + Package Owner + Principal Architect |
| Any change to RT-001 itself | Chief Architect + two Principal Architects |

## 5. Audience

### 5.1 Primary audience — implementing engineers

Engineers who build the package use the RT document as the authoritative behavioral contract. They read RT to understand what every method must do, in what order, under what conditions, and what errors must be raised. An implementing engineer must be able to implement every method to full conformance using only the API document (for types and signatures) and the RT document (for behavior).

### 5.2 Secondary audience — test authors

Engineers writing the TEST document and the test suite for the package use the RT document as the source of test case derivation. Every normative postcondition in RT generates at least one required test case. Every error path generates at least one required test case.

### 5.3 Tertiary audience — security and performance reviewers

The SEC owner uses the RT document to identify which methods cross trust boundaries and require security analysis. The PERF owner uses the RT document to identify which execution flows have latency implications and require SLO definition.

**Assumed knowledge:** Readers are assumed to be fluent engineers who have read the package's ARCH and API documents before reading the RT document. The RT document does not explain type definitions or module structure; it cites them.

## 6. Lifecycle

RT documents pass through the lifecycle states defined in EDS-001 §4.5 and governed by EES-001 §4.6:

```
Draft → Under Review → Frozen → Superseded | Archived
```

**Authorship dependency:** An RT document MUST NOT enter Under Review status until the package's API document is Frozen. The RT document is keyed to API method signatures; a non-frozen API means those signatures are not yet stable, and RT sections written against unstable signatures will require rework.

**Coordination dependency:** An RT document MUST be at stable draft (all sections complete) before the package's API document is frozen, because the API document cites RT sections by number in its behavioral specification citations. The RT owner and API owner coordinate on section numbers during the late stages of API authorship.

**Freeze dependency:** An RT document may be frozen independent of the SEC, PERF, TEST, OBS, and ADAPT documents. Those documents depend on RT and are authored after RT is frozen. RT freezing is a gate for them.

## 7. Normative Language

RT-001 and all governed RT documents use the RFC 2119 modal vocabulary as defined in ESS-001 §5.1 and TS-001 §3.1. The following applications are specific to runtime behavior documentation:

**In execution flow steps:** MUST denotes an invariant step — it must occur in every execution of the flow. MAY denotes a conditional step — it occurs only under stated conditions. The condition MUST always be stated.

**In precondition tables:** MUST denotes a caller obligation. "The caller MUST…" means the implementation is only obligated to behave correctly when this condition holds.

**In postcondition tables:** MUST denotes an implementation obligation. "The implementation MUST…" means this condition is guaranteed to hold when the method returns normally.

**Subject specificity requirement:** Every normative statement in an RT document MUST name its subject explicitly. "The component MUST NOT retain a reference" is non-compliant. "The `Registry` MUST NOT retain a reference" is compliant. Unnamed subjects are non-compliant per ESS-001 SP1.

## 8. Mandatory Sections

Every RT document MUST contain the following sections in the order defined in §9. No section may be omitted. A section that does not apply to the package must be present and marked:

> None — this package has no {section topic}. Rationale: {one sentence explanation}.

An omitted section without this marking is a structural defect detected at checklist item RT-S-01.

| Section # | Section title | Required content summary |
|---|---|---|
| 1 | Document Header | Per ESS-001 §4.1 and RT-001 §4 |
| 2 | Definitions | Alphabetical table of terms used normatively in this document |
| 3 | Scope | Covered methods/components and explicit exclusions |
| 4 | Initialization | Construction sequence, post-construction state, deferred initialization |
| 5 | Method Behaviors | One subsection per public method, in API document order |
| 6 | Concurrency Model | Thread safety classification, locking, atomicity, visibility |
| 7 | Caching Behavior | One subsection per cache maintained by the package |
| 8 | Lifecycle | Complete object lifecycle from construction to disposal |
| 9 | Error Behavior | Error propagation policy, recovery, fatal vs. recoverable failures |
| 10 | Background Execution | All background tasks: trigger, lifecycle, shutdown behavior |
| 11 | Resource Ownership | Allocation, sharing, and release rules for all owned resources |
| 12 | Retry and Timeout Policy | Per-operation retry rules and timeout measurement |
| 13 | Cancellation | Cancellation contract for every cancellable operation |
| 14 | Fallback Behavior | All fallback chains: trigger conditions and substitution behavior |
| 15 | Change History | Per ESS-001 §4.9 |

## 9. Mandatory Section Ordering

Section ordering is fixed and canonical. The rationale for the ordering is: the document progresses from the most general (initialization and signatures) to the most specific (cancellation, fallback), so that each section assumes the reader has already processed the preceding sections.

| Order | Section | Rationale for position |
|---|---|---|
| 1 | Document Header | Must precede all content |
| 2 | Definitions | Must precede use of defined terms |
| 3 | Scope | Bounds reader expectations before detail begins |
| 4 | Initialization | Construction is temporally first; all subsequent sections assume it |
| 5 | Method Behaviors | Core behavioral content; ordered to match API document for cross-reference |
| 6 | Concurrency Model | Governs how method behaviors compose under concurrency |
| 7 | Caching Behavior | Shared state mechanism referenced by multiple method behaviors |
| 8 | Lifecycle | Integrates method behaviors into a temporal whole |
| 9 | Error Behavior | Cross-cutting error rules applied to method behaviors |
| 10 | Background Execution | Out-of-band processes that affect observable state |
| 11 | Resource Ownership | Governs allocation/release obligations referenced in method behaviors and lifecycle |
| 12 | Retry and Timeout Policy | Cross-cutting policies referenced by individual method behaviors |
| 13 | Cancellation | Depends on understanding of method behaviors and resource ownership |
| 14 | Fallback Behavior | Depends on understanding of error behavior and retry policy |
| 15 | Change History | Must be final |

## 11. Notation Rules

### 11.1 Identifier notation

All code-level identifiers — class names, method names, property names, error types, error codes, state names, event names — are written in `monospace` throughout all RT document sections. This applies in both normative and informative content.

### 11.2 State reference notation

State names cited from the SM document are written in `monospace` ALL_CAPS to distinguish them from prose: `READY`, `CLOSING`, `FAILED`. When citing a state, the RT document MUST include a reference to the SM document section defining it:

> The `Registry` MUST be in the `READY` state (see I18N-SM-{VERSION} §3, row `READY`) when this method is called.

### 11.3 Execution flow step notation

Execution flow steps are numbered beginning at 1. Steps that are conditional are introduced with an "If" clause in the step description. Alternative paths branch from a numbered step and are lettered: step 3a, step 3b. All branches MUST terminate at a numbered step, a named error path, or a labeled postcondition.

**Format for a single execution flow step:**

```
{N}. [{Optional: If {condition}:}] {Subject} {MUST|MAY} {action}.
     [{Optional: See {DOCUMENT-ID} §{N.N} for {what}.}]
     [{Optional: Emits {event-name} per {PACKAGE}-OBS-{VERSION} §{N.N}.}]
     [{Optional: Causes state transition to `{STATE}` per {PACKAGE}-SM-{VERSION} §4, row ({CURRENT_STATE}, {EVENT}).}]
```

### 11.4 Duration notation

All durations are stated in explicit, spelled-out units: "60 seconds", not "60s". When a duration is defined by a PERF SLO rather than a fixed value, the RT step cites the PERF document: "within the timeout defined in {PACKAGE}-PERF-{VERSION} §3, row `{OperationName}`."

### 11.5 Sequence diagram policy

Sequence diagrams are INFORMATIVE. They illustrate a normative execution flow; they do not replace it. Every sequence diagram MUST be preceded by the normative numbered execution flow it illustrates. In the event of contradiction between a diagram and a numbered flow, the numbered flow governs. Diagrams MUST be labeled:

> [Diagram — {description} — INFORMATIVE. Normative source is §5.{N} steps {M}–{P}.]

## 12. Domain-Specific Rules

### 12.1 Execution flow completeness rule

Every public method MUST have at minimum:
- One success execution flow (the normal path when all preconditions are met)
- One or more error execution flows (one per distinct error path)

A method with no documented error paths is non-compliant unless the RT document explicitly states: "This method has no error paths. It is a pure computation that MUST NOT throw under any input satisfying its preconditions." Pure computations of this kind are rare; the author MUST verify this claim against the SEC document's input validation rules before making it.

### 12.2 Error path completeness rule

The error path table for every method MUST be exhaustive. Every error type listed in the API document's Throws table for that method MUST have a corresponding row in the RT error path table. Discrepancy between the API Throws table and the RT error path table is a cross-document consistency defect caught by checklist item RT-X-01.

### 12.3 Concurrency statement requirement

Every method that could be called concurrently MUST have a concurrency statement in its §5.{N} section. The concurrency statement either:
- Delegates to the class-level thread safety classification in §6 ("Thread safety: per §6, `{ClassName}` instance-level isolation applies"), or
- States a method-specific exception to the class-level classification with full justification.

A method with no concurrency statement is non-compliant unless §6 contains an explicit class-level statement that covers it.

### 12.4 State transition citation requirement

Any method that causes a state transition in a stateful object MUST include a side-effects entry citing the SM document's transition row. Format:

> **Side effects:** Causes state transition `{CURRENT_STATE}` → `{NEXT_STATE}` per {PACKAGE}-SM-{VERSION} §4, row ({CURRENT_STATE}, `{EVENT}`).

A method that causes a state transition but does not cite it is a cross-document consistency defect caught by checklist item RT-X-02.

### 12.5 Background task lifecycle requirement

Every background task MUST have a documented lifecycle with four phases:
1. **Trigger:** What starts the background task.
2. **Execution:** What the background task does.
3. **Error handling:** What the background task does when its work fails. It MUST NOT silently swallow errors.
4. **Shutdown:** How the background task is terminated as part of component shutdown, and what happens to in-progress work at shutdown time.

A background task with an undocumented shutdown behavior is non-compliant.

### 12.6 Resource ownership transfer rule

When a method transfers resource ownership — either from caller to implementation (the implementation takes responsibility for releasing the resource) or from implementation to caller (the caller takes responsibility) — the direction of transfer MUST be stated explicitly in the method's §5.{N} section and reflected in the resource ownership table (§11). Implicit ownership transfer is non-compliant.

### 12.7 In-flight deduplication specification rule

When a package deduplicates concurrent requests for the same operation (e.g., two concurrent calls to load the same namespace return the same result from a single loader invocation), the deduplication behavior MUST be fully specified with:
- The key used to identify duplicate requests
- Whether the second caller receives the result synchronously or asynchronously with respect to the first caller's completion
- What happens when the deduplicated operation fails (does the failure propagate to both callers?)
- Whether the deduplication spans process restarts or is in-process only

### 12.8 Partial failure specification rule

When an operation can succeed partially (some work completes, some fails), the RT document MUST specify:
- What constitutes "partial success" for this operation
- What observable state the system is in after partial success
- Whether the caller receives a partial result, an error, or both
- Whether partial effects are rolled back or retained

A method that can partially succeed but has no partial failure section is non-compliant.

### 12.9 Memory visibility rule

When a method mutates shared state, the RT document MUST specify when that mutation is visible to other callers. Options are: "immediately visible upon method return", "visible after the next full memory fence", or "eventual consistency with a bound of {N} operations." Unspecified visibility is non-compliant.

## 13. Versioning and Backward Compatibility

### 13.1 Semantic versioning for RT documents

RT documents follow semantic versioning per EDS-001 §6.6. The following criteria determine version type for RT-specific changes:

**MAJOR changes (breaking) in an RT document:**
- Removing a documented behavior (previously specified operations that may no longer occur)
- Changing an execution flow step that was previously normative
- Changing a postcondition to be weaker (removing a guarantee)
- Changing an error condition so that an error previously thrown is no longer thrown
- Changing a caching behavior in a way that alters observable timing
- Changing a concurrency guarantee in a way that requires callers to add synchronization
- Changing lifecycle phase transitions that callers must respond to
- Changing retry or timeout policies in a way that changes observable timing guarantees
- Changing resource ownership transfer direction
- Adding a precondition (restricts previously valid inputs)
- Making a previously synchronous operation asynchronous or vice versa

**MINOR changes (non-breaking) in an RT document:**
- Documenting a previously unspecified edge case without changing behavior
- Adding a new background task (additive)
- Adding a new cache (additive)
- Adding a fallback behavior for a previously unhandled error class
- Adding documentation for a new method (mirrors an API MINOR change)
- Strengthening a postcondition (adding a guarantee)

**PATCH changes in an RT document:**
- Typographical corrections
- Clarification of ambiguous prose without behavioral change
- Addition of an informative example or diagram
- Correction of a broken cross-reference

### 13.2 API/RT version alignment

When a new MAJOR or MINOR version of an API document is published, the RT owner MUST assess whether an RT update is required:
- Every new method in the API MUST have a corresponding RT section before the RT document's next MINOR or MAJOR version is frozen.
- A behavioral change that triggers a MAJOR API version MUST also trigger a MAJOR RT version.
- The RT version need not be identical to the API version; they version independently per EDS-001 §P5.

## 14. Deprecation Rules

### 14.1 Applicability

The general deprecation rules from TS-001 §4.5 apply without modification. The following RT-specific rules are additive.

### 14.2 Behavioral deprecation

When a behavior — not a symbol — is deprecated (e.g., a retry policy that is changing in the next major version), the RT document must include a deprecation notice in the relevant section:

```
[DEPRECATED since {version} — this behavior will change in version {N.0.0}. See {PACKAGE}-MIG-{N-1}-to-{N} for migration guidance.]
```

### 14.3 Deprecation of background tasks

A background task that is being removed in a future version MUST be deprecated in the RT document for at least one MINOR version before removal. Its §10.{N} section carries the deprecation notice and states the version in which it will be removed.

### 14.4 Concurrency guarantee deprecation

Weakening a concurrency guarantee — changing "thread-safe" to "requires external synchronization" — is a MAJOR change regardless of how it is labeled. It may not be done in a MINOR or PATCH version under any circumstances.

### 15.2 Adapter extensions to RT

An ADAPT document may define adapter-specific behavioral deviations from an RT section. When it does, it MUST:
- Cite the RT section it deviates from
- State only the delta — what is different for this adapter
- Not restate the RT content it does not change

An ADAPT document that contradicts an RT section without citing it is a cross-document contradiction, not a valid extension.

## 16. Examples Policy

### 16.1 All examples are informative

Examples in RT documents are informative. They illustrate normative execution flows; they do not replace them. In any conflict between an example and a normative statement, the normative statement governs.

### 16.2 Normative flow examples

A normative flow example shows a complete execution of the steps in §5.{N} for a specific set of inputs. It MUST:
- Identify the inputs
- Trace each step by its number
- Show which branch is taken at each decision point
- Show the final postcondition that holds

Label: `[Example — {MethodName} success flow with {input description}]`

### 16.3 Error flow examples

An error flow example shows a specific failure scenario. It MUST:
- Identify the trigger condition
- Trace the execution to the point of failure
- Show the error type and code raised
- Show the state of the object after the error

Label: `[Example — {MethodName} error flow: {error code}]`

### 16.4 Anti-patterns

An anti-pattern in an RT document shows a behavioral pattern that the implementation MUST NOT exhibit, paired with the normative rule it violates. Anti-patterns are especially useful for concurrency and lifecycle violations.

Label: `[Anti-pattern — {description}]`
Structure: show the forbidden behavior, cite the normative rule it violates, show the compliant alternative.

### 16.5 Counterexamples

A counterexample shows a scenario that might appear to be allowed by the normative text but is explicitly not allowed. Counterexamples appear where the normative text has a boundary that is easy to misread.

Label: `[Counterexample — {description}: this is NOT allowed]`

## 17. Prohibited Content

The following content is explicitly prohibited in RT documents. Its presence is a blocking defect at Specification Review.

| Prohibited content | Correct location |
|---|---|
| Type definitions, interface shapes, method signatures | API document |
| Error type definitions or error code enumerations | API document |
| State enumeration or complete transition tables | SM document |
| Quantified SLOs (specific millisecond targets, throughput numbers) | PERF document |
| Security threat models, trust boundary definitions, authorization rules | SEC document |
| Named metric definitions, log event schemas with structured field lists | OBS document |
| Infrastructure dependencies, environment variable names | DEPLOY document |
| Migration instructions for package consumers | MIG document |
| Module structure diagrams or module dependency rules | ARCH document |
| Adapter-specific behavioral variations beyond the base specification | ADAPT document |
| Implementation code, pseudocode that specifies an algorithm at code level | IMPL document |
| "TBD", "TODO", "to be specified", or placeholder strings | N/A — blocking defect |
| Prose descriptions of type shapes in place of citations to the API document | API document (cited) |
| Rationale for architectural decisions | ADR |
| Future plans, roadmap items, or "in the next version" statements | RFC |

## 18. Cross-Reference Rules

### 18.1 Inherited rules

All cross-reference rules from EDS-002 §22 and TS-001 §6 apply without modification.

### 18.2 Mandatory citations in RT documents

The following citations are mandatory in every RT document:

| Citation type | When required | Format |
|---|---|---|
| API method signature | At the opening of every §5.{N} section | "Per {PACKAGE}-API-{VERSION} §6.{N}, signature: `{signature}`." |
| API error type | In every error path table row | Error type cited from {PACKAGE}-API-{VERSION} §5.{N} |
| SM state name | Every time a state name appears in a normative statement | Cite state definition: "(`{STATE}` — see {PACKAGE}-SM-{VERSION} §3, row `{STATE}`)" on first use per section |
| SM transition | Every method that causes a state transition | Cite transition row: "{PACKAGE}-SM-{VERSION} §4, row (`{CURRENT}`, `{EVENT}`)" |
| PERF timeout value | Every timeout reference in an execution flow | "timeout defined in {PACKAGE}-PERF-{VERSION} §3, row `{OperationName}`" |
| OBS log event | Every log emission in a side-effects statement | "{log-event-name} per {PACKAGE}-OBS-{VERSION} §3.{N}" |
| SEC validation rule | Every method that performs security validation | "{PACKAGE}-SEC-{VERSION} §{N.N} — {boundary name}" |

### 18.3 Forbidden reference patterns in RT documents

| Forbidden pattern | Reason |
|---|---|
| Citing an unfrozen API document | RT is written against a frozen API |
| Restating an API type definition | Duplication; cite instead |
| Citing a PERF document's value inline without reference | Duplication; PERF owns the value |
| Citing an ADAPT document from within base RT | ADAPT is downstream of RT; the reference direction is reversed |
| Floating references (no version number) | Non-deterministic per EDS-002 §22.2 |

## 20. Completeness Scoring

RT documents are scored using the five-dimension model from TS-001 §7.2. The RT-specific rubric per dimension:

**Dimension 1 — Structural completeness (0–20):**
- 20: All 15 sections present; every public API method has a §5.{N} section; no section is "None" without rationale.
- 15: One non-critical section is thin or has placeholder content.
- 10: One critical section is missing (§5 Method Behaviors, §6 Concurrency Model, or §8 Lifecycle).
- 5: Two or more sections are missing or empty.
- 0: Template not followed; fewer than half the required sections are present.

**Dimension 2 — Normative precision (0–20):**
- 20: All execution flow steps are numbered, have explicit subjects, use RFC 2119 vocabulary. No forbidden language in normative sections.
- 15: 1–3 steps missing subject specification or using imprecise language.
- 10: A complete method section uses vague behavioral descriptions instead of numbered flows.
- 5: Systematic use of prose narrative in place of numbered execution flows.
- 0: Document describes behaviors rather than prescribing them throughout.

**Dimension 3 — Error path coverage (0–20):**
- 20: Every method has an exhaustive error path table; every row has a State-after-error and Recoverable entry; §9 has a complete propagation policy.
- 15: One method has an incomplete error path table.
- 10: Multiple methods have incomplete error paths; or §9 is absent.
- 5: Error paths exist but use "may fail" or "handles errors" style language.
- 0: No error path tables; §9 absent or empty.

**Dimension 4 — Cross-reference integrity (0–20):**
- 20: Every state reference cites SM; every type reference cites API; every timeout cites PERF; no content duplication.
- 15: 1–3 missing SM transition citations.
- 10: Multiple missing citations or one instance of content duplicated from API.
- 5: Systematic absence of SM/API citations; behavioral content from API embedded in RT.
- 0: No cross-references; RT functions as a standalone combined API+RT document.

**Dimension 5 — Audience appropriateness (0–20):**
- 20: Content is implementation-sufficient and correctly scoped; no prohibited content.
- 15: Minor off-type content (one paragraph).
- 10: A section contains type definitions or state tables that belong in API or SM.
- 5: The document conflates RT and API or RT and SM throughout.
- 0: Document is a code walkthrough rather than a behavioral specification.

**Thresholds:** Per TS-001 §7.2: 95–100 eligible for freezing; 85–94 accepted with deficiencies; 70–84 returned for revision; 0–69 rejected.

## 22. Freeze Criteria

An RT document MAY be frozen only when all of the following hold:

1. All 11 Quality Gates (RTG-01 through RTG-11) pass.
2. Completeness score ≥ 85.
3. The document contains no "TBD", "TODO", "to be specified", or placeholder strings in any section.
4. The API document for this package is Frozen at the version cited in the RT document.
5. The SM document for this package is Frozen at the version cited (when an SM document exists).
6. All cross-references resolve to frozen documents at the stated versions.
7. The Status header reads "Under Review" and the Specification Review panel has approved in writing.
8. For a MAJOR version: the RFC is closed as Accepted; any required ADR is filed as Accepted.
9. The Change History table contains an entry for the version being frozen.
10. The Package Owner has signed the validation checklist.
11. The TEST document owner has co-signed per RTG-09.

**Post-freeze immutability:** A frozen RT document MUST NOT be modified in place. Any change — including a typographical correction — requires a new version, a new review, and a new freeze.

## 23. Amendment Policy for RT-001

### 23.1 What requires an amendment to RT-001

An amendment to this document is required when:
- The mandatory section list (§8) is changed.
- A new required table is added to §10.
- A domain-specific rule in §12 is added, removed, or changed.
- A new item is added to the RT validation checklist (§19).
- A new quality gate is added to §21.
- The breaking/non-breaking change classification in §13 is changed.
- A new notation rule is added to §11.

### 23.2 Amendment process

1. File an RFC against RT-001 with a minimum 5 business day comment period.
2. Chief Architect and two Principal Architects review.
3. RT-001 is updated to a new version per §13.1.
4. All RT document owners are notified.
5. Grandfathering applies per TS-001 §4.6: existing frozen RT documents remain compliant with the RT-001 version under which they were frozen. Revised RT documents must comply with the current RT-001 version.
