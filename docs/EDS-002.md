# ARQON Platform — Engineering Specification Standard
## EDS-002 / ESS-001 — Version 1.0
**Status:** Active — Effective immediately upon ratification.
**Owner:** Chief Architect
**Audience:** All engineers, architects, and technical leads who write, review, or approve engineering specification documents on the ARQON Platform.

---

## 1. Purpose

EDS-001 defines what engineering documents exist, what each type owns, and when each is created. ESS-001 defines how each document type is written. Its objective is to make specification authorship deterministic: two independent architects given the same engineering facts must produce documents with the same organization, the same level of detail, the same terminology, and the same structural completeness.

ESS-001 does not change document ownership rules. Every ownership question is answered by EDS-001 §5. ESS-001 answers only authorship questions: structure, writing rules, required sections, prohibited content, terminology standards, templates, validation, scoring, and governance.

A specification document that does not conform to ESS-001 is non-compliant regardless of its technical accuracy. Technical accuracy and structural conformance are independent properties; both are required for a document to be frozen.

## 3. Specification Principles

These principles govern every authorship decision at every level of detail. They take precedence over any section-level rule when a conflict arises. An author who cannot satisfy a section-level rule without violating a principle must resolve the conflict by amending the section-level rule through the amendment process (§25), not by violating the principle.

**SP1 — Determinism over completeness.** A specification that is incomplete is better than one that is ambiguous. An omission can be filed as a specification gap and resolved through a patch. An ambiguity can produce two incompatible implementations before anyone notices. When in doubt, state what is known precisely, mark what is unknown explicitly, and do not bridge the gap with vague language.

**SP2 — Prescriptive, not descriptive.** A specification prescribes behavior. It does not describe what the implementation currently does. "The cache stores entries for 60 seconds" is not a specification; "the cache MUST store each entry for exactly 60 seconds measured from the time of insertion" is. Specifications use the modal vocabulary defined in §5.

**SP3 — One fact, one location.** Every engineering fact appears in exactly one section of exactly one document. A fact that must be communicated across documents is communicated by citation (§22), never by restatement.

**SP4 — Audience-appropriate scope.** Each document type is written for its designated audience (EDS-001 §4). An author who finds themselves explaining concepts that are prerequisite knowledge for the document's audience is writing for the wrong audience or has misclassified the content.

**SP5 — Falsifiability.** Every normative statement in a specification must be testable. A statement that cannot be expressed as a passing or failing test case is not a specification — it is a design note and belongs in IMPL, not in a Tier 2 document.

**SP6 — No forward compatibility assumptions.** A specification describes the current contract. It does not describe planned future extensions, hoped-for optimizations, or anticipated deprecations. Future intent belongs in an RFC. A statement beginning with "In the future…" or "Eventually…" is a violation of SP6.

**SP7 — Symmetrical treatment of error paths.** Every normative statement about the success path has a corresponding normative statement about the error path. An API that specifies what it returns on success but not what it does on failure is incomplete by definition.

## 4. Mandatory Writing Rules

These rules apply to every document type governed by ESS-001 without exception.

### 4.1 Document Header

Every document MUST begin with a header block in the following exact format. Fields marked required may not be omitted. Fields marked conditional are omitted only when the condition is not met.

```
# {PACKAGE} {DOCTYPE} — {Title}
## {DOCUMENT-ID} — Version {MAJOR}.{MINOR}.{PATCH}
**Status:** {Draft | Under Review | Frozen | Superseded | Archived}
**Owner:** {Full name and role}
**Audience:** {One sentence naming the specific reader role(s)}
**Depends on:** {Comma-separated list of document IDs this document depends on; "None" if none}
**Supersedes:** {Document ID of prior version; omit if this is version 1.0.0}
**Superseded by:** {Document ID of successor; omit if not yet superseded}
```

### 4.2 Section Numbering

All sections are numbered with dot-notation (`1`, `1.1`, `1.1.1`). Numbering must be continuous and must not skip levels. A subsection requires a parent section; `§3.2` requires `§3` to exist. Section numbers are stable across patch versions. A new section may be added at a minor version; an existing section may not be renumbered.

### 4.3 Normative vs. Informative Content

Every section is either normative or informative.

- **Normative sections** prescribe binding behavior. They are the authoritative content of the document. Every normative section uses the modal vocabulary defined in §5.
- **Informative sections** provide context, rationale, or examples. They are clearly labeled with the prefix `[INFORMATIVE]` in the section title. Informative content never overrides normative content. In the event of conflict, the normative section governs.

At least 80% of the substantive content of any Tier 2 document MUST be normative.

### 4.4 Normative Statements

Every normative statement in a Tier 2 document MUST:

- Use the modal vocabulary defined in §5
- Be scoped to a specific subject (not "the system" or "components" in general)
- Be falsifiable per SP5
- Have a corresponding error-path statement if it describes a success-path behavior (SP7)

A normative statement that does not identify its subject is incomplete. Acceptable: "The `Registry` MUST NOT hold a reference to the caller's `Logger` after `Registry.close()` returns." Unacceptable: "The logger MUST NOT be retained after close."

### 4.5 Forbidden Language

The following language patterns are forbidden in normative sections:

| Forbidden pattern | Reason | Replacement |
|---|---|---|
| "should" (lowercase, non-RFC) | Indeterminate obligation | SHOULD (RFC 2119) or restructure as MUST |
| "might", "could", "may or may not" | Non-deterministic | Specify the exact condition under which the behavior occurs |
| "typically", "usually", "in most cases" | Non-deterministic | State the invariant; carve out the exception explicitly |
| "the system", "the platform", "components" as subject | Ambiguous actor | Name the specific class, function, or module |
| "etc.", "and so on", "among others" | Open-ended enumeration | Enumerate completely or state the rule that generates the set |
| "TBD", "TODO", "to be specified" | Incomplete specification | A document containing these strings may not be frozen |
| "as expected", "naturally", "obviously" | Implied knowledge | State the behavior explicitly |
| "similar to", "analogous to" | Imprecise reference | Cite the exact section; do not paraphrase |
| "in the future", "eventually", "planned" | Forward compatibility assumption (SP6) | Remove; file an RFC if the future direction matters |
| "implementation-defined" | Delegated ambiguity | State the constraint; if variation is allowed, enumerate the allowed values |

### 4.6 Tables

Tables are mandatory for any enumeration of three or more items where items have two or more attributes. A prose list of five error codes with their meanings is a table violation. Every table MUST have:

- A numbered caption (`Table N — {Title}`)
- A header row with column names
- All cells populated (no empty cells; use "N/A" with justification when truly not applicable)

### 4.7 Code and Signature Notation

Type signatures in specification documents use TypeScript-style notation regardless of the implementation language. This is a notation standard, not a language requirement. The implementation may use any language; the specification uses TypeScript notation for precision.

```typescript
// Correct: complete signature with types and optionality
constructor(cache: CacheProvider, logger?: Logger): void

// Incorrect: missing return type
constructor(cache, logger)

// Incorrect: narrative description in lieu of signature
// "takes a cache and an optional logger"
```

When a parameter is optional with a default value, the default MUST be stated explicitly in the signature or in a normative note immediately following it.

### 4.8 Examples

Examples in specification documents are informative. They illustrate a normative statement; they do not replace it. An example MUST be preceded by the normative statement it illustrates. An example without a preceding normative statement is a violation of SP3 — the example is asserting behavior that has not been formally specified.

Examples are clearly labeled:

```
[Example — {description}]
{code or prose}
[End Example]
```

### 4.9 Change History

Every document MUST include a Change History table as its final section, before any appendices. The table records every version with date, author, and a one-sentence summary of changes. A document without a Change History table may not be frozen.

```
| Version | Date | Author | Summary |
|---|---|---|---|
| 1.0.0 | YYYY-MM-DD | {Name} | Initial frozen version. |
```

## 5. Terminology Rules

### 5.1 Modal Vocabulary

ESS-001 adopts the RFC 2119 modal vocabulary without modification. Every author MUST be familiar with the precise meanings of these terms before writing a normative section.

| Term | Meaning |
|---|---|
| MUST | Absolute requirement. Non-conformance is a defect. |
| MUST NOT | Absolute prohibition. Non-conformance is a defect. |
| REQUIRED | Synonym for MUST. Used when MUST would be grammatically awkward. |
| SHALL | Synonym for MUST. |
| SHALL NOT | Synonym for MUST NOT. |
| SHOULD | Strong recommendation. Non-conformance is permitted with documented justification. |
| SHOULD NOT | Strong recommendation against. Non-conformance is permitted with documented justification. |
| RECOMMENDED | Synonym for SHOULD. |
| MAY | Truly optional. Conforming implementations may or may not implement this behavior. |
| OPTIONAL | Synonym for MAY. |

These terms are written in ALL CAPS when used with their RFC 2119 meaning. When used in their ordinary English sense they are written in lower case. The distinction is significant: "a consumer may call this method multiple times" (ordinary English, no normative force) versus "a consumer MAY call this method multiple times" (normative permission).

### 5.2 Defined Terms

Every non-obvious term used normatively in a specification MUST be defined in a `§1. Definitions` or `§2. Definitions` section of that document. A term is "non-obvious" if it is not a standard English word, is a term of art in the domain, or is used with a meaning more precise than its everyday sense.

Defined terms are written in **bold** on first use in each section and in `monospace` when referring to code-level identifiers. The definitions section MUST list terms alphabetically.

A term defined in one document and used in another is cited: "as defined in {DOCUMENT-ID} §{N}, a **{term}** is…". The term is not redefined in the citing document.

### 5.3 Identifier Notation

Code-level identifiers — class names, method names, property names, type names, CLI flags, environment variable names — are written in `monospace` throughout all sections. This applies in both normative and informative contexts. Mixed-case identifiers are written as they appear in the API (`CacheProvider`, not `cache provider` or `Cache Provider`).

### 5.4 Unit Notation

All durations are stated in consistent units with the unit spelled out: "60 seconds", not "60s" or "one minute". All sizes are stated in bytes, kilobytes, megabytes, or gigabytes with the unit spelled out. Ambiguous units ("entries", "items") are qualified: "60 cache entries measured from the last access time".

### 5.5 Prohibited Terms

The following terms are prohibited in normative sections because they cannot be specified precisely:

- "fast", "slow", "quickly", "efficiently" — replace with a quantified SLO
- "large", "small", "many", "few" — replace with a specific threshold
- "reasonable", "appropriate", "sensible" — replace with the actual criterion
- "simple", "complex", "trivial" — these are assessments, not specifications
- "clean", "readable", "maintainable" — implementation quality judgments; not specifiable

## 6. RFC Writing Rules

An RFC proposes a change and solicits structured feedback. It does not specify — accepted RFC content is migrated to the target Tier 2 document and the RFC closes as a historical record.

### 6.1 RFC Template

```markdown
# RFC-{PACKAGE}-{SEQUENCE} — {Title}
**Status:** Draft | Comment Period Open | Accepted | Rejected
**Author:** {Full name and role}
**Filed:** {YYYY-MM-DD}
**Comment period closes:** {YYYY-MM-DD}
**Target document(s):** {Comma-separated list of document IDs this RFC proposes to change}
**Related ADR:** {ADR-NNN if applicable; omit otherwise}

---

## 1. Summary
{One paragraph. What is being proposed and why.}

## 2. Current State
{Describe the current behavior or document state that this RFC addresses.
Cite specific sections of existing documents rather than paraphrasing them.}

## 3. Proposed Change
{Describe the proposed change precisely. Use normative language (§5.1) for
the new behavior being proposed. For document changes, show the current text
and the proposed replacement text in adjacent code blocks.}

### 3.1 Current text
{DOCUMENT-ID} §{N.N}:
> {exact current text}

### 3.2 Proposed replacement
{exact proposed replacement text}

## 4. Motivation
{Why this change is needed. Reference real implementation problems, observed
incompatibilities, or stated product requirements. Do not argue from
preference or aesthetics.}

## 5. Impact Analysis
### 5.1 Documents changed
{List every document that must be updated if this RFC is accepted, with the
section and the nature of the change.}

### 5.2 Breaking change assessment
{State whether this RFC proposes a breaking change per EDS-001 §6.5.
If yes, describe the consumer impact and migration path.}

### 5.3 Downstream package impact
{List any packages that consume the affected document's package and will be
affected by this change.}

## 6. Alternatives considered
{Describe at least one alternative approach and explain why the proposed
approach is preferred. An RFC with no alternatives considered is incomplete.}

## 7. Open questions
{List any questions that remain unresolved. Each question is numbered.
Resolved questions are moved to §8.}

## 8. Resolved questions
{Questions from §7 that were resolved during the comment period, with their
resolutions. Initially empty.}

## 9. Comments
{Comments from reviewers during the comment period. Format: date, author,
content. Responses from the RFC author are indented beneath the comment they
respond to.}

## 10. Decision
{Populated when the RFC is closed. States Accepted or Rejected, the decision
maker, the date, and the rationale. For Accepted RFCs, states the document
version in which the change was incorporated.}

---
*RFC-{PACKAGE}-{SEQUENCE} — ARQON Platform*
```

### 6.2 RFC Completeness Rules

An RFC is not ready for comment period until:

- Sections 1 through 6 are complete
- At least one alternative is described in §6
- All documents affected in §5.1 are enumerated
- The breaking change assessment in §5.2 is complete

An RFC that opens a comment period with an incomplete §5 or §6 is returned to Draft status by the approving Principal Architect.

## 7. ADR Template

An ADR records a single decision. It does not specify behavior; it records why a direction was chosen. All behavioral specification follows in ARCH and downstream documents.

```markdown
# ADR-{NNN} — {Title}
**Status:** Proposed | Accepted | Superseded | Deprecated
**Author:** {Full name and role}
**Date accepted:** {YYYY-MM-DD; omit if not yet accepted}
**Supersedes:** {ADR-NNN; omit if none}
**Superseded by:** {ADR-NNN; omit if none}

---

## 1. Context
{Describe the situation that required a decision. Include:
- The specific technical or organizational problem
- Any constraints that were non-negotiable
- The timeframe in which the decision needed to be made
Do not describe the decision itself in this section.}

## 2. Decision drivers
{List the criteria used to evaluate options. These are the values or
requirements that mattered most. Format as a numbered list.}

## 3. Options considered
{For each option that was seriously evaluated:}

### 3.{N} Option {N} — {name}
**Description:** {What this option is.}
**Pros:** {Bulleted list.}
**Cons:** {Bulleted list.}
**Why not chosen:** {If this option was not selected, explain briefly.
Omit this field for the chosen option.}

## 4. Decision
{State the decision in one or two sentences.
Example: "We adopt {Option N} as described in §3.{N}."}

## 5. Rationale
{Explain why the chosen option was selected over the alternatives.
Reference the decision drivers from §2 explicitly.}

## 6. Consequences
### 6.1 Positive consequences
{What becomes easier or better as a result of this decision.}

### 6.2 Negative consequences
{What becomes harder or more constrained. Every ADR has at least one
negative consequence; if none can be identified the analysis is incomplete.}

### 6.3 Resulting documents
{List the ARCH, API, RT, or other Tier 2 documents that this ADR requires to
be created or updated. This is the implementation obligation created by the
decision.}

---
*ADR-{NNN} — ARQON Platform — {Date}*
```

### 7.1 ADR Writing Rules

- **Exactly one decision per ADR.** An ADR that makes two decisions must be split.
- **§3 must contain at least two options.** A decision with only one option considered is not a decision — it is an announcement. The Architecture Review Board will reject an ADR with fewer than two evaluated options.
- **§6.2 must identify at least one negative consequence.** No decision is free of tradeoffs.
- **§6.3 must enumerate all resulting document obligations.** If an ADR is accepted and no documents are listed in §6.3, implementation cannot begin.
- **The decision in §4 must be unambiguous.** It must not contain hedging language ("we lean toward", "we prefer to explore"). It states what was decided.

### 8.1 ARCH Writing Rules

- **§3 must contain an entry for every directory in the package root.** A directory without a §3 entry is an undocumented module.
- **§4.1 and §4.2 must be complete and consistent.** If A may import B and B may import A, this is a dependency cycle and is a defect in the architecture, not in the document.

### 9.1 RT Writing Rules

- **Every method in the API document MUST have a corresponding §4.{N} section.** An RT document that does not cover a public method is incomplete.
- **Error path tables MUST be exhaustive.** "Other errors" is not an acceptable row. Every error type the method can raise or return must be named.
- **§6 is mandatory.** An RT document with no concurrency model section is incomplete, even if the answer is "this package is single-threaded and all methods MUST be called from the same thread."
- **§7 is mandatory if the package caches anything.** "Cache behavior is implementation-defined" is a violation of SP1.
- **Preconditions and postconditions are distinct.** A precondition is what must be true when the method is called. A postcondition is what will be true when it returns. Mixing them produces an unverifiable specification.

## 20. Completeness Scoring Model

Specification documents are scored before Specification Review. A document scoring below 85 is returned to the author. A document scoring 85–94 may be accepted with noted deficiencies tracked as specification debt. A document scoring 95–100 is eligible for freezing.

### 20.1 Scoring Method

The score is computed from five dimensions. Each dimension is scored 0–20. The total is out of 100.

**Dimension 1 — Structural completeness (0–20)**
All required sections for the document type are present and non-empty.
- 20: All required sections present with substantive content.
- 15: One non-critical section is missing or empty.
- 10: One critical section (Definitions, core behavior, error paths) is missing.
- 5: Two or more sections are missing.
- 0: Template was not followed.

**Dimension 2 — Normative precision (0–20)**
Normative statements are falsifiable, use correct modal vocabulary, and have no forbidden language.
- 20: Zero forbidden language patterns; all statements are falsifiable.
- 15: 1–2 non-critical instances of imprecise language.
- 10: Systematic use of imprecise language in one section.
- 5: Widespread imprecision across multiple sections.
- 0: Document uses no RFC 2119 vocabulary.

**Dimension 3 — Error path coverage (0–20)**
Every success path has a documented error path per SP7.
- 20: Every success path has a complete error path entry.
- 15: One method or behavior is missing an error path.
- 10: Multiple methods are missing error paths.
- 5: Error paths are present but qualitatively described ("may fail").
- 0: No error paths documented.

**Dimension 4 — Cross-reference integrity (0–20)**
All references to other documents use the correct citation format (§22), reference existing sections, and introduce no content duplication.
- 20: All references are correct; no duplication.
- 15: 1–2 minor citation format errors (e.g., version not pinned).
- 10: One significant duplication of content owned by another document.
- 5: Multiple duplications or several broken references.
- 0: Systematic duplication or no citations where required.

**Dimension 5 — Audience appropriateness (0–20)**
The document is written at the correct level of detail for its designated audience and contains no content that belongs in a different document type.
- 20: Content is precisely scoped to the document type; no off-type content.
- 15: Minor off-type content (one paragraph).
- 10: One section belongs in a different document type.
- 5: Significant content misplacement affecting two or more sections.
- 0: The document conflates multiple document types throughout.

### 20.2 Scoring Thresholds

| Score | Decision |
|---|---|
| 95–100 | Eligible for freezing. |
| 85–94 | Accepted with tracked deficiencies. Deficiencies MUST be resolved before the next minor version. |
| 70–84 | Returned for revision. Author MUST address all scoring failures before resubmission. |
| 0–69 | Rejected. A rejected document requires a full rewrite, not revision. |

| SG-07 | Document is consistent with all documents it depends on. No contradiction between this document and its dependencies. | Specification Review panel |
| SG-08 | The document's version increment correctly reflects the nature of changes (§23). | Package Owner |

## 22. Cross-Reference Rules

### 22.1 Citation Format

Every reference to content in another document uses the following format:

> See {DOCUMENT-ID} §{N.N} — {section title}.

Example: "See I18N-RT-2.1.0 §4.3 — `Registry.load` behaviors."

The document ID MUST include the full version number. A reference without a version number is non-compliant. When a document is updated, all references to it in other documents are reviewed for version accuracy.

### 22.2 Pinned vs. Floating References

All references in frozen Tier 2 documents are pinned to a specific version. The phrase "the current version of" is forbidden — it is a floating reference and produces an unversioned dependency.

Tier 4 documents (MIG, RUN, DEV, IMPL) MAY use floating references by naming the document without a version number, in which case the reference resolves to the latest frozen version at time of reading.

### 22.3 Forward References

A document MUST NOT reference a section that has not yet been defined within the same document. All internal forward references (e.g., "as described in §7 below") are forbidden. The content in §7 must be accessible from the point of reference by reading upward, or the document must be reorganized.

### 22.4 Reference Depth

References MUST be direct. A document MAY NOT say "see Document A §3, which references Document B §5." The citing document cites Document B §5 directly if that content is needed. Chains of references that require the reader to traverse more than one hop to reach the authoritative content are non-compliant.

### 22.5 Reference Validation

Before a document is submitted for Specification Review, every cross-document reference MUST be validated:

1. The referenced document exists.
2. The referenced document is frozen at the stated version.
3. The referenced section exists in that version.
4. The referenced section contains the content the citing document implies.

A broken reference (document not found, section not found, version not frozen) is a blocking defect.

## 23. Versioning Rules

### 23.1 Version Increment Policy

Document versions follow `MAJOR.MINOR.PATCH` semantics as defined in EDS-001 §6.5 and §6.6. These rules are restated here for authorship completeness:

| Increment | Trigger |
|---|---|
| MAJOR | Any breaking change per EDS-001 §6.5 (removal, rename, semantic change, guarantee narrowing). Requires RFC. |
| MINOR | Additive non-breaking change (new section, new symbol, new test case, new metric). No RFC required; notification to consuming teams required. |
| PATCH | Non-behavioral clarification, ambiguity resolution, typographic correction, example addition. No RFC required; no notification required. |

### 23.2 What Constitutes Each Type of Change

**MAJOR changes in API:** Removal of any exported symbol; change to any parameter type, return type, or error type; removal of a default value; addition of a required parameter; narrowing of an error code set.

**MAJOR changes in RT:** Change to any observable behavior; change to concurrency guarantees; change to cache TTL or invalidation rules; change to error propagation policy; change to lifecycle order.

**MAJOR changes in SM:** Removal of any state; removal of any transition; change to the initial state; addition of a guard to a previously unguarded transition.

**MINOR changes in API:** Addition of an optional parameter with a default; addition of a new exported symbol; addition of a new error code; addition of a deprecation notice.

**MINOR changes in RT:** Description of a previously unspecified edge case without changing behavior; addition of a new error path for a newly added API method.

**PATCH changes (all types):** Correction of a typographical error; clarification of an ambiguous sentence without changing the intended behavior; addition of an example; correction of a cross-reference.

### 23.3 Version History Requirement

The Change History table (§4.9) MUST record every version. A document submitted for Specification Review without a complete Change History table is rejected at SG-01.

## 24. Freeze Policy

### 24.1 Freeze Conditions

A document MAY be frozen only when all of the following hold:

1. The document has passed all Specification Quality Gates (§21).
2. The document has been approved by the Specification Review panel.
3. The Status header reads "Under Review" and the review is complete.
4. The Change History table is current.
5. The document contains no "TBD", "TODO", or "to be specified" strings.

### 24.2 Freeze Process

1. Author updates the Status header from "Under Review" to "Frozen".
2. Author commits the frozen document to the package documentation repository.
3. Author files a release record entry (EES-001 §9.2) noting the document version.
4. The Package Owner announces the freeze to consuming teams.

### 24.3 Post-Freeze Prohibition

A frozen document MUST NOT be edited. Any change — including a typographical correction — requires:

1. A new version number (PATCH for typos, MINOR or MAJOR for substantive changes).
2. The new version going through Specification Review.
3. A new freeze.

Editing a frozen document in place, without a version increment and new review, is a governance violation logged by the Architecture Review Board and tracked as a compliance finding.

### 24.4 Supersession

When a new major version of a document is frozen, the previous version is superseded:

1. The previous version's Status header is updated to "Superseded".
2. The "Superseded by" field in the previous version's header is populated.
3. The new version's "Supersedes" field is populated with the previous version's ID.
4. The previous version is not deleted and remains accessible in the documentation repository.

## 25. Amendment Policy

### 25.1 What Requires Amendment

An amendment to ESS-001 itself is required when:

- A new document type is added to EDS-001 and a template is needed.
- A mandatory section requirement is changed for an existing document type.
- A new item is added to the Universal Checklist (§19.1).
- The scoring model (§20) is changed.
- A new quality gate (§21) is added or removed.
- A cross-reference rule (§22) is changed.

### 25.2 Amendment Process

1. File an RFC against EDS-002 (this document). The RFC comment period is 5 business days.
2. The Chief Architect reviews and approves the RFC.
3. ESS-001 is updated to a new version per §23.
4. If the amendment is to the Universal Checklist or a template, all existing frozen documents are grandfathered under their current version; only new versions produced after the amendment take effect must comply.

### 25.3 Grandfathering Rule

An amendment to ESS-001 does not retroactively invalidate frozen documents. A frozen document is compliant with the version of ESS-001 that was in effect when it was frozen. When that document is next revised, it MUST comply with the current ESS-001 version at the time of revision.

## 26. Examples of Compliant and Non-Compliant Specifications

### 26.1 Compliant: RT Method Specification

The following is a compliant excerpt from a Runtime Specification:

```markdown
### 4.3 `Registry.load(namespace: string): Promise<void>`

**Preconditions:**
1. The `Registry` instance MUST be in the `Initialized` state as defined in
   {PACKAGE}-SM-1.0.0 §3.
2. The `namespace` parameter MUST be a non-empty string.

**Postconditions:**
1. If this method resolves, the dictionary for `namespace` is available via
   `Registry.t()` for the duration of the current instance's lifetime.
2. If this method rejects, the `Registry` state is unchanged from its state
   at the time of the call.

**Success path:**
1. `Registry` checks its `CacheProvider` for an existing entry keyed by
   `{locale}:{namespace}`.
2. If a cache hit occurs, `Registry` populates its in-memory dictionary from
   the cached value and resolves. Steps 3–5 are skipped.
3. `Registry` invokes the configured `DictionaryLoader.load(namespace, locale)`.
4. `Registry` stores the returned dictionary in the `CacheProvider` with the
   key `{locale}:{namespace}`.
5. `Registry` populates its in-memory dictionary and resolves.

**Error paths:**

| Error type | Condition | State after error |
|---|---|---|
| `LoadError(code: NAMESPACE_NOT_FOUND)` | `DictionaryLoader.load` rejects with a not-found signal. | `Registry` remains in `Initialized` state. The namespace is not added to the in-memory dictionary. |
| `LoadError(code: LOADER_TIMEOUT)` | `DictionaryLoader.load` does not resolve within the timeout defined in {PACKAGE}-PERF-1.0.0 §3, row "Registry.load". | `Registry` remains in `Initialized` state. |
| `RegistryStateError` | The `Registry` is not in the `Initialized` state when this method is called. | `Registry` state is unchanged. |

**Concurrency:** This method is safe to call concurrently on the same instance.
Concurrent calls for the same `namespace` MUST be deduplicated: exactly one
loader invocation occurs. See {PACKAGE}-RT-1.0.0 §6 for the deduplication
mechanism.

**Side effects:** On success, emits the `registry.namespace.loaded` log event
defined in {PACKAGE}-OBS-1.0.0 §3.2.
```

**Why this is compliant:**
- Uses MUST/SHALL correctly throughout.
- Preconditions and postconditions are distinct.
- Success path is numbered and deterministic.
- Error path table is exhaustive and identifies exact error types and codes.
- State after error is stated for every error path.
- Concurrency is addressed.
- Side effects are documented with a citation to OBS.
- All cross-references are pinned to specific versions.

### 26.2 Non-Compliant: RT Method Specification

The following is a non-compliant excerpt of the same specification:

```markdown
### 4.3 `Registry.load`

The registry will try to load the namespace from cache first. If not found, it
calls the loader. The result is stored and returned. Errors are handled
appropriately. This method is generally thread-safe.
```

**Why this is non-compliant:**

| Violation | Rule |
|---|---|
| "will try" — not RFC 2119 vocabulary | §5.1 |
| "If not found" — ambiguous condition (not found where? under what conditions?) | SP1, §4.4 |
| "handled appropriately" — forbidden language | §4.5 |
| No parameter type or return type | §4.7 |
| No preconditions | §9.1 RT-rule |
| No postconditions | §9.1 RT-rule |
| No error path table | §9.1 RT-rule, SP7 |
| "generally thread-safe" — "generally" is forbidden; no concurrency specification | §4.5, §9.1 RT-rule |
| No cross-references | §22.1 |

### 26.3 Compliant: SM Transition Table Excerpt

```markdown
| Current state | Event | Guard | Next state | Action |
|---|---|---|---|---|
| `UNINITIALIZED` | `initialize()` called | None | `INITIALIZING` | Begin async loader setup. |
| `UNINITIALIZED` | Any other event | None | Error | Raise `RegistryStateError`. |
| `INITIALIZING` | Loader setup completes | None | `READY` | Emit `registry.initialized` log event. |
| `INITIALIZING` | Loader setup fails | None | `FAILED` | Capture error; emit `registry.init.failed` log event. |
| `INITIALIZING` | `close()` called | None | `CLOSING` | Cancel loader setup; proceed to closing. |
| `READY` | `close()` called | None | `CLOSING` | Begin async teardown. |
| `READY` | `initialize()` called | None | Ignored | — |
| `CLOSING` | Teardown completes | None | `CLOSED` | Release all resources. |
| `CLOSED` | Any event | None | Ignored | — |
```

**Why this is compliant:** Every (state, event) pair is present. "Ignored" and "Error" dispositions are explicit. Guards are stated ("None" where no guard). Actions are stated.

| From | Event | To |
|---|---|---|
| UNINITIALIZED | init | INITIALIZING |
| INITIALIZING | success | READY |
| READY | close | CLOSED |
```

### 26.5 Compliant: API Method Signature

```markdown
### 6.4 `Registry.t`
```typescript
t(key: string, variables?: Record<string, string | number>): string
```

| Parameter | Type | Required | Default | Description |
|---|---|---|---|---|
| `key` | `string` | Yes | — | Dot-notation lookup key of the form `namespace.path.to.value`. |
| `variables` | `Record<string, string \| number>` | No | `{}` | Interpolation variables substituted into the returned string. |

**Return value:** The translated string for `key` in the current locale, with `variables` interpolated. If `key` is not found, returns `key` unchanged. See {PACKAGE}-RT-1.0.0 §4.5 for the complete behavioral specification.

**Throws:**

| Error type | Condition |
|---|---|
| `KeyFormatError` | `key` does not match the pattern `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)+$`. |
```
