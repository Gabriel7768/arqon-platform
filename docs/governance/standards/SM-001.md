## 1. Purpose

SM-001 governs **how every State Machine Specification (SM) document is
written**. It does NOT define any package's state machine. It defines the
structure, mandatory tables, notation, and validation that every State Machine
Spec MUST inherit.

SM-001 is the parent standard for state-machine-bearing packages such as
`packages/i18n` (locale loading lifecycle), `packages/auth` (session
lifecycle), `packages/billing` (payment lifecycle), `packages/events`, etc.

### 1.1 Relationship

| Document | Relationship |
|---|---|
| Architecture Spec | Defines what has state; SM defines the states |
| Public API Spec (API-001) | Symbols that change state cite SM transition rows |
| Runtime Spec (RT-001) | Cites SM transitions caused by runtime events |
| Security Spec (SEC-001) | State transitions may be guarded by SEC requirements |

---

## 2. Scope

### 2.1 In scope
- States and their meanings
- Transitions between states
- Guards (conditions for a transition)
- Actions (effects of a transition)
- Invariants per state
- Initial and terminal states
- Hierarchical/nested states (if applicable)
- Concurrent regions (if applicable)

### 2.2 Out of scope (owning document)
- How transitions are executed at runtime → Runtime Spec (RT-001)
- Public signatures that trigger transitions → Public API Spec (API-001)
- Authn/authz of who may trigger → Security Spec (SEC-001)
- Persistence schema → Data Model Spec
- Observability of transitions → Observability Spec (OBS-001)

---

## 3. Mandatory Document Structure

An SM document inherits ESS-001 §3 (§1–§9) and adds:

| § | Section | Purpose |
|---|---|---|
| 10 | State inventory | Every state listed and defined |
| 11 | State table | Per-state properties |
| 12 | Transition table | Every legal transition |
| 13 | Guard table | Conditions gating transitions |
| 14 | Action table | Effects of transitions |
| 15 | Invariant table | Per-state and global invariants |
| 16 | Lifecycle map | Initial → ... → terminal |
| 17 | Notation & diagrams | How states/transitions are drawn |

---

## 4. Mandatory Tables

### 4.1 State table

| State ID | Name | Meaning | Type | Entry action | Exit action |
|---|---|---|---|---|---|

- **Type** = initial / normal / terminal / error.

### 4.2 Transition table

| Transition ID | From | To | Trigger | Guard | Action | Side effect |
|---|---|---|---|---|---|---|

- Every transition has a stable ID so Runtime/API specs can cite it (e.g.,
  `T-03`).

### 4.3 Guard table

| Guard ID | Transition | Condition | Failure result |
|---|---|---|---|

### 4.4 Action table

| Action ID | Transition | Effect | Idempotent? | Side effect |
|---|---|---|---|---|

### 4.5 Invariant table

| Invariant ID | Scope (state/global) | Property | Testable as |
|---|---|---|---|

---

## 5. Notation Rules

- States are `UPPER_SNAKE` IDs (e.g., `LOADING`, `READY`).
- Transitions are `T-NN` with a verb phrase name (e.g., `T-03 load-complete`).
- Guards are `G-NN`; actions are `A-NN`.
- Diagrams use a Mermaid `stateDiagram-v2` block as the canonical visual.
- The table is normative; the diagram is informative. On conflict, the table wins.

## 7. Domain-Specific Rules

| Rule | Statement |
|---|---|
| SM-R1 State completeness | Every state reachable in the system MUST appear in the state table. |
| SM-R2 Transition completeness | Every legal transition MUST appear in the transition table. Undocumented transitions are defects. |
| SM-R3 Determinism | For a given (state, trigger, guard-result), exactly one transition applies. No ambiguity. |
| SM-R4 Initial state | Exactly one initial state MUST be declared. |
| SM-R5 Terminal states | Terminal states MUST be marked; no transitions leave them. |
| SM-R6 Guard explicitness | Every transition with a condition MUST have a guard row; condition MUST be testable. |
| SM-R7 Action idempotency | Actions MUST declare whether they are idempotent. |
| SM-R8 Invariant testability | Every invariant MUST be testable. |
| SM-R9 No orphan transitions | Every transition's From and To MUST exist in the state table. |
| SM-R10 Citation stability | Transition IDs are stable; renumbering is a Major change requiring ADR. |

## 8. Validation Framework

### Universal — from EDS-001 + EES-001 + ESS-001.
### Structural (SM-S)

| ID | Check | Pass/Fail |
|---|---|---|
| SM-S01 | State inventory present | ☐ |
| SM-S02 | State table present | ☐ |
| SM-S03 | Transition table present | ☐ |
| SM-S04 | Guard table present | ☐ |
| SM-S05 | Action table present | ☐ |
| SM-S06 | Invariant table present | ☐ |
| SM-S07 | Lifecycle map present | ☐ |
| SM-S08 | Mermaid diagram present (informative) | ☐ |

### Content (SM-C)

| ID | Check | Pass/Fail |
|---|---|---|
| SM-C01 | Exactly one initial state | ☐ |
| SM-C02 | Terminal states marked | ☐ |
| SM-C03 | Every transition has From/To in state table | ☐ |
| SM-C04 | Every guarded transition has a guard row | ☐ |
| SM-C05 | Every action declares idempotency | ☐ |
| SM-C06 | Every invariant testable | ☐ |
| SM-C07 | Transition IDs unique and stable | ☐ |
| SM-C08 | Determinism: no overlapping (state,trigger) without disambiguating guard | ☐ |

### Consistency (SM-X)

| ID | Check | Pass/Fail |
|---|---|---|
| SM-X01 | RT state-changing methods cite transition IDs | ☐ |
| SM-X02 | API state-changing symbols cite transition IDs | ☐ |
| SM-X03 | Guards referencing SEC requirements are consistent | ☐ |
| SM-X04 | No transition leaves a terminal state | ☐ |
| SM-X05 | Diagram consistent with tables | ☐ |
