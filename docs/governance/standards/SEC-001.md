## 1. Purpose

SEC-001 governs **how every Security Specification (SEC-xxx) document is
written**. It does NOT define the security controls of any package. It defines
the structure, mandatory tables, notation, and validation that every Security
Spec MUST inherit.

SEC-001 is the parent standard for security specs such as `I18N-SEC-1.0.0`,
`AUTH-SEC-1.0.0`, `BILL-SEC-1.0.0`, etc.

### 1.1 Relationship

| Document | Relationship |
|---|---|
| Architecture Spec | Defines the surface; SEC defines how it is protected |
| Public API Spec (API-001) | Auth-touching symbols cite SEC requirements |
| Runtime Spec (RT-001) | Enforcement points cite SEC requirements |
| State Machine Spec (SM-001) | Guards MAY cite SEC requirements |
| Adapter Spec (ADAPT-001) | Adapters handling secrets/sessions cite SEC |

---

## 2. Scope

### 2.1 In scope
- Authentication (authn) — who is the caller
- Authorization (authz) — what may the caller do
- Secrets management — keys, tokens, webhook secrets
- Threat model — assets, actors, threats, mitigations
- Input validation / injection defense (at the security boundary)
- Webhook verification
- Data protection — what is sensitive, how it is handled
- Rate limiting / abuse prevention (security-relevant)

### 2.2 Out of scope (owning document)
- Public signatures → Public API Spec (API-001)
- Execution flows → Runtime Spec (RT-001)
- States/transitions → State Machine Spec (SM-001)
- Performance SLOs → Performance Spec
- Observability schema → Observability Spec (OBS-001)
- Deployment topology → Deployment Spec (DEPLOY-001)

---

## 3. Mandatory Document Structure

A Security Spec inherits ESS-001 §3 (§1–§9) and adds:

| § | Section | Purpose |
|---|---|---|
| 10 | Threat model | Assets, actors, trust boundaries, threats, mitigations |
| 11 | Authentication surface | How callers prove identity |
| 12 | Authorization surface | What each identity may do |
| 13 | Secrets contract | Which secrets exist, who holds them, rotation |
| 14 | Input validation & injection | Security-boundary validation requirements |
| 15 | Webhook verification | How inbound webhooks are authenticated |
| 16 | Data protection | Sensitive data classification and handling |

---

## 4. Mandatory Tables

### 4.1 Threat model table

| Threat ID | Asset | Actor | Trust boundary | Threat | Mitigation | Residual risk |
|---|---|---|---|---|---|---|

### 4.2 Authentication surface table

| Operation | Authn method | Credential | Held by | Failure result |
|---|---|---|---|---|

### 4.3 Authorization surface table

| Operation | Required identity | Required permission | Decision | Deny result |
|---|---|---|---|---|

### 4.4 Secrets contract table

| Secret ID | Purpose | Held by (host) | Rotation | Leak handling | Env var |
|---|---|---|---|---|---|

- Secrets MUST NOT appear in code or VCS (per EDS-001 §9).
- Each secret maps to an env var name; values never committed.
- Rotation policy MUST be stated (even if "manual, on incident").

### 4.5 Input validation table

| Input | Source | Validation | On invalid | Injection class defended |
|---|---|---|---|---|

### 4.6 Webhook verification table

| Inbound webhook | Verification method | On mismatch | Idempotency key |
|---|---|---|---|

### 4.7 Data classification table

| Data element | Classification | At rest | In transit | Retention |
|---|---|---|---|---|

- Classification: public / internal / confidential / restricted.

---

## 5. Notation Rules

- Threat IDs are `TH-NN`; requirements are `SEC-RNN`.
- Credential types are named (e.g., `bearer-api-key`, `webhook-secret`).
- Secrets are referenced ONLY by their env var name, never by value.

## 7. Domain-Specific Rules

| Rule | Statement |
|---|---|
| SEC-R1 Threat model present | Every package handling sensitive data MUST have a threat model. |
| SEC-R2 Secrets never in code | No secret value in source or VCS; env var names only. |
| SEC-R3 Rotation stated | Every secret MUST state a rotation policy. |
| SEC-R4 Authn explicit | Every protected operation MUST state its authn method. |
| SEC-R5 Authz explicit | Every protected operation MUST state required permission. |
| SEC-R6 Input validation at boundary | Every external input MUST be validated at the trust boundary. |
| SEC-R7 Webhook verification | Every inbound webhook MUST be verified (secret/signature). |
| SEC-R8 Idempotency for webhooks | Webhook processing MUST be idempotent by event id. |
| SEC-R9 Data classification | Every data element MUST be classified. |
| SEC-R10 Leak response | Every secret MUST state leak-handling (revoke + rotate). |
| SEC-R11 No plaintext secrets in logs | Secrets MUST NOT be logged. |
| SEC-R12 Fail closed | On authn/authz failure, deny by default. |
