## 1. Purpose

EES-001 defines **how engineering work is performed** across the ARQON
Platform. It is the operational counterpart to EDS-001, which defines how
engineering knowledge is documented.

- EDS-001 governs **documentation.**
- EES-001 governs **execution.**

Together they form the complete engineering governance model for a platform
developed by multiple independent teams over a decade.

EES-001 does NOT define APIs, runtime behavior, or package contracts. It
defines the lifecycle, workflow, roles, quality gates, and release governance
that produce them.

---

## 2. Software Engineering Lifecycle

Every unit of engineering work passes through these stages. A stage may be
trivially short for a small change, but it MUST NOT be skipped.

| # | Stage | Output | Gate |
|---|---|---|---|
| 1 | Idea | One-paragraph problem statement | — |
| 2 | Discovery | Notes, constraints, options | — |
| 3 | RFC | RFC document (Tier D) | RFC review |
| 4 | Architecture review | Decision recorded | Architecture review |
| 5 | ADR creation | ADR-NNN (Tier B) | ADR accepted |
| 6 | Specification writing | Specs (Tier C) per SPD | Spec freeze |
| 7 | Implementation | Source code | Code review |
| 8 | Code review | Approved merge | Reviewer sign-off |
| 9 | Testing | Test evidence | Testing gate |
| 10 | Validation | Integration evidence | Validation gate |
| 11 | Release | Tagged release | Release approval |
| 12 | Deployment | Deployed artifact | Deploy gate |
| 13 | Monitoring | Metrics/logs baseline | Observability check |
| 14 | Maintenance | Patches | Maintenance review |
| 15 | Deprecation | Deprecation notice + migration guide | Deprecation gate |
| 16 | Removal | Removed artifact | Removal gate |

A change MAY collapse stages (e.g., a one-line fix skips RFC/ADR), but the
collapsing MUST be explicit and justified by the change's classification
(§4). Silent skipping is forbidden.

## 3. Engineering Workflow

### 3.1 Responsibilities per stage

| Stage | Responsible role | Required artifacts |
|---|---|---|
| RFC | Author | RFC doc |
| Architecture review | Principal Architect | ADR |
| Spec writing | Package Owner | Specs + governing standard citation |
| Implementation | Senior Engineer / Staff | Source + tests |
| Code review | Reviewer | Review record |
| Testing | Engineer | Test report |
| Release | Release Manager | Tag, changelog |
| Deployment | Release Manager | Deploy record |
| Monitoring | On-call | Runbook |

### 3.2 Ownership transitions

Ownership transfers explicitly at each gate. The previous owner is no longer
accountable after transfer; the next owner is. There is no implicit "it's
someone's job" — at every moment exactly one role owns the work.

### 3.3 Decision points

- **Go/No-Go after RFC:** does this need an ADR, or is it implementation-only?
- **Freeze after spec:** are all mandatory specs Frozen? If not, no implementation.
- **Release-ready:** all gates passed? If not, no release.

---

## 4. Change Classification

A change is classified to determine which stages apply. Classification is
recorded in the PR/commit.

| Class | Examples | Requires ADR | Requires spec update |
|---|---|---|---|
| Architectural | New package, boundary change, new host | Yes | Yes |
| Breaking API | Signature change, removed export | Yes | Yes |
| Runtime change | Flow, lifecycle, concurrency | Yes (if breaking) | Yes |
| Security change | Auth, secrets, threat surface | Yes | Yes |
| Performance change | SLO change | Yes (if breaking) | Yes |
| Implementation-only | Internal refactor, no contract change | No | No |

---

## 5. Package Lifecycle

A package moves through these phases:

| Phase | Entry criterion | Exit criterion |
|---|---|---|
| Proposal | RFC accepted | ADR accepted |
| Approval | ADR accepted | SPD exists |
| Implementation | All mandatory specs Frozen | Code review passed + tests green |
| Stabilization | First release candidate | Stabilized release |
| Production | Stabilized release deployed | — |
| Maintenance | In production | Deprecation announced |
| Deprecation | Deprecation ADR | Migration guide complete |
| Archival | Migration guide complete | Removed from active set |

Implementation MUST NOT begin until every mandatory specification for the
package reaches Frozen status (per the package's SPD).

## 6. Engineering Roles

| Role | Responsibility | Authority | Decision scope |
|---|---|---|---|
| Founder | Product direction, freeze authority | Final freeze sign-off | Product/business |
| CTO | Technology strategy, standards ownership | Technical sign-off | All technical |
| Principal Architect | Architecture, ADRs | Approve/reject architecture | Architecture |
| Staff Engineer | Cross-cutting design, specs | Approve specs | Spec-level |
| Senior Engineer | Implementation | Author code + tests | Implementation |
| Package Owner | Owns a package's specs and roadmap | Triage, prioritize | Their package |
| Reviewer | Code/spec review | Block merge | Review scope |
| Release Manager | Releases and deploys | Approve/release | Release |

A person may hold multiple roles; the responsibilities do not.

## 7. Quality Gates

These gates MUST pass before a package can be released.

| Gate | Checks |
|---|---|
| Architecture review | Module boundaries, dependency graph, ADR exists |
| API review | Public API Spec frozen, OpenAPI contract matches |
| Runtime review | Runtime Spec frozen, flows complete |
| Security review | Security Spec frozen, no secrets in code |
| Performance review | SLOs defined (if applicable) |
| Testing review | Test Spec satisfied, coverage targets met |
| Documentation review | Specs Frozen, `.env.example` present, runbook exists |

## 8. Release Governance

### 8.1 Semantic versioning

Packages follow semver. Document versions follow semver independently (per
EDS-001 §7.4).

- **Major:** breaking contract change.
- **Minor:** backward-compatible capability.
- **Patch:** backward-compatible fix.

### 8.2 Release approval workflow

1. Release Manager proposes a release with a changelog.
2. CTO (or delegate) approves.
3. Tag created.
4. Deploy proceeded per Deployment Spec.

### 8.3 Rollback policy

Every release MUST have a documented rollback path. If rollback is not
possible, the release is flagged as high-risk and requires explicit CTO
approval.

### 8.4 Hotfix workflow

A hotfix bypasses RFC/ADR at proposal but MUST create a retroactive ADR
within one release cycle documenting the decision.

### 8.5 Emergency changes

Emergency changes may proceed without full review, but the change MUST be
flagged and reviewed within 48 hours.

## 9. Engineering Principles

1. **Contracts before code.** No implementation without a Frozen spec.
2. **One owner per topic.** (From EDS-001 §5.)
3. **Frozen means frozen.** Mutate only via ADR.
4. **Smallest reversible step.** Prefer small, independently shippable changes.
5. **Value over completeness.** Ship a thin slice over finishing every spec.
6. **Evidence over assertion.** Gates pass on evidence, not claims.
7. **Reversibility.** Every release has a rollback path.
8. **No secrets in code.** (From EDS-001 §9.)
9. **Scoped imports only.** (From EDS-001 §6.)
10. **Honest status.** A "Frozen" claim requires a commit; chat history is not freeze.
