## 1. Purpose

ESS-001 defines **how every package specification (Tier C) is structured**.
Where EDS-001 defines the documentation hierarchy and EES-001 defines
execution, ESS-001 defines the canonical form that a specification document
itself MUST take so that it is deterministic, reviewable, and freezable.

ESS-001 does NOT define any package's behavior. It defines the structure that
every Architecture Spec, API Spec, Runtime Spec, State Machine Spec, etc. MUST
inherit.

Specialized standards (API-001, RT-001, SM-001, ADAPT-001, SEC-001) add
discipline-specific sections on top of this base structure. ESS-001 is the
common skeleton they all extend.

## 3. Mandatory Document Structure

Every package specification MUST contain the following sections in this
canonical order. Specialized standards MAY append additional sections after
§9, but MUST NOT reorder or omit these.

| § | Section | Purpose |
|---|---|---|
| 1 | Metadata header | ID, version, status, owners, derives-from, frozen-at |
| 2 | Purpose | What this spec defines; what it does NOT define |
| 3 | Scope | In-scope behaviors; explicitly out-of-scope behaviors with owning document |
| 4 | Definitions | Domain terms used normatively |
| 5 | Contract | The normative content (signatures, flows, states, tables) — the body |
| 6 | Dependencies | Upstream specs/standards/ADRs this spec references |
| 7 | Invariants | Properties that MUST always hold |
| 8 | Non-compliance & remediation | What violation means; how it is fixed |
| 9 | Validation | Checklist + quality gates specific to this spec |
| 10+ | Discipline-specific extensions | Per the governing specialized standard (API-001, RT-001, …) |

### 3.1 Normative statement rules

- Statements use RFC 2119 keywords: **MUST**, **MUST NOT**, **SHOULD**,
  **SHOULD NOT**, **MAY**.
- Every MUST has a corresponding validation checklist item.
- No prose-only obligations: if it is normative, it is checkable.

---

## 4. Scope Discipline

§3 of every spec MUST contain two parallel lists:

1. **In scope** — behaviors this spec owns (per EDS-001 §5 topic ownership).
2. **Out of scope** — behaviors that belong elsewhere, each annotated with the
   owning document.

This is the mechanism that enforces EDS-001's single-source-of-truth rule at
the spec level. A spec that fails to declare an out-of-scope topic is
ambiguous about ownership.

---

## 5. The Contract Section (§5)

The contract section is the normative heart. Its form depends on spec type:

| Spec type | Contract form |
|---|---|
| Architecture Spec | Module boundaries, dependency graph, responsibility matrix |
| Public API Spec | Signature table, parameter/return semantics, error table |
| Runtime Spec | Flow descriptors, lifecycle phases, concurrency model |
| State Machine Spec | State table, transition table, guard table, invariant table |
| Security Spec | Threat model, authn/authz surface, secrets contract |
| Adapter Spec | Adapter interface, mapping table, lifecycle hooks |

Every contract element MUST be expressed in a table or a numbered flow — never
in unstructured prose alone. Tables are the anti-entropy device: they force
completeness and make review deterministic.

---

## 6. Dependency Declaration

§6 MUST list every upstream document this spec references, by ID. The set of
dependencies MUST form a directed acyclic graph (per EDS-001 §7.1). A spec
MUST NOT reference a downstream document (one that depends on it).

---

## 7. Invariants

§7 lists invariants — properties that MUST hold in every state and every flow.
Invariants are the strongest form of contract: violating one is a defect, not
a preference. Each invariant MUST be testable.

---

## 8. Non-compliance & Remediation

§8 defines:
- What constitutes a violation of this spec.
- The remediation path (which gate fails, who is responsible, timeline).
- Whether a violation blocks release.

---

## 9. Validation

§9 contains:
- A **checklist** of binary pass/fail items, each with a responsible party.
- **Quality gates** — conditions that MUST hold to freeze the spec.

Every MUST in §5/§7 MUST have a corresponding checklist item. This is the
traceability rule: no obligation without a check.

---

## 10. Versioning

Package specs follow semantic versioning, independent of package code versions
(per EDS-001 §7.4).

- **Major:** breaking contract change (requires ADR).
- **Minor:** backward-compatible addition.
- **Patch:** clarification, no new obligation.

A spec is `Frozen` only when committed to `docs/` and marked Frozen in
INDEX.md. A Frozen spec changes only via ADR.

| ID | Check | Pass/Fail |
|---|---|---|

| SS-06 | Dependencies listed by ID, acyclic (§6) | ☐ |
| SS-07 | Invariants present and each testable (§7) | ☐ |
| SS-08 | Non-compliance & remediation defined (§8) | ☐ |
| SS-09 | Every MUST has a matching checklist item (§9) | ☐ |
| SS-10 | Spec cites its governing specialized standard | ☐ |
| SS-11 | Spec cites the authorizing ADR | ☐ |
| SS-12 | Spec is in `docs/` and marked Frozen before being called Frozen | ☐ |
