## 1. Purpose of a Technical Standard

A Technical Standard is a Tier-A document (per EDS-001 §3) that defines **how**
a class of specifications is written. It does NOT define what any package does.

A Technical Standard solves:
- **Structural entropy** — every spec of a class looks the same, so reviewers
  know where to look.
- **Terminology drift** — shared terms mean the same thing across specs.
- **Validation inconsistency** — every spec is checked the same way.
- **Versioning chaos** — every spec evolves under one model.

### 1.1 Relationship

| Document | Relationship to a Technical Standard |
|---|---|
| EDS-001 | Provides the hierarchy; a Technical Standard is Tier A |
| EES-001 | Provides execution gates that act on specs governed by standards |
| ESS-001 | Provides the base spec structure a Technical Standard extends |
| ADRs | Authorize a standard's creation or major change |
| Package Specs | Conform to their governing Technical Standard |

### 1.2 Standards governed by TS-001

TS-001 is the parent of: API-001, RT-001, SM-001, SEC-001, PERF-001 (future),
TEST-001 (future), OBS-001 (future), DEPLOY-001 (future), ADAPT-001. Every
future Technical Standard MUST inherit TS-001.

## 2. Mandatory Document Structure

Every Technical Standard MUST contain these sections in this canonical order.
This mirrors ESS-001 (because a standard is itself a specification of how to
write specifications) and adds standard-specific content.

| § | Section | Purpose |
|---|---|---|
| 1 | Metadata header | ID, version, status, owners, derives-from, frozen-at |
| 2 | Purpose | What this standard governs; what it does NOT govern |
| 3 | Scope | In-scope behaviors; out-of-scope with owning document |
| 4 | Shared terminology | Terms used normatively in this standard |
| 5 | Mandatory document structure | Canonical structure inherited by every spec of this class |
| 6 | Mandatory tables | Tables every spec of this class MUST contain |
| 7 | Notation rules | How flows, states, signatures are written |
| 8 | Cross-reference rules | What this standard's specs MAY/MUST reference |
| 9 | Domain-specific rules | Discipline-specific obligations |
| 10 | Validation framework | Checklist + quality gates |
| 11 | Examples policy | Normative/informative/counterexample rules |
| 12 | Versioning | How this standard and its specs version |
| 13 | Change history | — |

A standard MUST NOT omit any of §1–§10. It MAY extend §9 with additional
domain rules.

## 3. Shared Terminology

These terms are normative across every Technical Standard and every spec.

| Term | Definition |
|---|---|
| Normative Requirement | A MUST/MUST NOT obligation; violation is a defect |
| Recommendation | A SHOULD/SHOULD NOT; violation requires justification |
| Constraint | A boundary a spec MUST operate within |
| Invariant | A property that MUST always hold; testable |
| Compliance | A spec meets all applicable normative requirements |
| Validation Rule | A binary check (pass/fail) with a responsible party |
| Quality Gate | A condition that MUST hold to freeze |
| Implementation Note | Informative guidance, non-normative |
| Example | Illustrative; normative examples are marked as such |
| Anti-pattern | A pattern a spec MUST NOT describe |
| Extension Point | A place where a spec MAY add discipline-specific content |
| Compatibility Rule | What changes are backward compatible |
| Deprecation Rule | How an obligation is retired |
| Review Rule | Who reviews what |
| Approval Rule | Who signs off what |

## 4. Versioning Model

Technical Standards and the specs they govern follow semantic versioning.

| Change | Standard version | Spec version |
|---|---|---|
| New optional section | Minor | unaffected |
| New mandatory obligation | Major | specs MUST re-conform |
| Clarification, typo | Patch | unaffected |
| Supersession | New ID | specs migrate to citing new ID |

### 4.1 Backward compatibility

A Minor or Patch change MUST NOT break a conforming spec. A Major change
breaks conformance and requires specs to be updated and re-frozen in the same
change set (per EDS-001 §7.3).

### 4.2 Freeze policy

A standard is Frozen when committed to `docs/governance/standards/` and marked
Frozen in INDEX.md. A Frozen standard changes only via ADR. After freeze, only
Patch clarifications may land without an ADR; Minor/Major require an ADR.

---

## 5. Validation Framework

Every Technical Standard MUST define a validation framework inherited by its
specs:

1. **Universal checks** — from EDS-001 §10 (U-01..U-10) and EES-001 §10.
2. **Structural checks** — from ESS-001 §11 (SS-01..SS-12).
3. **Standard-specific structural checks** — e.g., RT-S-NN for RT-001.
4. **Content checks** — discipline-specific, e.g., RT-C-NN.
5. **Consistency checks** — cross-document, e.g., RT-X-NN.

Every check is binary (pass/fail) and names a responsible party. A spec is
freezable only when all applicable checks pass.

### 5.1 Completeness scoring

A spec reports its checklist result as a fraction (e.g., 37/37). A spec with
any Fail is NOT freezable. There is no partial freeze.

### 5.2 Quality gates

Each standard defines quality gates (e.g., RTG-NN). A gate may require a
co-sign from another document's owner (e.g., an RT spec's error paths must be
co-signed by the TEST document owner).

### 5.3 Audit expectations

A Frozen spec is auditable: any reviewer can re-run the checklist against the
committed document and reach the same pass/fail.

## 6. Cross-Reference Rules

### 6.1 What a Technical Standard's specs MAY reference

| Reference | Allowed? |
|---|---|
| The governing standard | MUST |
| Authorizing ADR | MUST |
| EDS-001, EES-001, ESS-001, TS-001 | MAY |
| Other specs (upstream only, by ID) | MAY |
| Implementation Notes | MAY (informative) |

### 6.2 Forbidden references

| Reference | Forbidden? | Reason |
|---|---|---|
| Downstream specs | Yes | creates a cycle |
| Inline-copied content from another doc | Yes | violates single source of truth |
| Tribal knowledge / chat history | Yes | not version controlled |

### 6.3 Cycle prevention

The reference graph MUST be acyclic. Each standard declares its derivation
order; a spec MUST NOT reference a document that derives from it.

---

## 7. Extension Mechanism

A future Technical Standard extends TS-001 by:
1. Citing TS-001 as `derives-from`.
2. Inheriting §2 structure and §3 terminology.
3. Adding its §6 tables, §9 domain rules, §10 checks.

A standard MUST NOT duplicate rules already in TS-001/EDS-001/ESS-001; it
references them. This keeps the meta-layer DRY.

## 9. Compliance Rules

- **Compliant:** a standard/spec passes all applicable checklist items and is
  in git.
- **Non-compliant:** any Fail, OR not in git, OR a Frozen doc mutated without ADR.
- **Remediation:** the responsible party fixes the failing item; if structural,
  an ADR may be required.

---

## 10. Freeze Policy

- A standard is Frozen at first commit to `docs/governance/standards/` with
  status Frozen in INDEX.md.
- After freeze: Patch without ADR; Minor/Major with ADR.
- Supersession: a new standard ID supersedes the old; the old is marked
  `Superseded by <NEW-ID>`, never deleted.
