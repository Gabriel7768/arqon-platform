## 1. Purpose

API-001 governs **how every Public API Specification is written**. It does NOT
define any package's API. It defines the structure, mandatory tables, notation,
and validation that every Public API Spec MUST inherit.

ARQON is OpenAPI-first: the source of truth for API shapes is
`lib/api-spec/openapi.yaml`, from which Orval generates TanStack Query hooks
and Zod schemas. API-001 governs how the API Spec *document* describes and
constrains that contract.

---

## 2. Scope

### 2.1 In scope
- Public interface signatures (functions, hooks, classes, endpoints)
- Parameter semantics (name, type, meaning, ownership, lifecycle)
- Return semantics (type, meaning, nullability, ownership)
- Error contracts (thrown/returned errors, codes, meanings)
- Versioning of public interfaces
- Deprecation of public interfaces

### 2.2 Out of scope (owning document)
- Execution flows → Runtime Spec (RT-001)
- States/transitions → State Machine Spec (SM-001)
- Internal algorithms → Runtime Spec
- Authn/authz enforcement → Security Spec (SEC-001)
- Performance SLOs → Performance Spec
- Adapter wiring → Adapter Spec (ADAPT-001)

---

## 3. Shared Terminology

Inherits TS-001 §3. Additional:

| Term | Definition |
|---|---|
| Public symbol | An exported function/class/hook/endpoint usable by callers outside the package |
| Stable API | A public symbol whose contract is versioned and may only change via semver |
| Experimental API | A public symbol marked experimental; may change without major bump |
| Throws | An error a function may produce, documented in the error table |
| Contract owner | The package that owns the symbol's definition |

---

## 4. Mandatory Document Structure

A Public API Spec inherits ESS-001 §3 (§1–§9) and adds:

| § | Section | Purpose |
|---|---|---|
| 10 | Symbol inventory | Every public symbol listed |
| 11 | Signature table | Per-symbol full signature |
| 12 | Parameter table | Per-parameter semantics |
| 13 | Return table | Per-symbol return semantics |
| 14 | Error table | Per-symbol thrown/returned errors |
| 15 | Lifecycle & ownership table | Per-symbol lifecycle, ownership transfer |
| 16 | Versioning & deprecation | Per-symbol version, deprecation status |
| 17 | OpenAPI mapping | How HTTP endpoints map to symbols |

## 5. Mandatory Tables

### 5.1 Signature table

| Symbol | Kind | Signature | Stability | Since |
|---|---|---|---|---|

### 5.2 Parameter table

| Symbol | Parameter | Type | Nullable | Meaning | Ownership | Default |
|---|---|---|---|---|---|---|

- **Ownership** = caller-owned / callee-owned / transferred (per RT-001 resource
  ownership rules).

### 5.3 Return table

| Symbol | Return type | Nullable | Meaning | Ownership |
|---|---|---|---|---|

### 5.4 Error table

| Symbol | Error | Code/Type | Meaning | Recoverable | State-after-error |
|---|---|---|---|---|---|

- **Recoverable** = can the caller retry and succeed?
- **State-after-error** = what state is the system in after this error?
- This table MUST be consistent with the Runtime Spec's error path table
  (cross-document consistency check API-X-01).

### 5.5 Lifecycle & ownership table

| Symbol | Created by | Destroyed by | Ownership | Side effects |
|---|---|---|---|---|

### 5.6 OpenAPI mapping table (HTTP APIs only)

| Endpoint | Method | Symbol | Request schema | Response schema | Error codes |
|---|---|---|---|---|---|

## 6. Notation Rules

- Signatures use TypeScript syntax (the platform language).
- Types reference the package's exported type aliases, never inline-anonymous.
- Error codes are stable strings/HTTP status; never magic numbers undocumented.
- Nullability is explicit (`T | null`), never implied.

---

## 7. Cross-Reference Rules

| Reference | Rule |
|---|---|
| Runtime Spec | MUST: every symbol with runtime behavior cites RT §flow |
| State Machine Spec | MUST: every state-changing symbol cites SM transition row |
| Security Spec | MUST: every symbol touching authn/authz cites SEC requirement |
| Adapter Spec | MAY: if symbol is adapter-exposed |
| OpenAPI yaml | MUST: HTTP symbols cite the `operationId` |

---

## 8. Domain-Specific Rules

| Rule | Statement |
|---|---|
| API-R1 Completeness | Every public symbol MUST appear in the signature table. |
| API-R2 Error exhaustiveness | The error table MUST list every error a symbol can produce. |
| API-R3 Stability marking | Every symbol MUST be marked Stable or Experimental. |
| API-R4 Ownership explicit | Every parameter/return with resource semantics MUST declare ownership. |
| API-R5 Nullability explicit | No implicit nullability. |
| API-R6 Deprecation path | Deprecated symbols MUST cite replacement and removal version. |
| API-R7 OpenAPI parity | The OpenAPI yaml MUST match the signature/error tables (codegen parity). |
| API-R8 No undocumented errors | An error thrown in code but absent from the table is a defect. |

## 9. Validation Framework

### Universal — from EDS-001 §10 + EES-001 §10.
### Structural (API-S) — from ESS-001 §11 (SS-01..SS-12).
### Content (API-C)

| ID | Check | Pass/Fail |
|---|---|---|
| API-C01 | Every public symbol in inventory | ☐ |
| API-C02 | Every symbol has a signature row | ☐ |
| API-C03 | Every parameter has semantics | ☐ |
| API-C04 | Every return has semantics | ☐ |
| API-C05 | Every error listed and recoverable/state-after-error filled | ☐ |
| API-C06 | Every symbol marked Stable/Experimental | ☐ |
| API-C07 | Ownership declared where applicable | ☐ |
| API-C08 | Nullability explicit everywhere | ☐ |
| API-C09 | Deprecated symbols have replacement + removal version | ☐ |

### Consistency (API-X)

| ID | Check | Pass/Fail |
|---|---|---|

## 11. Examples Policy

- **Normative example:** shows the required signature form; marked `Normative`.
- **Informative example:** illustrates usage; marked `Informative`.
- **Counterexample:** shows a forbidden form; marked `Anti-pattern`.
- Examples MUST NOT introduce obligations not in the tables.

---

## 12. Versioning

Inherits TS-001 §4. A public symbol's `Since` version is recorded. A breaking
change to any symbol is a Major bump of the spec AND the package, requiring an
ADR.
