## 1. Purpose

RT-001 governs **how every Runtime Specification (RT) document is written**.
It does NOT define the runtime behavior of any package. It defines how runtime
behavior MUST be specified.

Every Runtime Specification (`RT-xxx`) in the platform MUST conform to RT-001.
Examples: `packages/i18n`, `packages/auth`, `packages/events`, `packages/config`,
`packages/logger`, `packages/cache`, `packages/billing`.

### 1.1 Relationship to other documents

| Document | Relationship |
|---|---|
| Architecture Spec | Defines module boundaries; RT defines execution within them |
| Public API Spec (API-001) | Defines what is called; RT defines how it runs |
| State Machine Spec (SM-001) | Defines states; RT cites SM transitions caused by runtime events |
| Security Spec (SEC-001) | Defines controls; RT cites SEC requirements at enforcement points |
| Implementation | Realizes the RT; deviations are defects |
| Testing Spec | Verifies RT postconditions and error paths |

## 3. Mandatory Document Structure

An RT document inherits ESS-001 §3 (§1–§9) and adds the following mandatory
sections in this fixed canonical order. Section numbers are stable: §5 always
means Method Behaviors, §6 always means Concurrency Model, etc.

| § | Section |
|---|---|
| 1 | Metadata header |
| 2 | Purpose |
| 3 | Runtime Scope |
| 4 | Definitions |
| 5 | Method Behaviors |
| 6 | Concurrency Model |
| 7 | Caching Behavior |
| 8 | Lifecycle Phases |
| 9 | Error Propagation Policy |
| 10 | Background Tasks |
| 11 | Resource Ownership |
| 12 | Retry Policy |
| 13 | Cancellation Contract |
| 14 | Fallback Chain |
| 15 | Validation & Quality Gates |

This fixed ordering makes every RT document structurally navigable without
reading it first.

## 4. Definitions

Inherits TS-001 §3. Additional:

| Term | Definition |
|---|---|
| Runtime flow | A numbered sequence of steps from trigger to postcondition |
| Lifecycle phase | A named phase (construction, init, steady, shutdown, disposal, restart, recovery) |
| Background task | A unit of work executing outside a request lifecycle |
| In-flight dedup | Collapsing concurrent identical operations into one |
| Memory visibility | Guarantee that a mutation by one thread is observable by another |

---

## 5. Method Behaviors

For every method, the RT MUST define a success flow and at least one error
flow (rule RT-R1). Each flow uses:

| Element | Requirement |
|---|---|
| Trigger | What starts the flow |
| Preconditions | What MUST hold before |
| Sequence | Numbered steps |
| Decision points | Branches with conditions |
| Alternative paths | Non-error alternatives |
| Failure paths | Error paths |
| Postconditions | What MUST hold after success |
| Observable effects | Side effects visible externally |
| Referenced API symbols | By symbol name |
| Referenced SM transitions | By transition row ID |
| Referenced SEC requirements | By SEC requirement ID |
| Referenced performance constraints | By PERF ID |

---

## 6. Concurrency Model

The RT MUST document, per shared-state resource:

| Element | Requirement |
|---|---|
| Shared state | What is shared |
| Isolation | Per-request vs global |
| Synchronization | Mechanism used |
| Locking | Lock and acquisition order |
| Ordering guarantees | Happens-before relations |
| Race-condition avoidance | Strategy |
| Memory ownership | Who owns what |
| Visibility guarantees | How mutations become visible |

---

## 7. Caching Behavior

The RT MUST provide a cache descriptor per cache:

| Element | Requirement |
|---|---|
| Cache key | Composition |
| Cache value | Type |
| TTL | Time-to-live |
| Invalidation triggers | What evicts |
| Eviction policy | LRU/FIFO/etc. |
| Concurrency | How concurrent access is handled |
| Capacity | Max entries/size |
| Stale behavior | What happens on miss/expiry |

## 8. Lifecycle Phases

The RT MUST document each lifecycle phase with a descriptor:

|---|---|---|---|---|

Phases: construction, initialization, steady state, shutdown, disposal,
restart, recovery.

|---|---|

## 15. Domain-Specific Rules

| Rule | Statement |
|---|---|
| RT-R1 Execution flow completeness | Every method MUST have a success flow and at least one error flow. |
| RT-R2 Error path exhaustiveness | The RT error table MUST be consistent with the API Throws table (API-001 §5.4). |
| RT-R3 Mandatory concurrency statements | Every method touching shared state MUST have concurrency statements. |
| RT-R4 State transition citation | Every state-changing method MUST cite the SM transition row. |
| RT-R5 Background task four-phase lifecycle | Every background task MUST define trigger, execution, error handling, shutdown. |
| RT-R6 Resource ownership transfer direction | MUST be explicit. |
| RT-R7 In-flight deduplication | MUST specify four properties: key, window, result sharing, eviction. |
| RT-R8 Partial failure specification | MUST specify which sub-operations can partially fail and the resulting state. |
| RT-R9 Memory visibility | Shared-state mutations MUST specify visibility guarantees. |
| RT-R10 Lock acquisition order | When multiple locks are held, the acquisition order MUST be documented. |
