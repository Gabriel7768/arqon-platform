## 1. Purpose

EDS-001 defines the documentation system that every package of the ARQON
Platform MUST follow. Its objective is to **prevent documentation entropy over
a ten-year horizon** across multiple independent engineering teams.

EDS-001 governs **how engineering knowledge is documented**. Its operational
counterpart, EES-001, governs **how engineering work is performed**.

EDS-001 does NOT define APIs, runtime behavior, state machines, security
controls, or package-specific behavior. It defines the architecture of the
documentation that holds those things.

### 1.1 Design goals

The documentation system MUST satisfy all of the following:

1. **Single Source of Truth** — each engineering topic belongs to exactly one
   authoritative document.
2. **Zero duplicated information** — no topic appears in two documents.
3. **Zero contradictory information** — impossible by construction, given (1).
4. **Clear ownership** — every document has a named owner.
5. **Deterministic implementation** — two teams reading the same document reach
   the same implementation.
6. **Independent versioning** — each document versions on its own lifecycle.
7. **Scalable to hundreds of packages.**
8. **Compatible with ADR methodology, Domain-Driven Design, Clean Architecture,
   and Hexagonal Architecture.**

---

## 2. Platform Context

This standard MUST govern documentation for the platform in **both its current
and target states**:

- **Current state:** the SaaS runs entirely in Replit as a same-origin monolith
  (`artifacts/` + `lib/`, JWT in `localStorage`).
- **Target state:** decoupled multi-host — Render (API), Vercel (web), Supabase
  (Postgres/Auth), Abacatepay (billing).

Standards and specifications MUST be written so they remain valid across the
Replit→multi-host migration. This is why the import contract (§6) is framed
around scoped names, not physical paths.

## 3. Documentation Hierarchy

Every document in the platform belongs to one of the following tiers. For each,
the table fixes its purpose, audience, owner, lifecycle, versioning, freeze
policy, update frequency, dependencies, allowed contents, and forbidden
contents.

### Tier A — Engineering Standards

Standards govern **how documents are written**, not what any package does.

| Document | Purpose | Audience | Owner | Freeze | Update |
|---|---|---|---|---|---|
| EDS-001 | Documentation system | All engineers | CTO | Frozen; change via ADR | Rare |
| EES-001 | Execution lifecycle | All engineers | CTO | Frozen; change via ADR | Rare |
| ESS-001 | How package specs are structured | Spec authors | CTO | Frozen; change via ADR | Rare |
| TS-001 | Meta-standard for technical standards | Standard authors | CTO | Frozen; change via ADR | Rare |
| API-001 | How Public API Specs are written | API spec authors | CTO | Frozen; change via ADR | Rare |
| RT-001 | How Runtime Specs are written | Runtime spec authors | CTO | Frozen; change via ADR | Rare |
| SM-001 | How State Machine Specs are written | SM spec authors | CTO | Frozen; change via ADR | Rare |
| ADAPT-001 | How Adapter Specs are written | Adapter spec authors | CTO | Frozen; change via ADR | Rare |
| SEC-001 | How Security Specs are written | Security spec authors | CTO | Frozen; change via ADR | Rare |

**Allowed contents:** structure rules, terminology, validation checklists,
quality gates, cross-reference rules.
**Forbidden contents:** package-specific behavior, real APIs, real runtimes,
real state machines, real implementations.

### Tier B — Architecture Decision Records (ADRs)

| Aspect | Value |
|---|---|
| Purpose | Record immutable architectural decisions and their rationale |
| Audience | Architects, senior engineers |
| Owner | Principal Architect |
| Lifecycle | Proposed → Accepted → Superseded. Never edited after Accepted; supersede via new ADR |
| Versioning | Numeric (ADR-NNN), immutable once accepted |
| Freeze | Accepted = frozen forever (only superseded, never mutated) |
| Allowed | Decision, context, alternatives, consequences, status |
| Forbidden | Implementations, full APIs, runtime flows |

### Tier C — Package Specifications

Specifications describe **what a package does**, contractually. They do NOT
contain implementation. Each is governed by the relevant Tier-A standard.

| Document | Governing standard | Purpose |
|---|---|---|
| Architecture Spec | ESS-001 | Module boundaries, responsibilities, dependency graph |
| Public API Spec | API-001 | Public interfaces, signatures, error contracts |
| Runtime Spec | RT-001 | Execution flows, lifecycle, concurrency, caching |
| State Machine Spec | SM-001 | States, transitions, guards, invariants |
| Security Spec | SEC-001 | Authn/authz surface, secrets, threat model |
| Adapter Spec | ADAPT-001 | Per-adapter contract (React, Email, PDF, Notification, …) |
| Testing Spec | (future TEST-001) | Test contracts, coverage targets |
| Observability Spec | (future OBS-001) | Metrics, logs, traces |
| Deployment Spec | (future DEPLOY-001) | Host mapping, build config, env contract |
| Data Model Spec | (ESS-001) | Tables, relations, constraints |
| Spec Planning Doc (SPD) | ESS-001 | Decomposes a package into the specs it needs before impl |

**Allowed contents:** contracts, signatures, flows, states, tables, invariants.
**Forbidden contents:** source code, framework internals, vendor lock-in detail
that belongs in an adapter spec.

### Tier D — Implementation & Operational Documents

| Document | Purpose | Lifecycle |
|---|---|---|
| Implementation Notes | How the spec was realized; deviations | Per-release |
| Operational Runbook | Incidents, on-call procedures | Living |
| Migration Guide | How to move between versions | Per-release |
| Developer Guide | Onboarding | Living |
| RFC | Proposed change before ADR | Proposed → Accepted/Rejected |

**Allowed:** concrete guidance, runbooks, examples.
**Forbidden:** redefining contracts that belong in Tier C.

## 4. Documentation Taxonomy

The complete set of document types the platform recognizes:

```
Engineering Standards          (Tier A)
Architecture Decision Records  (Tier B)
Package Specifications         (Tier C)
   ├─ Architecture Spec
   ├─ Public API Spec
   ├─ Runtime Spec
   ├─ State Machine Spec
   ├─ Security Spec
   ├─ Performance Spec
   ├─ Concurrency Spec
   ├─ Data Model Spec
   ├─ Adapter Spec
   ├─ Protocol Spec
   ├─ CLI Spec
   ├─ SDK Spec
   ├─ Testing Spec
   ├─ Observability Spec
   ├─ Deployment Spec
   └─ Spec Planning Doc (SPD)
Operational Documents          (Tier D)
   ├─ Operational Runbook
   ├─ Migration Guide
   ├─ Developer Guide
   ├─ Implementation Notes
   └─ RFC
```

A package is not required to have every type. SPD-001 (per package) determines
which are mandatory for that package.

## 5. Topic Ownership Matrix

Every engineering topic belongs to **exactly one** authoritative document. No
topic may appear in two. This is the core anti-entropy mechanism.

| Topic | Owning document type |
|---|---|
| Module boundaries | Architecture Spec |
| Dependency graph | Architecture Spec |
| Package responsibilities | Architecture Spec |
| Public interfaces | Public API Spec |
| Constructor signatures | Public API Spec |
| Type definitions | Public API Spec |
| Algorithms | Runtime Spec |
| Execution flows | Runtime Spec |
| Sequence diagrams | Runtime Spec |
| State machines | State Machine Spec |
| Error contracts | Public API Spec ( Throws) + Runtime Spec (recovery) |
| Performance guarantees | Performance Spec |
| Concurrency guarantees | Concurrency Spec / Runtime Spec |
| Caching rules | Runtime Spec |
| Lifecycle rules | Runtime Spec |
| Memory ownership | Runtime Spec |
| Thread safety | Runtime Spec |
| Framework integration | Adapter Spec |
| Testing contracts | Testing Spec |
| Mock behavior | Testing Spec |
| Configuration | Deployment Spec |
| Environment variables | Deployment Spec |
| Feature flags | Deployment Spec |
| CLI commands | CLI Spec |
| Observability — metrics | Observability Spec |
| Observability — logging | Observability Spec |
| Observability — tracing | Observability Spec |
| Security — authentication | Security Spec |
| Security — authorization | Security Spec |
| Security — secrets | Security Spec |
| Deployment | Deployment Spec |
| Migration | Migration Guide |
| Examples | Developer Guide (informative); Spec (normative only) |

**Conflict rule:** if two documents appear to own a topic, the lower-tier
document yields. Standards (Tier A) define *how*; Specs (Tier C) define *what*;
Implementation Docs (Tier D) describe *how it was built*.

## 6. Package Layout & Import Contract

This section is normative and directly affects code.

### 6.1 Physical layout (factual)

- `artifacts/` — deployable applications (Replit-native, carry
  `.replit-artifact`). Stable; apps live here.
- `lib/` — shared libraries, **grandfathered**. Existing packages remain until
  opportunistically migrated.
- `packages/` — canonical going-forward home for **new** shared platform
  libraries (i18n, auth, billing, …). Does not exist yet; created on first new
  platform package.
- `scripts/` — tooling.

### 6.2 Import contract (CANONICAL RULE)

> **Cross-package imports MUST use the `@workspace/*` scoped package name.
> Relative cross-package imports (`../../lib/`, `../artifacts/`) are FORBIDDEN.**

Rationale: scoped imports make each host's build (Render, Vercel) resolve
packages by name rather than relative path, which is a hard requirement for
multi-host deployment of a monorepo. It also makes any future `lib/`→`packages/`
migration a config change, not an import rewrite.

New code MUST comply. Existing relative `lib/` imports are grandfathered but
MUST be converted when the file is next meaningfully touched.

### 6.3 Workspace package names

Every package declares a `@workspace/<name>` name in its `package.json`. New
packages follow the same convention.

## 7. Cross-Document Rules

### 7.1 Reference rules

| Rule | Statement |
|---|---|
| Standards MAY reference other standards | Yes, via ID (e.g., "derives from TS-001") |
| Specs MAY reference standards | Yes |
| Specs MAY reference ADRs | Yes |
| Specs MAY reference other specs | Yes, but only by ID, never by copying content |
| Specs MUST NOT duplicate content owned elsewhere | Enforced |
| ADRs MUST NOT duplicate spec content | Enforced |
| Circular references | FORBIDDEN. The dependency graph MUST be acyclic. |

### 7.2 Reference format

A reference MUST be written as the owning document ID, optionally with a
section anchor: `[RT-001 §6]`. A reference MUST NOT inline the referenced
content.

### 7.3 Change propagation

When an owning document changes a contract:

- If **breaking**: requires an ADR AND downstream specs that reference it MUST
  be updated and re-frozen in the same change set.
- If **non-breaking**: downstream specs are unaffected; a note MAY be added.

### 7.4 Document vs package versioning

Document versions and package versions are independent. A package may release
(`@workspace/auth@1.2.0`) while its Architecture Spec remains at v1.0. A spec
version bump does not force a package release, and vice versa.

## 8. Governance

### 8.1 When an ADR is required

- Any breaking change to a Frozen standard or Frozen spec.
- Any change to module boundaries or the dependency graph.
- Introduction of a new package.
- Introduction of a new hosting target.
- Supersession of an existing ADR.

### 8.2 When an ADR is superseded

- A new ADR explicitly marks the old one `Superseded by ADR-NNN`.
- The old ADR is never mutated; only its status field changes.

### 8.3 When an RFC is required

- Exploratory proposals before a decision is firm. RFCs are not authoritative;
  they graduate to ADRs when accepted.

### 8.4 Review scopes

| Change | Required review |
|---|---|
| Standard change | Architecture review |
| API change | API review |
| Runtime change | Runtime review |
| Security change | Security review |
| Implementation-only change | Implementation review (no architecture review) |

## 9. Hosting & Secrets Contract (requirement)

Because the platform targets multi-host deployment (Render, Vercel, Supabase,
Abacatepay), EDS-001 records the following requirements. Detail is deferred to
a dedicated SEC-001 / DEPLOY-001.

1. **No secret in code or version control, ever.**
2. An `.env.example` MUST be versioned as the canonical contract of which
   environment variables exist (keys only, never values).
3. Each host receives only the subset of secrets it needs (Vercel must not hold
   Abacatepay keys; Render must not hold frontend-only secrets).
4. Cross-origin (Vercel→Render) requires an explicit CORS allowlist in the API.

## 12. Versioning

This standard follows semantic versioning.

- **Patch:** clarifications, checklist additions, typo fixes — no new obligations.
- **Minor:** new optional sections, new allowed document types — backward compatible.
- **Major:** new mandatory obligations, changed ownership, changed import contract — requires ADR.
