## 1. Package Overview

### 1.1 Purpose

`packages/i18n` is the ARQON Platform's internationalization library. It provides a structured, tenant-aware, runtime-configurable system for loading, caching, and resolving translated string dictionaries in both server-side and browser-side JavaScript environments. It is a foundational platform library: every package and application surface that presents human-readable text to users depends on it.

### 1.2 Responsibilities

The package is responsible for exactly the following capabilities. This list defines the boundary of what must be specified. Capabilities outside this list are explicitly out of scope.

| Responsibility | Description |
|---|---|
| Dictionary loading | Loading locale-keyed string dictionaries from static bundles or remote HTTP endpoints |
| Dictionary caching | Caching loaded dictionaries in memory or via a pluggable cache provider |
| Translation resolution | Resolving a dot-notation key to a translated string within a loaded dictionary |
| Variable interpolation | Substituting named variables into translated strings |
| Locale fallback | Falling back to a configured fallback locale when a key is absent in the primary locale |
| Tenant isolation | Maintaining per-tenant dictionary registries when multi-tenant configurations are in use |
| Enum translation | Resolving enumeration values to translated labels via a namespace convention |
| Namespace management | Partitioning dictionaries into named namespaces for independent loading and versioning |
| Critical namespace loading | Distinguishing namespaces that must be loaded synchronously before rendering from those that may load lazily |
| Framework integration | Providing a React adapter (provider and hook), a Node.js server adapter, and a browser adapter |
| Testing support | Providing a `MockRegistry` with deterministic behavior for use in consumer test suites |

### 1.3 Architectural boundaries

**What the package owns:**
- The `Registry` abstraction and its `ReadableRegistry` / `WritableRegistry` interface split
- All loader interfaces (`DictionaryLoader`) and their bundled implementations (`StaticLoader`, `HttpLoader`, `HybridLoader`)
- All cache interfaces (`CacheProvider`) and their bundled implementations (`MemoryCache`, `NullCache`)
- The core resolution, interpolation, and fallback algorithms
- The React, Node.js, and browser adapter implementations
- The `MockRegistry` testing utility

**What the package does NOT own:**
- Dictionary content (owned by each consuming application or service)
- HTTP transport implementation (delegated to the host environment's `fetch` or a consumer-provided implementation)
- Authentication credentials for loading dictionaries (consumed as configuration; not stored or managed)
- Locale detection (the package accepts a locale; it does not detect it from the request or browser)
- Pluralization rules beyond what is encoded in dictionary values (not in scope for v1)

### 1.4 External dependencies

| Dependency | Type | Rationale |
|---|---|---|
| Host environment `fetch` | Runtime API | `HttpLoader` uses `fetch` for remote dictionary loading; the host provides it |
| `react` | Peer dependency | The React adapter requires React; it is a peer dependency, not bundled |
| `react-dom` | Peer dependency | Required by the React adapter |

The package has no ARQON workspace package dependencies in its v1 scope. It is a leaf library.

### 1.5 Known dependents

These packages and surfaces are expected to depend on `packages/i18n` once the package is production-ready. They are identified here because their requirements must not be allowed to silently drive i18n design decisions that have not been specified:

| Dependent | Dependency nature |
|---|---|
| All consumer-facing web applications | React adapter |
| All server-side rendering services | Node.js adapter |
| `packages/auth` | Login and error string translation |
| `packages/billing` | Invoice and notification string translation |
| `packages/notifications` | Message template resolution |
| ARQON SDKs | Core registry for SDK-generated UI surfaces |

No document in Layer N references any document in Layer N or higher. The graph is acyclic.

### 3.3 Critical path

The critical path — the sequence that determines the minimum elapsed time to implementation readiness — is:

```
ADR(s) → ARCH → DATA → API → RT → [SEC, PERF, TEST in parallel] → ADAPT set
                  ↘ SM → API
```

The bottleneck is `I18N-API-1.0.0`. Nothing in the adapter layer, the behavioral layer, the quality layer, or the operational layer can be frozen until API is frozen. Parallelizing ARCH → DATA and ARCH → SM is the primary schedule optimization opportunity.

## 4. Writing Order

The writing order follows the topological sort of the dependency graph. Documents within the same layer may be written in parallel by different authors.

### Phase 1 — Governance prerequisite (before any i18n specification work begins)

**ADR(s) — Architecture Decision Record(s)**
*Responsible:* Principal Architect
*Dependency:* None
*Rationale:* The ARCH document cannot be written until the architectural decisions it expresses have been made and recorded. If ADRs covering the Registry model, the loader merge strategy, the tenant model, and the cache abstraction do not yet exist, they must be filed and accepted before Phase 2 begins. The number of ADRs is not prescribed here; it is determined by how many distinct architectural decisions were made. Each ADR covers exactly one decision per EDS-001 §4.2.

**Gate before Phase 2:** All governing ADRs are in Accepted status.

---

### Phase 2 — Architecture (serial; gates all subsequent work)

**I18N-ARCH-1.0.0**
*Responsible:* Principal Architect
*Dependency:* Accepted ADR(s)
*Rationale:* Every other specification document for this package is grounded in the module structure ARCH defines. The API owner needs ARCH to know what modules expose what surfaces. The RT owner needs ARCH to know what modules own what behaviors. Adapter owners need ARCH to know what extension interfaces are provided by which modules. Writing any specification before ARCH is frozen risks structural rework when module boundaries are clarified.

**Gate before Phase 3:** I18N-ARCH-1.0.0 is Frozen.

---

### Phase 3 — Foundation specifications (parallel; may be written simultaneously by different authors)

**I18N-DATA-1.0.0** (parallel with SM)
*Responsible:* Staff Engineer (data owner)
*Dependency:* I18N-ARCH-1.0.0
*Rationale:* The Dictionary schema, Locale identifier format, and Tenant configuration structure are referenced by the API document's type definitions. The API author cannot write type signatures involving `Dictionary`, `Locale`, or `TenantConfig` until their schemas are specified. DATA must be frozen before API authorship begins.

**I18N-SM-1.0.0** (parallel with DATA)
*Responsible:* Staff Engineer (RT owner)
*Dependency:* I18N-ARCH-1.0.0
*Rationale:* The `Registry` lifecycle state machine governs which methods are callable in which states. The API document references state names in preconditions (e.g., "the Registry MUST be in the `READY` state"). The state names must be canonical before they appear in the API. Writing the SM in parallel with DATA allows both to complete before API authorship begins. Note: SM will reference API error types for state transition errors, but since SM is written before API is frozen, the SM author and API author must coordinate on error type names during Phase 3. The SM is frozen after API error types are confirmed.

**Gate before Phase 4:** I18N-DATA-1.0.0 Frozen AND I18N-SM-1.0.0 Frozen (or at stable draft with confirmed error type names).

*Ordering note on SM freeze:* I18N-SM-1.0.0 has a dependency on I18N-API-1.0.0 for error types (SM transition error column references API error types). However, API depends on SM for state names. This creates an authorship coordination requirement, not a circular document dependency: the SM is authored in Phase 3 with placeholder error type names that are confirmed and finalized in Phase 4 when API is authored. I18N-SM-1.0.0 is formally frozen in Phase 4 after API error types are confirmed, not before.

---

### Phase 4 — Public contract (serial; bottleneck of the entire specification effort)

**I18N-API-1.0.0**
*Responsible:* Staff Engineer (API owner)
*Dependency:* I18N-ARCH-1.0.0, I18N-DATA-1.0.0, I18N-SM-1.0.0 (stable draft)
*Rationale:* The API document is the central specification artifact. It defines every exported symbol: the `Registry` class and both its readable and writable interface splits, all loader interfaces and their implementations, all cache interfaces and implementations, the `t()` function calling convention, `formatEnum`, error types and all error codes, all constants. No RT document can be written without knowing method signatures. No adapter specification can be written without knowing the extension interfaces they implement. No test specification can be written without the contracts being defined. API is the single most critical document in the specification set.

*Authorship notes:*
- The API author finalizes error type names in coordination with the SM author; I18N-SM-1.0.0 is frozen immediately after API error types are confirmed.
- The API document cites I18N-RT-1.0.0 §{N.N} for every method's behavioral specification. Since RT has not been written yet, these citations are recorded as draft forward references and resolved when RT is frozen. The API document is not itself frozen until these citations resolve.
- API freeze requires RT to exist in at minimum a stable draft, so that behavioral specification section numbers can be confirmed.

**Gate before Phase 5:** I18N-API-1.0.0 Frozen AND I18N-SM-1.0.0 Frozen (SM is finalized here with confirmed error types).

---

### Phase 5 — Behavioral contract (serial; gates quality, operational, and adapter work)

**I18N-RT-1.0.0**
*Responsible:* Staff Engineer (RT owner)
*Dependency:* I18N-API-1.0.0 (Frozen), I18N-SM-1.0.0 (Frozen)
*Rationale:* The RT document specifies the execution flows for every public method, the caching rules, the locale fallback algorithm, the interpolation algorithm, the in-flight deduplication mechanism, the error propagation policy, and the concurrency model. It is the document an implementing engineer reads to understand exactly how to implement a method. RT cannot be written until API is frozen because RT sections are keyed to API method signatures. The RT is the most detailed document in the set; its authorship requires the most engineering time and produces the most implementation-critical content.

**Gate before Phase 6:** I18N-RT-1.0.0 Frozen.

---

### Phase 6 — Quality, safety, and operational specifications (parallel; all depend on RT)

All documents in this phase may be authored simultaneously by different authors once I18N-RT-1.0.0 is frozen.

**I18N-SEC-1.0.0** (parallel)
*Responsible:* Security Owner
*Dependency:* I18N-API-1.0.0, I18N-RT-1.0.0
*Rationale:* Security review requires knowing both the interface (what inputs are accepted) and the behavior (how inputs are processed). SEC defines input validation rules for all public entry points — namespace strings, locale identifiers, dictionary values, tenant identifiers — and the trust boundary for remote dictionary loading (HttpLoader accepts arbitrary URLs from configuration; this boundary must be analyzed). SEC must be frozen before the implementation handles any external input.

**I18N-PERF-1.0.0** (parallel)
*Responsible:* Performance Owner
*Dependency:* I18N-RT-1.0.0
*Rationale:* SLOs must be known before implementation begins so that the implementation is built to meet them. A performance specification written after implementation is a measurement of what was built, not a contract for what must be built. Key SLOs to define: `t()` resolution latency at p99 (this is on every render hot path), `Registry.load()` latency under cache hit vs. cache miss, memory budget per registry instance, and concurrency guarantees for `t()` calls during active loading.

**I18N-TEST-1.0.0** (parallel)
*Responsible:* Staff Engineer (API owner)
*Dependency:* I18N-API-1.0.0, I18N-RT-1.0.0
*Rationale:* Test contracts must be defined before implementation so that the implementation is built to be testable. The `MockRegistry` contract is especially critical: consuming packages will use `MockRegistry` in their own tests, and its behavior must be contractually specified before any consumer writes a test against it. TEST also defines the `DictionaryLoader` mock and `CacheProvider` mock contracts needed to test the `Registry` in isolation.

**I18N-OBS-1.0.0** (parallel)
*Responsible:* SRE / Observability Owner
*Dependency:* I18N-RT-1.0.0, I18N-SM-1.0.0
*Rationale:* Observability events are specified alongside behavior so that the implementation emits them correctly. Log events are keyed to state transitions (SM) and method executions (RT). Defining OBS after RT ensures that every significant RT event (load completed, cache hit, cache miss, fallback triggered, load failed) has a corresponding named log event. OBS must be frozen before the package enters Stabilizing status.

**Gate before Phase 7:** I18N-SEC-1.0.0 Frozen, I18N-PERF-1.0.0 Frozen, I18N-TEST-1.0.0 Frozen. (I18N-OBS-1.0.0 need not be frozen to begin Phase 7 adapter work, but must be frozen before Phase 8.)

---

### Phase 7 — Adapter specifications (parallel set, with one exception)

All documents in this phase except HYBRID may be authored simultaneously.

**I18N-ADAPT-STATIC-1.0.0** (parallel)
*Responsible:* Staff Engineer (loader owner)
*Dependency:* I18N-API-1.0.0, I18N-RT-1.0.0
*Rationale:* StaticLoader is the simplest loader. Its adapter spec defines what happens when a requested namespace is not present in the static bundle (the most important failure mode for a static-only deployment). Frozen before HYBRID begins.

**I18N-ADAPT-HTTP-1.0.0** (parallel)
*Responsible:* Staff Engineer (loader owner)
*Dependency:* I18N-API-1.0.0, I18N-RT-1.0.0, I18N-DEPLOY-1.0.0
*Rationale:* HttpLoader has the most complex failure modes (network unavailability, timeout, non-200 responses, malformed payloads). Its adapter spec must enumerate all of these. It also reads environment variables documented in DEPLOY. DEPLOY must be frozen (or at stable draft with confirmed env var names) before HTTP adapter spec is frozen.

**I18N-ADAPT-CACHE-1.0.0** (parallel)
*Responsible:* Staff Engineer (cache owner)
*Dependency:* I18N-API-1.0.0, I18N-RT-1.0.0
*Rationale:* Both bundled cache implementations share a single adapter spec because they implement the same `CacheProvider` interface. The document covers MemoryCache TTL behavior and eviction, and NullCache's pass-through guarantee (which is important: NullCache must not silently retain entries across calls).

**I18N-ADAPT-REACT-1.0.0** (parallel)
*Responsible:* Staff Engineer (React adapter owner)
*Dependency:* I18N-API-1.0.0, I18N-RT-1.0.0
*Rationale:* The React adapter is the primary consumer surface. `I18nProvider` and `useTranslation` together determine how the entire consumer-facing API is experienced by developers. The adapter spec must define re-render behavior precisely: does a locale change trigger a full re-render of all translated components? What is the context contract? SSR compatibility is a first-class concern.

**I18N-ADAPT-NODE-1.0.0** (parallel)
*Responsible:* Staff Engineer (server adapter owner)
*Dependency:* I18N-API-1.0.0, I18N-RT-1.0.0
*Rationale:* The Node.js adapter governs per-request registry lifecycle. The critical question it must answer is whether `Registry` instances are per-request or shared singletons, and what the memory lifecycle implications are. This is a significant implementation decision that must be specified, not discovered in code review.

**I18N-ADAPT-BROWSER-1.0.0** (parallel)
*Responsible:* Staff Engineer (browser adapter owner)
*Dependency:* I18N-API-1.0.0, I18N-RT-1.0.0
*Rationale:* The browser adapter defines how dictionaries are loaded in a browser context without a server. Offline behavior and Service Worker interaction (if in scope) must be specified here. Browser version compatibility matrix establishes the support boundary.

**I18N-DEPLOY-1.0.0** (parallel with Phase 6 and Phase 7, but gates HTTP adapter)
*Responsible:* Release Manager
*Dependency:* I18N-OBS-1.0.0
*Rationale:* DEPLOY defines the package publication contract: npm package name, bundle formats (ESM/CJS), environment variable names read by the HTTP adapter, and peer dependency version ranges. It is a library deployment spec, not a server deployment spec. It gates I18N-ADAPT-HTTP-1.0.0 because the HTTP adapter reads environment variables that must be named in DEPLOY.

**Gate before Phase 8:** I18N-ADAPT-STATIC-1.0.0 Frozen, I18N-ADAPT-HTTP-1.0.0 Frozen (HYBRID depends on both).

### Phase 8 — Dependent adapter specifications (serial)

**I18N-ADAPT-HYBRID-1.0.0**
*Responsible:* Staff Engineer (loader owner)
*Dependency:* I18N-API-1.0.0, I18N-RT-1.0.0, I18N-ADAPT-STATIC-1.0.0, I18N-ADAPT-HTTP-1.0.0
*Rationale:* HybridLoader composes StaticLoader and HttpLoader. Its adapter spec defines precedence rules, failure fallback between the two, and the critical namespace classification contract (namespaces designated critical are loaded through the static path; others use HTTP with optional static fallback). **I18N-ADAPT-MOCK-1.0.0**
*Responsible:* Staff Engineer (API owner)
*Dependency:* I18N-API-1.0.0, I18N-TEST-1.0.0
*Rationale:* MockRegistry's behavioral contract must be consistent with both the public API (so it is a valid substitute in tests) and the TEST document's mock contract requirements. It is the last adapter specified because it is the testing analog of the full system — it cannot be fully specified until the system it mocks is fully specified.

**Gate before Implementation Readiness:** All 18 specification documents Frozen.

| Risk ID | Potential gap | Assessment | Resolution |
|---|---|---|---|
| MG-01 | The `formatEnum` function's lookup convention (`${namespace}.enum.${value}`) is a behavior that must appear in RT. ### 7.3 Potential circular dependency risks

The dependency graph (§3) was verified acyclic before this SPD was published. However, the following authorship patterns carry a risk of introducing a cycle during drafting:

| Risk ID | Potential cycle | Prevention |
|---|---|---|
| CD-01 | API cites RT for behavior, RT cites API for types. This is permitted (§6.6 of EDS-002) but is only non-circular if API cites RT for behavioral algorithms and RT cites API for type definitions — not the same sections. If RT begins duplicating type definitions from API, a functional cycle exists. | The RT author MUST NOT restate type definitions. Any type needed in RT is cited from API by section number. RT's §1 (Definitions) cites API, not restates it. This is checked at SG-04 (cross-reference integrity). |
| CD-02 | ADAPT-HYBRID cites ADAPT-STATIC and ADAPT-HTTP. If ADAPT-STATIC or ADAPT-HTTP then cites ADAPT-HYBRID (e.g., referencing "the composition behavior in HYBRID"), a cycle exists. | ADAPT-STATIC and ADAPT-HTTP must not reference ADAPT-HYBRID. The HYBRID document is the reference point for composition; the component adapters specify their behavior in isolation only. This is checked by the Specification Review panel for both STATIC and HTTP. |
| CD-03 | TEST cites API and RT. ADAPT-MOCK cites API and TEST. If API later cites ADAPT-MOCK (e.g., to describe the MockRegistry in the API surface section), a cycle API→ADAPT-MOCK→TEST→API exists. | API's §3 (Scope) lists `MockRegistry` as an exported symbol, but `MockRegistry`'s behavioral contract is owned by ADAPT-MOCK, not by API. API cites ADAPT-MOCK for the mock's specification. ADAPT-MOCK does not need to cite back to API for this. If API later cites ADAPT-MOCK for behavioral content, this is a content misplacement defect, not a legitimate reference. |
