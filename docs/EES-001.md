# ARQON Platform — Engineering Execution Standard
## EES-001 — Version 1.0
**Status:** Active — Effective immediately upon ratification.
**Owner:** Chief Architect
**Audience:** All engineers, architects, technical leads, package owners, release managers, and reviewers across all ARQON platform teams.

---

## 1. Purpose and Scope

EDS-001 governs how engineering knowledge is documented. EES-001 governs how engineering work is performed. Together they form the complete governance layer for the ARQON Platform.

EES-001 defines:

- The end-to-end engineering lifecycle from idea to retirement
- Engineering roles, responsibilities, authority, and decision scope
- The package lifecycle from proposal to archival
- Change management procedures for every class of change
- Mandatory quality gates for every release
- Release governance including versioning, rollback, hotfix, and emergency change procedures
- Engineering principles binding on every contributor

EES-001 applies without exception to every team and every package on the ARQON Platform. Where EDS-001 and EES-001 address the same topic, EDS-001 is authoritative on what to document; EES-001 is authoritative on how to execute the work.

---

## 2. Engineering Principles

These principles are binding. They are not aspirational. Every contributor, regardless of seniority, is expected to apply them without exception. Deviation requires a written justification filed as an IMPL note and reviewed by the Package Owner.

**E1 — Specification before implementation.** No implementation work begins until the relevant API and RT documents are frozen for the target version. Code is an expression of a specification, not a substitute for one.

**E2 — One owner per decision.** Every decision has exactly one owner at all times. Ambiguous ownership is resolved before work begins, not after a conflict surfaces.

**E3 — Breaking changes are expensive.** A breaking change creates migration burden for every downstream consumer. The author of a breaking change is responsible for the migration path, not the consuming teams.

**E4 — Observable behavior is contractual.** Any behavior that a consumer has relied on — even undocumented behavior — is a de facto contract. It may not be changed without a breaking-change process.

**E5 — Quality gates are not optional.** A gate exists because a class of defect has caused production harm. Bypassing a gate requires written approval from the Architecture Review Board and is recorded as a known risk in the release record.

**E6 — Rollback must be possible.** Every release must have a tested rollback path defined before deployment. A release without a rollback path is not approved.

**E7 — Monitoring precedes deployment.** No package enters production without its OBS document approved and its observability infrastructure provisioned and validated in staging.

**E8 — Documentation is not optional.** A feature that is not documented to the level required by EDS-001 is not complete. Documentation debt is tracked as a blocking defect, not a follow-up task.

**E9 — Security is not a phase.** Security review occurs at specification time, not as a pre-release checkpoint. A security concern raised at the gate stage is an architectural failure, not a process success.

**E10 — Deprecation is a contract.** When a symbol, API, or behavior is deprecated, the deprecation period, migration path, and removal date are stated at the time of deprecation. They are not adjusted downward after announcement.

## 3. Engineering Roles

### 3.1 Chief Architect

**Responsibilities:** Owns EDS-001 and EES-001. Makes final architectural decisions on cross-package concerns. Chairs the Architecture Review Board. Approves all ADRs, new packages, and EDS/EES amendments. Owns the platform-wide dependency graph.

**Authority:** May veto any technical decision on architectural grounds. May require an RFC for any change deemed to have platform-wide impact.

**Decision scope:** Platform architecture, cross-package contracts, platform-wide standards, escalation resolution.

### 3.2 Principal Architect

**Responsibilities:** Owns the architecture of an assigned domain (a group of related packages). Writes and owns ARCH documents. Approves ADRs within their domain. Reviews breaking changes to API and RT. Participates in Architecture Review Board.

**Authority:** May approve or reject architectural decisions within their domain without escalation. Escalates cross-domain decisions to the Chief Architect.

**Decision scope:** Domain architecture, module boundaries within domain, inter-package dependency rules within domain.

### 3.3 Staff Engineer

**Responsibilities:** Owns API and RT documents for one or more packages. Drives RFC processes for breaking changes. Reviews all specification documents in their package set. Participates in cross-team technical alignment.

**Authority:** May approve minor API and RT changes without RFC. Must initiate RFC for breaking changes.

**Decision scope:** Package API and runtime contracts, intra-package architecture, cross-package integration design.

### 3.4 Senior Engineer

**Responsibilities:** Implements packages according to frozen specifications. Writes and maintains Tier 3 and Tier 4 documents. Authors RFCs for changes within their package. Owns the implementation correctness of assigned components.

**Authority:** May approve patch-level changes to Tier 3 and Tier 4 documents. May not approve breaking changes to Tier 2 documents unilaterally.

**Decision scope:** Implementation choices within a specified design, Tier 3 and Tier 4 documents, test cases.

### 3.5 Package Owner

**Responsibilities:** Accountable for the health, quality, compliance, and lifecycle of a specific package. Assigns document owners within the package. Approves all releases of the package. Is the escalation point for all package-level disputes. The Package Owner role may be held concurrently with a technical role (e.g., Staff Engineer who is also Package Owner).

**Authority:** May approve all non-architectural decisions within the package. Escalates architectural decisions to the Principal Architect.

**Decision scope:** Package release approval, document ownership assignments within the package, compliance with EDS-001 and EES-001 within the package.

### 3.6 Reviewer

**Responsibilities:** Reviews code, specifications, or documents as assigned. Provides written feedback within the review SLA (§6.4). Approves or requests changes with justification. A Reviewer may hold any other role concurrently.

**Authority:** May approve or block a review item. A block must include a specific, actionable reason. A block may be escalated to the Package Owner if the reviewer and author cannot resolve it within 2 business days.

**Decision scope:** The specific review item assigned.

### 3.7 Release Manager

**Responsibilities:** Executes the release process for a package or a coordinated set of packages. Validates that all quality gates are passed before triggering deployment. Owns the release record. Coordinates rollback if a release fails post-deployment.

**Authority:** May hold a release pending gate completion. May trigger an emergency rollback without prior approval (§9.5).

**Decision scope:** Release timing, release record, rollback execution.

## 4. Engineering Lifecycle

The lifecycle has 14 stages. Every new feature, package, or breaking change begins at Stage 1. Bug fixes, patch releases, and hotfixes enter at Stage 9. Emergency changes follow §9.5.

```
Stage 1   Idea
Stage 2   Discovery
Stage 3   RFC
Stage 4   Architecture Review
Stage 5   ADR
Stage 6   Specification Writing
Stage 7   Implementation
Stage 8   Code Review
Stage 9   Testing
Stage 10  Validation
Stage 11  Release
Stage 12  Deployment
Stage 13  Monitoring
Stage 14  Maintenance → (returns to Stage 1 for new work, or proceeds to Deprecation)

Deprecation Track
Stage D1  Deprecation Notice
Stage D2  Migration Period
Stage D3  Removal
Stage D4  Archival
```

---

### 4.1 Stage 1 — Idea

**Entry condition:** Any engineer identifies a potential feature, improvement, architectural change, or new package.

**Activities:** Idea is captured in a free-form note or issue. No formal artifact is required at this stage. The author identifies whether the idea is within an existing package, requires a new package, or affects cross-package contracts.

**Exit condition:** Author decides to pursue the idea formally (advances to Discovery) or abandons it (closed with reason).

**Owner:** Originating engineer.

**Required artifacts:** None.

---

### 4.2 Stage 2 — Discovery

**Entry condition:** Author decides to pursue an idea.

**Activities:** Author investigates scope and impact. Identifies which packages, documents, and teams are affected. Determines whether the change is additive (non-breaking minor) or structural (breaking or new package). Consults with the Package Owner for in-scope packages. Identifies whether an RFC is required per EDS-001 §7.3.

**Exit condition:** Scope is understood, impact is documented in a brief discovery note (≤1 page), and the change class is determined.

**Owner:** Originating engineer, in consultation with the relevant Package Owner.

**Required artifacts:** Discovery note (informal; filed in the package's documentation repository).

---

### 4.3 Stage 3 — RFC

**Entry condition:** Discovery determines that an RFC is required per EDS-001 §7.3.

**Activities:** Author writes RFC per the RFC document type definition in EDS-001 §4.21. RFC is filed and the comment period opens. All affected teams are notified. The Principal Architect is notified for cross-package RFCs. The comment period is per EDS-001 §7.3 thresholds and runs from the notification date, not the filing date.

**Exit condition:** Comment period closes. RFC is either Accepted or Rejected by the designated approver (Package Owner for single-package RFCs; Principal Architect for multi-package RFCs; Chief Architect for platform-wide RFCs).

**Owner:** RFC author.

**Required artifacts:** Filed RFC document per EDS-001 §4.21.

**Approver:** Package Owner (single-package), Principal Architect (domain), Chief Architect (platform-wide or EDS/EES amendment).

**If rejected:** Work does not proceed. RFC is archived as Rejected with the rejection rationale.

**If accepted:** RFC is archived as Accepted. Work proceeds to Stage 4 if an architectural decision is required, or directly to Stage 6 if only a specification update is needed.

---

### 4.4 Stage 4 — Architecture Review

**Entry condition:** The change requires an ADR (EDS-001 §7.1) or the accepted RFC involves a cross-package contract, a new package, or a change to ARCH.

**Activities:** Principal Architect or Chief Architect (per scope) convenes an Architecture Review Board session. The session reviews the accepted RFC, validates that the proposed change is consistent with existing ARCH documents, identifies downstream impact, and either approves or rejects the architectural direction.

**Exit condition:** Written Architecture Review outcome (approved or rejected with conditions) is filed. If approved, the architectural decision is recorded in an ADR (Stage 5). If rejected, the RFC is returned to Stage 3 for revision or archived as Rejected.

**Owner:** Principal Architect (domain) or Chief Architect (platform-wide).

**Required artifacts:** Architecture Review outcome document, referencing the RFC by ID.

**SLA:** Architecture Review Board must convene within 5 business days of a complete RFC being submitted for review.

---

### 4.5 Stage 5 — ADR Creation

**Entry condition:** Architecture Review approves the architectural direction.

**Activities:** The architect responsible for the decision writes the ADR per EDS-001 §4.2. ADR is filed, numbered, and marked Accepted. Any ARCH document affected by the decision is updated (or a new ARCH is created) in this stage, before specification writing begins.

**Exit condition:** ADR is filed as Accepted. All affected ARCH documents are updated to a new version consistent with the ADR.

**Owner:** Principal Architect or Chief Architect (consistent with the Architecture Review owner).

**Required artifacts:** ADR, updated ARCH document(s).

---

### 4.6 Stage 6 — Specification Writing

**Entry condition:** Either (a) ADR is accepted and ARCH is updated, or (b) the change does not require an ADR and an accepted RFC authorizes a specification change.

**Activities:** The assigned document owners write or update the required Tier 2 and Tier 3 specification documents per EDS-001 §4. Documents are written in dependency order: ARCH first (if changed), then API, then RT, then all others. A document is not released to the next stage until all documents it depends on are in a stable draft.

No implementation code is written during Stage 6. Prototype code written to validate a specification is discarded before Stage 7 begins and does not constitute implementation.

Draft documents are reviewed by the Specification Review panel (§6.2) before being frozen.

**Exit condition:** All required specification documents are frozen at their new version. The implementation team has been briefed.

**Owner:** Document owners per the package's ARCH ownership assignments.

**Required artifacts:** All required Tier 2 and Tier 3 document updates or new versions, frozen.

---

### 4.7 Stage 7 — Implementation

**Entry condition:** All specification documents required for the implementation scope are frozen.

**Activities:** Engineers implement the package or feature against the frozen specifications. Implementation must not deviate from frozen specifications. If an implementation reveals a specification error or omission, the engineer raises it immediately with the document owner. The document owner either issues a patch version of the specification (for clarifications) or opens a new RFC (for behavioral changes). Implementation is blocked on specification resolution — it does not proceed on an assumed interpretation.

**Exit condition:** Implementation is complete, all automated tests pass, and the code is ready for code review.

**Owner:** Implementing engineer(s), coordinated by the Package Owner.

**Required artifacts:** Implementation code, passing automated test suite, updated IMPL notes for any non-obvious decisions.

---

### 4.8 Stage 8 — Code Review

**Entry condition:** Implementation is complete and tests pass.

**Activities:** Code review is assigned to at least one Reviewer with sufficient knowledge of the affected package. For breaking changes, the Package Owner is a required reviewer. For changes affecting security contracts, the security owner is a required reviewer.

Reviewers check: conformance to the frozen specification, test coverage of specified behaviors (per TEST document), absence of undocumented behavior, correctness of IMPL notes, and compliance with §2 engineering principles.

Reviewers do not re-litigate specification decisions. A specification concern raised during code review is a Stage 6 failure and must be resolved through the specification amendment process — it does not block or delay code review indefinitely.

**Exit condition:** All required reviewers have approved. All blocking comments are resolved.

**Owner:** Package Owner (assigns reviewers, breaks ties).

**Required artifacts:** Approved code review record.

**SLA:** Initial review feedback within 2 business days. Re-review within 1 business day of revision.

---

### 4.9 Stage 9 — Testing

**Entry condition:** Code review is approved.

**Activities:** All test cases required by the TEST document are executed. Automated tests run in CI. Integration tests are run in the staging environment. Performance tests are run if the change affects components with a PERF document. Security tests are run if the change affects components with a SEC document.

Test results are recorded in the release record. A failing required test case blocks advancement. A failing optional test case is recorded as a known limitation with an associated remediation ticket.

**Exit condition:** All required test cases pass. Test results are filed in the release record.

**Owner:** Implementing engineer (for unit and integration tests); Release Manager (for staging execution).

**Required artifacts:** Test execution report (CI output and staging report), filed in the release record.

---

### 4.10 Stage 10 — Validation

**Entry condition:** All required tests pass.

**Activities:** All quality gates in §6 are checked in order. A quality gate failure at this stage returns the work to the appropriate earlier stage (Stage 7 for implementation defects, Stage 6 for specification defects). Quality gate bypass is possible only under the conditions in §6.5.

The Release Manager assembles the release record (§9.2) and confirms all gate checkboxes are complete.

**Exit condition:** All quality gates are passed. Release record is complete and signed by the Package Owner.

**Owner:** Release Manager, with sign-off from the Package Owner.

**Required artifacts:** Complete release record with all quality gates checked.

---

### 4.11 Stage 11 — Release

**Entry condition:** Complete release record signed by the Package Owner.

**Activities:** The release is tagged per the semantic versioning policy (§9.1). Release notes are published, referencing the relevant RFC, ADR, and document version changes. For major releases, consuming teams are notified with a minimum 5 business day notice before the release is made available in production-facing registries.

**Exit condition:** Package is tagged and published to the registry. Release notes are published.

**Owner:** Release Manager.

**Required artifacts:** Release tag, release notes.

---

### 4.12 Stage 12 — Deployment

**Entry condition:** Package is released and consuming services have updated their dependency.

**Activities:** The deployment is executed per the package's DEPLOY document. Pre-deployment validation confirms observability infrastructure is provisioned (per OBS document). Rollback path is confirmed to be executable before deployment proceeds. Canary or staged rollout is used for any major version deployment or any change to a critical path.

**Exit condition:** Deployment is live, health checks pass, and the monitoring period (Stage 13) begins.

**Owner:** Release Manager (for the package release); consuming team's release manager (for the consuming service's deployment).

**Required artifacts:** Deployment record (environment, version, timestamp, rollout strategy, health check results).

---

### 4.13 Stage 13 — Monitoring

**Entry condition:** Deployment is live.

**Activities:** The on-call engineer monitors the metrics, logs, and alerts defined in the OBS document for a minimum observation window. For major releases, the observation window is 48 hours. For minor releases, 24 hours. For patch releases, 4 hours. During the observation window, any alert from the OBS document that fires is treated as a potential release defect and investigated immediately.

**Exit condition:** Observation window closes with no unresolved alerts from the OBS document, or an alert has been investigated and determined to be pre-existing. The release is marked stable and the monitoring period ends.

**Owner:** On-call engineer for the affected service(s), supervised by the Release Manager.

**Required artifacts:** Monitoring report (observation window start/end, any alerts fired and their dispositions), filed in the release record.

---

### 4.14 Stage 14 — Maintenance

**Entry condition:** Release is marked stable.

**Activities:** Package enters normal maintenance. Bug reports are triaged by the Package Owner. Bugs that affect specified behaviors are treated as specification non-conformances and enter the lifecycle at Stage 7 (for implementation fixes) or Stage 6 (for specification ambiguities that require clarification). New feature requests enter at Stage 1.

**Owner:** Package Owner.

## 5. Package Lifecycle

A package has eight lifecycle states. Transitions between states are gated.

```
Proposed → Approved → In Development → Stabilizing → Production → Maintained → Deprecated → Archived
```

### 5.1 Proposed

**Entry:** Any engineer files a package proposal, which is an RFC with package-level scope (EDS-001 §7.3).

**Exit to Approved:** RFC is accepted by the Chief Architect. ARCH document is initialized.

**Exit to Abandoned:** RFC is rejected. No further action.

**Required artifacts:** RFC, Architecture Review outcome.

### 5.2 Approved

**Entry:** RFC accepted and Architecture Review approved.

**Activities:** Package Owner is assigned. Document ownership assignments are made. ARCH is written and frozen. API and RT documents are drafted. Package repository is initialized.

**Exit to In Development:** API and RT documents are frozen at 1.0.0. ADR is filed. Package Owner is confirmed.

**Required artifacts:** ARCH-1.0.0, API-1.0.0, RT-1.0.0, ADR, Package Owner assignment record.

### 5.3 In Development

**Entry:** Specification documents are frozen at 1.0.0.

**Activities:** Implementation proceeds through Stages 7–10. The package is not available to consuming teams. A development preview may be shared under an explicit pre-release version label (e.g., `0.x.x` or `1.0.0-beta.N`).

**Exit to Stabilizing:** First complete implementation passes all required quality gates (§6).

**Required artifacts:** Passing test suite, complete quality gate record.

### 5.4 Stabilizing

**Entry:** First complete implementation passes all quality gates.

**Activities:** Package is made available to a limited set of early adopting teams under a release candidate label (`1.0.0-rc.N`). Feedback is collected. Specification defects discovered during stabilization are corrected through patch versions. No new features are introduced during stabilization.

**Minimum duration:** 10 business days.

**Exit to Production:** No open blocking defects, at least one consuming team has successfully integrated in staging, and the Package Owner approves General Availability.

**Required artifacts:** Stabilization report (issues found, patches released, adopter feedback), GA approval record.

### 5.5 Production

**Entry:** Package Owner approves General Availability.

**Activities:** Package is published as Generally Available. All quality gate requirements apply to every subsequent release. Package follows the standard lifecycle (Stages 1–14) for all changes.

**Exit to Maintained:** No further distinction — Production and Maintained are the same steady state once the package is no longer receiving active development.

### 5.6 Maintained

**Entry:** Active development has concluded. Package receives only bug fixes and security patches.

**Activities:** Bug fixes enter at Stage 7. Security patches follow the security change management procedure (§7.3). No new features. No breaking changes. Package Owner confirms the Maintained status in the package registry.

**Exit to Deprecated:** Package Owner, in consultation with the Principal Architect, determines the package should be replaced or retired.

### 5.7 Deprecated

**Entry:** Package Owner and Principal Architect agree on deprecation.

**Activities:** Deprecation notice is issued per §7.6. The notice specifies the deprecation date, the removal date, and the migration path (pointing to the replacement package or API). The deprecation period may not be shorter than 12 months for any package with known production consumers. The MIG document is written and published at deprecation time.

**No new consumers** may adopt a deprecated package after the deprecation notice is published.

**Exit to Archived:** Removal date passes and all known consumers have migrated.

**Required artifacts:** Deprecation notice (published in package registry and release notes), MIG document.

### 5.8 Archived

**Entry:** Removal date passes and Package Owner confirms no production consumers remain.

**Activities:** Package is removed from the active registry. Source code is moved to the archive repository. All specification documents are marked Archived. No further changes are made.

**This state is terminal.** An archived package may not be unarchived. A replacement must be proposed as a new package.

**Required artifacts:** Archival record (date, confirming engineer, confirmation that all consumers have migrated).

## 6. Quality Gates

Every release must pass all applicable quality gates before advancing to Stage 11. Gates are checked in the order listed. A gate failure returns the work to the indicated stage.

### 6.1 Gate Definitions

| Gate | Required for | Checked by | Return stage on failure |
|---|---|---|---|
| G1 — Architecture Review | New packages, ARCH changes, breaking API/RT changes | Principal Architect or Chief Architect | Stage 4 |
| G2 — Specification Review | All Tier 2 document changes | Specification Review panel (§6.2) | Stage 6 |
| G3 — API Conformance | All releases | Staff Engineer (API owner) | Stage 7 |
| G4 — Runtime Conformance | All releases | Staff Engineer (RT owner) | Stage 7 |
| G5 — Security Review | Any change to SEC document or security-relevant RT behavior | Security owner | Stage 6 |
| G6 — Performance Review | Any change to a component with a PERF document | Performance owner | Stage 7 |
| G7 — Test Coverage | All releases | Package Owner | Stage 7 |
| G8 — Documentation Completeness | All releases | Package Owner | Stage 6 |
| G9 — Observability Readiness | All production deployments | Release Manager | Stage 6 |
| G10 — Rollback Readiness | All production deployments | Release Manager | Stage 12 preparation |

### 6.2 Specification Review Panel

The Specification Review panel for a package consists of: the Package Owner, the Staff Engineer responsible for API and RT, and one Reviewer from a consuming team (nominated by the Principal Architect). The panel reviews all Tier 2 document drafts before they are frozen. Approval requires unanimous agreement. A dissenting panel member must file a written objection; the Package Owner escalates unresolved objections to the Principal Architect.

### 6.3 Gate Checklists

Each gate has a checklist that the responsible reviewer signs before marking the gate passed. Checklists are maintained per package as appendices to the TEST document and are updated when the specification changes. The Release Manager assembles all signed checklists into the release record before Stage 11.

### 6.4 Review SLAs

| Gate | Review SLA |
|---|---|
| G1 — Architecture Review | 5 business days from submission |
| G2 — Specification Review | 3 business days from draft distribution |
| G3–G4 — API/RT Conformance | 2 business days |
| G5 — Security Review | 3 business days |
| G6 — Performance Review | 2 business days |
| G7 — Test Coverage | 1 business day (automated gate) |
| G8 — Documentation Completeness | 2 business days |
| G9–G10 — Observability/Rollback | 1 business day |

If a review SLA is missed, the Package Owner is notified immediately. If the SLA is missed by more than 2 business days, the Principal Architect is notified and assigns a substitute reviewer.

### 6.5 Gate Bypass

A gate may be bypassed only under all of the following conditions:

1. A production incident is actively causing customer harm.
2. The change is the minimal remediation to stop the harm.
3. Written approval is obtained from the Package Owner and the Principal Architect.
4. The bypass is recorded in the release record as a known risk.
5. The bypassed gate is completed retrospectively within 5 business days of the bypass deployment.

A gate bypass does not waive the gate requirement permanently. If the retrospective gate check reveals a defect, it is treated as a production bug and enters Stage 7 immediately.

## 7. Change Management

### 7.1 Breaking API Change

**Definition:** Per EDS-001 §6.5 — any removal, rename, signature change, or semantic change to a public API symbol.

**Process:**
1. Originating engineer files an RFC with a minimum 5 business day comment period.
2. Architecture Review is conducted.
3. ADR is filed.
4. API document is updated to a new major version.
5. RT document is reviewed and updated if affected.
6. MIG document is written for the version boundary.
7. Consuming teams are notified with minimum 5 business days before the new major version is published to production-facing registries.
8. Previous major version enters a support window of minimum 6 months from the date the new major version reaches Production status.

**Approver:** Principal Architect (domain), Chief Architect (cross-domain).

### 7.2 Runtime Behavior Change

**Definition:** Any change to an observable behavior specified in an RT document.

**Process:**
1. If breaking per EDS-001 §6.5: follow the Breaking API Change process (§7.1).
2. If non-breaking: the RT document owner issues a minor or patch version per EDS-001 §4.5. Notification to consuming teams is required. RFC is not required but may be opened if the change has cross-team impact.

**Approver:** Staff Engineer (RT owner), with Package Owner sign-off.

### 7.3 Security Change

**Definition:** Any change to a SEC document, or any implementation change that affects a trust boundary, authentication, authorization, or secrets handling.

**Process:**
1. Security owner is notified immediately upon discovery of the need for a security change.
2. If the change is in response to a vulnerability: follow the emergency change process (§9.5) for any change that mitigates active exploitation. For non-exploited vulnerabilities, the standard process applies with expedited review SLAs.
3. SEC document is updated to a new version.
4. G5 (Security Review) is mandatory and cannot be bypassed for security changes.
5. Security changes are not published in release notes with vulnerability details until after deployment (coordinated disclosure).

**Approver:** Security owner, Package Owner, and Principal Architect.

### 7.4 Performance Change

**Definition:** Any change to a guarantee stated in a PERF document, or any implementation change expected to materially affect the metrics defined in the PERF document.

**Process:**
1. If a guarantee is being relaxed (a breaking change): follow the Breaking API Change process (§7.1), with PERF document updated alongside API.
2. If a guarantee is being improved: PERF document is updated to a minor version. RFC not required. Notification to consuming teams is recommended.
3. G6 (Performance Review) must be passed before any performance-relevant change is released.

**Approver:** Performance owner, Package Owner.

### 7.5 Architectural Change

**Definition:** Any change to module boundaries, dependency rules, or ownership assignments in an ARCH document.

**Process:**
1. RFC is filed with minimum 5 business day comment period.
2. Architecture Review is mandatory.
3. ADR is filed.
4. ARCH document is updated to a new version.
5. All downstream Tier 2 documents are reviewed for consistency.
6. If architectural change implies API changes, the Breaking API Change process (§7.1) is run in parallel.

**Approver:** Chief Architect.

### 7.6 Deprecation

**Definition:** The decision to retire a symbol, API version, package feature, or package.

**Process:**
1. Package Owner and Principal Architect agree on deprecation.
2. Deprecation notice is published in the API document (for symbol deprecation) or the package registry (for package deprecation).
3. Deprecation notice includes: deprecated item, deprecation date, removal date, migration path, and replacement (if any).
4. MIG document is published at deprecation time.
5. Minimum deprecation period: 12 months for packages with production consumers; 6 months for individual symbols with known consumers; 3 months for symbols with no known external consumers.
6. Removal proceeds only after the Package Owner confirms that all known consumers have migrated.

## 8. Release Governance

### 8.1 Semantic Versioning Policy

All packages follow semantic versioning (`MAJOR.MINOR.PATCH`), aligned with document versioning per EDS-001 §6.6.

- **MAJOR:** Breaking change as defined in EDS-001 §6.5. Requires RFC, Architecture Review (for architectural changes), and minimum 5 business day consumer notification before production registry publication.
- **MINOR:** Additive non-breaking change. Requires Specification Review (G2). Consumer notification required; no minimum advance notice period.
- **PATCH:** Non-behavioral clarification, bug fix that restores specified behavior, or documentation-only change. Requires G7 (Test Coverage) and G8 (Documentation Completeness). No advance consumer notification required.

Pre-release labels:
- `X.Y.Z-alpha.N` — internal only, no consumer commitments
- `X.Y.Z-beta.N` — shared externally for feedback, no stability guarantee
- `X.Y.Z-rc.N` — release candidate, feature-frozen, stability target
- `X.Y.Z` — Generally Available

A pre-release version does not trigger the mandatory consumer notification periods. Consumer notification periods apply only to Generally Available versions.

### 8.2 Release Approval Workflow

1. Release Manager assembles the release record: version, release notes, all quality gate checklists, test report, monitoring plan, and rollback procedure.
2. Package Owner reviews and signs the release record.
3. For MAJOR releases: Principal Architect co-signs.
4. For platform-wide or cross-domain releases: Chief Architect co-signs.
5. Release Manager executes the release tag and registry publication.
6. Release notes are published within 1 business day of tag creation.

No release may be tagged without a complete, signed release record.

### 8.3 Rollback Policy

Every release must have a rollback procedure defined before deployment. The rollback procedure is part of the release record and must be tested in staging before production deployment.

**Automatic rollback triggers:** Any OBS alert that fires at P0 severity within the monitoring window (Stage 13) triggers an automatic rollback unless the Release Manager actively vetoes it with a documented justification within 15 minutes.

**Manual rollback:** The Release Manager may trigger a rollback at any time during the monitoring window or after, with Package Owner notification. Rollback does not require prior approval.

**Rollback record:** All rollbacks are recorded in the release record with timestamp, trigger, and outcome.

**Post-rollback:** After a rollback, the change re-enters Stage 9 (Testing) and may not be re-deployed until the root cause is identified and resolved. A rollback does not reset the release version — a new patch or minor version is required for the re-release.

### 8.4 Hotfix Workflow

A hotfix addresses a production defect in a released version without introducing new features.

**Entry condition:** A production defect is confirmed by the on-call engineer and classified as requiring immediate remedy before the next planned release cycle.

**Process:**
1. Package Owner approves hotfix classification.
2. Hotfix branch is cut from the production tag (not from the development branch).
3. Fix is implemented (Stage 7).
4. Expedited code review: minimum 1 reviewer, 4-hour SLA.
5. Automated tests must pass (Stage 9).
6. G3 (API Conformance), G4 (RT Conformance), and G7 (Test Coverage) are mandatory. All other gates are waived with Package Owner sign-off, recorded in the release record.
7. Release Manager executes the hotfix release as a PATCH version.
8. Hotfix is merged back to the development branch within 1 business day.

**Hotfixes may not introduce behavioral changes beyond the minimum required to correct the defect.** A hotfix that expands scope is reclassified as a standard minor release.

### 9.5 Emergency Change

An emergency change is a deployment that bypasses some or all standard workflow stages due to an active production incident causing customer harm.

**Conditions for emergency change:**
- Active customer harm confirmed by the on-call engineer.
- The proposed change is the minimal remediation.
- Package Owner has been notified and is actively engaged.

**Minimum required before deployment:**
- Implementing engineer confirms the change is targeted and minimal.
- One reviewer has reviewed and approved (no SLA — best effort, minimum 30 minutes).
- Automated tests pass.
- Package Owner verbally approves (written confirmation within 1 hour).

**Post-emergency obligations (all within 5 business days):**
- Release record is completed retroactively.
- All bypassed quality gates are completed retrospectively.
- Root cause analysis is filed.
- Corrective action item is tracked to completion.
- Principal Architect is notified and reviews the root cause analysis.

An emergency change does not exempt the package from any permanent compliance requirement. It is a time-limited exception, not a process waiver.

## 9. Cross-Cutting Obligations

### 9.1 Specification Debt

Any implementation behavior that is not covered by a frozen specification document is specification debt. Specification debt is tracked as a blocking defect with the same priority as a code defect. It is remediated by updating the appropriate specification document through the standard change process. It is not resolved by adding comments to code.

### 9.2 Release Record

The release record is a structured artifact maintained per release. It contains:

- Package name and version
- Release type (major / minor / patch / hotfix / emergency)
- Release notes (link to published notes)
- RFC reference (if applicable)
- ADR reference (if applicable)
- Document version changes (list of all EDS-001 document versions changed in this release)
- Quality gate checklists (signed, per §6.3)
- Test report (link)
- Monitoring plan (observation window, responsible on-call)
- Rollback procedure (link to RUN document section)
- Approver signatures (Package Owner, Principal Architect for MAJOR, Chief Architect as applicable)

Release records are retained indefinitely and are available to all engineers.

### 9.3 Incident Learning

Every production incident that results in a rollback or an emergency change produces a Root Cause Analysis. The Root Cause Analysis identifies: the contributing specification, implementation, or operational failure; the contributing process failure (if any); and the corrective action. Corrective actions are tracked by the Package Owner to completion. If a corrective action requires a specification change, it enters the standard lifecycle at Stage 3 or Stage 6 as appropriate.

### 9.4 Compliance Review

The Architecture Review Board conducts an annual compliance review of all Production and Maintained packages. The review checks: EDS-001 compliance (required document set, content rules), EES-001 compliance (lifecycle adherence, quality gate records), and open specification debt. Findings are reported to the Chief Architect and are actionable within 60 calendar days.

## 10. Relationship to EDS-001

EES-001 and EDS-001 form a pair. Neither is complete without the other.

| Concern | Governing Standard |
|---|---|
| What documents exist | EDS-001 §3 |
| What each document contains | EDS-001 §4 |
| Which document owns each topic | EDS-001 §5 |
| How documents reference each other | EDS-001 §6 |
| When documents change | EDS-001 §7 |
| How engineering work is staged | EES-001 §4 |
| Who does each stage | EES-001 §3, §4 |
| What gates a release | EES-001 §6 |
| How change classes are managed | EES-001 §7 |
| How releases are governed | EES-001 §8 |
| How packages are born and retired | EES-001 §5 |

When a question cannot be answered by either standard, the resolution process is: the Chief Architect issues a written ruling, which is incorporated into the appropriate standard as a patch version amendment.
